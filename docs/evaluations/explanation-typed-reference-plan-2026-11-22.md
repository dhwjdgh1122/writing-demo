# 실제 인용과 사전 참조를 구분하는 오프라인 설계 검증

2026-11-22 / #22·Draft PR #55. [사전 참조 실험](explanation-lexical-reference-result-2026-11-22.md)에는 남은 단어 문제를 포착했지만 원문에 없는 기본형·대안어휘를 따옴표로 써 차단된 출력이 있었다. 같은 실험에는 실제 의미 오판도 있었으므로 인용 검사 전체를 완화하지 않는다.

## 이전 구현과 구분

PR #34는 실제 before/after 근거와 설명문을 분리했고, `evidenceIds`도 시험했다. 당시 ID는 원문·후보의 변경 구간을 가리켰으며 사전 출처가 아니었다. 기본형 풀이를 따옴표 없이 쓰는 것은 허용했지만, 실제 문장에 없는 용어를 인용하면 계속 차단했다. 이번 사전 입력 실험도 출력은 기존 설명 문자열이라 그 구분을 검사할 수 없었다.

새 설계는 모델이 인용·참조의 성격을 명시하도록 하고 서버가 각기 다른 근거로 확인한다. 먼저 **모델 호출 없이 파서와 렌더링 경계를 검증**한다. 이것이 모델의 형식 준수나 의미 오류를 해결했다는 뜻은 아니다.

| 조각 유형 | 받을 값 | 확인·표시 방식 |
| --- | --- | --- |
| 일반 설명 `text` | 설명 문자열 | 인용 문자를 금지한다. 없애서 자동 수정하지 않는다. 의미 정확성은 별도 평가다. |
| 실제 인용 `input_quote` | source/candidate 구분·인용문 | 지정한 원문 또는 해당 후보에서 공백·줄바꿈까지 정확한 연속 구절인지 확인하고 서버가 인용 표시를 붙인다. 다른 후보의 구절은 허용하지 않는다. |
| 사전 참조 `lexical_reference` | 서버가 제공한 고정 ID | 기존 공식 사전의 두 항목에서 용어명을 읽어 `사전 용어`임을 구분해 표시한다. 모델이 정의·라벨·URL을 바꾸지 못하게 한다. |

## 최소 검증 범위

- 후보 ID·조각 종류·필드를 엄격하게 검사하고 조각 수와 최종400자 한도를 지킨다. 서버가 붙이는 인용/참조 표시도 길이에 포함한다.
- 실제 없는 인용, 다른 후보 인용, 공백·개행·Unicode를 고쳐 쓴 인용, 알 수 없는 사전 ID, 정의·라벨·URL 주입과 자유문 인용 우회를 거부한다.
- 여러 인용 조각을 합쳐 문장에 없는 단일 인용으로 만들지 않는다. 인용 조각마다 근거와 표시 경계를 유지한다.
- 일반 설명이 서버의 `사전 용어` 라벨을 흉내 내는 경로를 막는다. 문자열을 여러 조각으로 나눈 경우도 합친 뒤 검사한다. 실제 입력에 있던 동일 문구를 정확히 인용한 경우는 인용 표시를 유지하고 사전 근거로 승격하지 않는다. 이는 예약 표시의 출처 검사이며 일반 설명의 모든 오해 가능성을 제거한다는 뜻은 아니다.
- 최소 proof에서는 인용 안에 다시 인용 문자가 있는 경우도 거부한다. 실제 중첩 인용이 틀렸다는 뜻이 아니라 표시 경계를 단순하게 유지하는 실험상의 제약이며, 제품 적용 전에는 별도 검토가 필요하다.
- 사전 용어는 사전 항목으로 확인된다는 뜻이다. 해당 문맥에 적절하거나 원문에서 실제로 수정됐다는 뜻이 아니다. 일반 설명의 잘못된 단정은 여전히 별도 평가가 필요하다.
- 시험 자료를 사람이 조립한 것은 파서 시험이다. 기존 모델 원출력을 조립 자료로 대체하거나 실패를 성공으로 다시 분류하지 않는다.

제품 응답 계약·프롬프트·API·UI는 바꾸지 않는다. 공식 사전 항목은 [이미 확인한 동일 자료](../../scripts/lib/explanation-lexical-reference.mjs)를 재사용하고 새로운 출처를 생성하지 않는다. 추후 실제 모델 진단을 한다면 그 입력·원출력·호출 계획을 별도로 먼저 고정한다. 단어 뜻 표시만으로 R-03의 잔존 오류 안내나 전체 #22 기준을 통과시키지 않는다.

응답 스키마 검토에 참고한 [Gemini 공식 구조화 출력 문서](https://aistudio.google.com/docs/structured-output)는 `anyOf` 예시와 스키마 복잡도 제한, 앱에서 값·의미를 별도로 검사해야 한다는 점을 명시한다. 문서의 최신 예시 모델로 전환하지 않으며, 스키마 지원 안내만으로 현재 사용 모델의 실제 응답 성공을 주장하지 않는다.

## 오프라인 확인 결과

파서8개·실행기5개를 포함해 단위/API181/181 및 타입 검사가 통과했다. 독립 코드 검토에서 자유문이 사전 라벨을 위장하는 경로를 발견해 최종 합성 후 검사로 막았으며, 보완 후 추가 차단 문제는 발견하지 못했다. 양쪽 제공자의 dry-run은 모델을 호출하지 않는다. 후속 실제 요청은 [별도4회 진단 계획](explanation-typed-reference-live-plan-2026-11-22.md)을 따른다.
