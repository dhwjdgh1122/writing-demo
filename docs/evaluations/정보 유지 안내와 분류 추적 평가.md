# 정보 유지 안내와 분류 추적 평가 — I

2026-11-16 / #22 / 코드 `bd84781` / Codex AI 보조 예비 평가. 사람의 독립 평가나 사용자 효과 측정은 아니다.

## 결론

**원문 오타를 그대로 유지하라고 권하는 조합 방식은 바꿨지만, 설명 품질은 아직 완료 기준에 미달한다.** Gemini의 반환 사례에서는 단어 수정 여부와 복합 의미 변화를 구분했으나, 조사 표기·띄어쓰기 설명 누락이 남고 서비스 오류로 별도 사례 확인을 마치지 못했다. 엘리스는 조건 누락과 잘못된 의미 분류, 참조 연결 오류가 남았다. PR #23을 Draft로 유지하고 main에 병합하지 않는다.

## 무엇을 바꿨는가

- H는 연결된 원문 표현을 유지 안내에 그대로 복사했다. 원문에 오타가 있으면 그 오타까지 권할 수 있었다. I는 구체적인 전후 값·조건을 앞 문장에서 설명하게 하고, 서버 안내에는 날짜·수치·조건 등 **정보의 종류**를 넣는다. 안내는 “맞춤법·띄어쓰기는 다듬되, … 정보는 원문의 뜻에 맞게 유지하면 됩니다.” 형태다.
- 프롬프트에서 문맥상 명확한 오탈자·단어 오용의 수정과 사실 정보 변경을 구분했다. 그대로 남은 단어를 고쳤다고 설명하지 않도록 명시했다. 미수정 용례 문제의 자유 안내나 모델의 잘못된 분류까지 코드로 보증하지는 않는다.
- 수동 평가의 `modelDrafts`에 스키마·후보 ID 검사를 통과한 내부 구조를 참조 검사 전에 복사한다. `meaningChanges`·요약·자유 안내와 조합 후 `adapterExplanations`를 비교할 수 있다. 운영 요청에는 관찰 함수를 연결하지 않는다. 제공자 응답 봉투·인증정보·스키마/ID 오류 응답은 기록하지 않는다.
- 교정 후보 생성·화면·공개 API·실제 `.env`는 유지했다. 기업 데이터가 아닌 작성 원문과 고정 후보만 전송했다.

`합`은 실제 후보 안에 있으므로 문자열 검사를 통과했다. 하지만 의미를 설명하는 충분한 구절이 아니다. **인용이 존재한다는 검사와 설명이 타당하다는 판정은 별개**라는 한계를 다시 확인했다.

## 이번 기록으로 구분할 수 있는 것

- 엘리스 E-03의 `meaningChanges`에는 quantity·action·negation만 있고 condition·certainty는 없다. 서버가 분류를 바꾼 것이 아니라 모델이 조건을 누락하고 확정성 변화를 다른 종류로 분류한 것이다.
- E-04는 직접 따옴표, I-02는 미사용 참조가 형식 거부의 원인이었다. E-07·R-04는 의미 참조와 요약의 연결 불일치다. 단순히 오류 코드만 있었던 H보다 원인을 구체적으로 확인할 수 있다.
- 이번 반환 설명에는 원문 오타를 그대로 유지하라는 안내가 없었다. 다만 엘리스 E-04가 거부됐고 Gemini 별도 사례는 미실행이므로, 실사용에서 이 문제가 완전히 사라졌다는 결론은 아니다. 회귀 테스트는 잘못 분류된 전체 원문에도 오타를 유지 권고로 복사하지 않는 **서버 조합 동작**을 확인한다.
