## 결론

**참조 번호와 요약의 불일치를 줄이는 구조로 전환했지만 #22는 미완료다.** 엘리스에서 역할·부정 변화와 날짜·오타 혼합 사례의 설명이 제공됐다. 그러나 후보 간 내용 혼동, 후보 ID 불일치, 의미 방향을 거꾸로 설명한 초안이 남았다. Gemini는 첫 요청에서 서비스 오류로 중단해 이번 구조의 설명 품질을 확인하지 못했다. PR #23을 Draft로 유지하며 main에 병합하지 않는다.

## 변경 내용과 완료 조건

이전 I는 모델이 참조 목록·의미 변화 연결·전체 요약을 각각 작성했다. J는 `changes[{kind,before,after,effect}]`로 한 변경의 근거와 영향을 묶고 서버가 각 항목을 빠짐없이 표시한다. 별도 참조 번호와 요약 템플릿은 제거했다. 남아 있는 용례 문제는 `notes[{text,reason}]`로 구별한다.

- 오탈자·띄어쓰기·단어 오용·뜻이 같은 표현 수정은 서버가 종류별 짧은 설명을 붙인다. 의미 변화의 영향은 모델이 작성한다. 모델의 수정 종류 판단 자체는 여전히 검증 대상이다.
- `before`는 원문, `after`는 해당 후보에서 정확히 찾는다. 동일 구절을 변경으로 표시하거나, 글자가 달라졌는데 공백만 바뀌었다고 분류한 항목을 거부한다. 같은 변경의 중복, 빈 의미 영향, 자유 설명의 직접 인용도 검사한다.
- notes의 인용은 원문과 후보 양쪽에 남아 있어야 한다. 고쳐진 단어를 미수정 문제로 표시하거나 새 단어를 제안하는 용도가 아니다.
- 표시 형식은 `원문 → 후보: 수정 내용/영향` 항목을 세미콜론으로 연결한 짧은 단락이다. 필요하면 종류별 정보 유지 안내를 붙인다. 최종 400자 제한, 공개 API, 선택·적용 흐름, 교정 후보 생성은 유지했다.
- 인용의 존재·항목 형식 검사는 의미의 타당성·완전성을 보증하지 않는다. 실제 실패 사례에서 중요한 정보가 정확히 설명되고 별도 사례에서도 확인돼야 품질 완료로 판단한다. 표시 성공률을 높이기 위해 오류 검사를 해제하지 않는다.

## 남은 작업

1. 후보끼리 변경 내용을 복사하는 오류와 ID 불일치를 줄여야 한다. 후보별 입력 분리 등은 후속 검토 방향이며 아직 구현하지 않았다.
2. 뜻이 반대로 설명되거나 중요한 조건이 빠지는 문제는 실제 사례로 확인해야 한다. 모든 변경 항목을 출력한다는 보장은 모델이 필요한 항목을 모두 찾았다는 보장이 아니다.
3. 한 글자 인용·중복 설명·서술 오타를 줄이고, 새 표시 형식이 사용자에게 이해하기 쉬운지 확인해야 한다.
4. Gemini 실패/미실행과 엘리스 실패 사례, 이번 범위 밖의 기존 사례를 확인해야 한다. 실패를 지우거나 성공할 때까지 반복해 통과로 만들지 않는다.
