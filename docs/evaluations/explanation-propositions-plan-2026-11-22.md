# 문장 쌍의 검토 명제 생성 진단 계획

2026-11-22 / #22·Draft PR #55 / 실행 전 기준. 제품 코드·설명 계약·전체 품질 기준은 변경하지 않는다.

**실행 후 상태:** 사용자의 「실행」 지시에 따라 아래 고정 기준으로 5회 요청했다. Gemini 503 이후 남은 1회는 미실행으로 보존했다. [원자료와 내용 검토 결과](explanation-propositions-result-2026-11-22.md)를 별도로 연결하며 후속 판단·제품 적용은 진행하지 않는다.

**준비 당시 기록:** 사용자의 작업 중단 요청으로 준비만 완료했고 실제 모델 호출 0회·계획 6회 미실행 상태로 보존했다. 이후 재개 지시를 받아 실행했으며 아래 실행 전 기준은 변경하지 않았다.

## 확인하려는 문제와 기존 시도

같은 조건이나 제한을 다르게 쓴 문장을 잘못 구분하거나, 수량·조건·미확정 정보를 빠뜨리는 문제가 남았다. 이번에는 **원문과 후보가 각각 전달하는 내용을 검토용 명제 목록으로 먼저 만들 때, 중요한 정보와 그 정보에 걸린 조건을 보존하는가**만 확인한다. 이 명제는 모델이 만든 검토 대상이며 확인된 사실이나 정답이 아니다.

- `641931e`의 [전체 동등성 사례](https://github.com/dhwjdgh1122/writing-demo/blob/641931e/tests/fixtures/explanation-equivalence-cases.json)는 두 문장 전체의 동등성 판단을 다뤘다. 이번에는 동등성·변화 여부를 답하게 하지 않고, 두 문장에서 검토할 구체적인 명제의 합집합을 제안하게 한다.
- [독립 조건 추출 18회](explanation-isolated-conditions-result-2026-11-22.md)는 문장별 조건·행동 구절을 뽑았다. 이번 명제에는 조건뿐 아니라 수량·예정·부정·기한 등 해당 진술을 해석하는 데 필요한 정보를 함께 보존하도록 한다. 단순히 필드 수를 늘린 사실을 개선으로 보지 않는다.
- 장래에는 생성한 동일한 명제 `h`를 고정한 뒤, 각 문장만 따로 제공해 그 명제를 뒷받침하는지·모순되는지·판단할 수 없는지 검토하는 방식을 고려할 수 있다. **이번에는 그 후속 판단을 실행하지 않는다.** 첫 생성부터 정보를 빠뜨리거나 의미를 바꾸면 후속 단계가 그 오류를 물려받을 수 있기 때문이다.

## 고정 입력과 출력

[재사용 사례 fixture](../../tests/fixtures/explanation-propositions-2026-11-22.json)의 CT-03·EQ-03·E-03을 그대로 사용한다. CT-03·E-03은 [기존 gate 원본](../../tests/fixtures/issue22-original-gate-2026-11-22.json), EQ-03은 위 `641931e`의 문장 쌍과 출처 기록을 보존한다. 모두 기존 개발·평가용 고정 사례이며 새로운 사용자 데이터가 아니다.

- 입력은 역할을 표시하지 않는 `t1`·`t2` ID와 각 문장만 담은 `texts` 배열이다. 두 문장은 한 요청에 함께 들어간다. 첫 생성 단계의 독립 입력 실험은 아니다.
- 사례 ID·`required`·`expected`·출처 메타데이터·과거 출력·평가표·사전 정의는 모델에 보내지 않는다. 이번 문서의 아래 판정표도 평가에만 사용한다.
- 출력은 `propositions` 배열 1~8개다. 항목은 중복 없는 `h1`~`h8` ID, `statement` 1~300자, `originId`(`t1` 또는 `t2`), `quote` 1~2000자로 제한한다. 다른 필드와 자동 정답 판정은 받지 않는다.
- 각 명제는 출처로 지정한 한 문장만으로 뒷받침되어야 한다. 인용은 그 문장 안에 실제 있는 연속 구절이어야 하며, 조건·부정·예정 등을 잘라내 의미를 강화해서는 안 된다. 두 문장의 정보를 섞어 제3의 사실을 만드는 것도 실패다.
- 코드 검사는 구조·길이·ID·완전히 같은 명제 문자열의 중복·출처별 정확한 인용만 확인한다. 의미상 중복, 인용과 명제의 의미 관계, 중요한 누락은 원문과 대조하는 별도 내용 검토로 판정한다. 이번 AI 내부 검토를 실제 사람의 검증으로 보고하지 않는다. 문구가 다르다는 이유만으로 두 명제가 다른 뜻이라고 판단하지 않는다.

[진단 모듈](../../scripts/lib/explanation-propositions.mjs), [단위 검사](../../tests/explanation-propositions.test.ts), [실행기](../../scripts/evaluate-explanation-propositions.mjs)를 사용한다. 구조·출처 검사의 성공값은 의미 평가 미수행을 명시한다. 잘못된 출력은 원자료로 보존하며 자동 수정하거나 정답으로 대체하지 않는다.

## 원문 기준 판정표

모델이 만든 명제 목록만을 분모로 삼으면 생성하지 않은 정보가 평가에서 사라진다. 따라서 아래 원문 체크리스트와 실제 두 문장에 비추어 **제안한 명제의 정확성, 중요한 정보의 누락, 의미상 중복**을 분리해 기록한다. 항목의 개수나 특정 문구를 정답 형식으로 강제하지 않는다.

| 사례 | 놓치면 안 되는 내용 | 과잉 판정 방지 |
| --- | --- | --- |
| CT-03 | `회원인 경우에만 자료를 받을 수 있습니다.`와 `회원만 자료를 받을 수 있습니다.`의 회원 제한과 받을 수 있다는 가능성을 보존한다. | 같은 제한을 한 명제로 묶어도 된다. 비회원도 받는다고 하거나, 회원은 반드시 이미 받았다고 바꾸면 안 된다. 표현 차이·명제 수 차이만으로 의미 변화를 판정하지 않는다. |
| EQ-03 | `승인을 받은 경우에만 자료를 공개합니다.`의 명시적 승인 제한과 `승인을 받으면 자료를 공개합니다.`의 조건부 진술을 구별해 보존한다. | 한쪽에만 있는 `만`을 양쪽으로 옮기지 않는다. 후보가 실제 무승인 공개를 허용한다고 추측하거나, 원문을 승인만 받으면 반드시 공개한다는 충분조건으로 강화하지 않는다. 이번 단계에서 최종 동등성 판정을 요구하지 않는다. |
| E-03 | 원문의 담당자 확인 전제, 화요일까지라는 기한, 8명, 발송 예정, 별도로 명시된 발송 미확정을 보존한다. 후보의 화요일까지·10명·발송한다는 서술도 보존한다. | 담당자가 이미 확인했다거나 발송이 실제 확정·완료됐다고 단정하지 않는다. 기한을 담당자 확인 같은 논리적 전제로 바꾸지 않는다. `8명에게 발송한다`처럼 조건·예정·미확정을 제거해 독립 사실로 만들지 않는다. |

E-03처럼 한 명제에 여러 정보가 들어가도 각 정보가 보존되었는지 확인한다. `예정`을 남겼다는 이유만으로 별도의 `발송은 확정되지 않았습니다`까지 충분히 보존했다고 자동 처리하지 않으며, 반대로 의미를 정확히 담은 문장에 특정 낱말이 없다는 이유만으로 누락 판정을 하지 않는다. 범위가 애매하면 판정 근거와 불확실성을 함께 남긴다.

이 단계는 선택 기준·교정 이유를 생성하지 않는다. 선택 기준이 없다는 사실만으로 명제 생성 실패라고 하지 않으며, 명제 생성을 잘했다고 기존 설명 평가의 선택 기준을 충족한 것으로 계산하지도 않는다. [#22 원래 품질 gate](issue22-original-gate-2026-11-22.md)의 의미 정확성·누락·사용자 선택 안내 기준은 그대로 유지한다.

## 실행 규모와 기록

**3사례 × 2제공자 = 최대 6요청**이다. Gemini `gemini-3.5-flash-lite`와 엘리스 `gpt-4o-mini`의 기존 연결·출력 토큰·추론 설정을 유지한다. 제공자별 사례당 한 번이며 자동 반복·후속 판단·모델 전환은 없다. 별도 실험 스키마를 사용하므로 제품 설명 API나 브라우저의 동작 검증으로 보고하지 않는다.

호출 직전 기존 장부에 예약하고 실제 입력·지침·스키마·코드 해시·원출력·구조/출처 결과·지연·토큰을 남긴다. 성공·실패·미실행을 구분하며 원문 판정표에 따른 내용 검토는 별도 기록한다. 이번 6회는 실험 크기이며 사용자가 해제한 전체 호출 상한을 다시 설정하는 것이 아니다.

서비스·쿼터·스키마 요청 거절·시간 초과·원출력 확보 실패가 발생하면 해당 제공자의 남은 실행을 중단하고 실패 요청도 장부에 남긴다. 다른 제공자는 같은 사전 고정 계획으로만 실행하며 오류를 이유로 실패 요청을 다른 모델에 대신 보내지 않는다. 확보한 원출력의 JSON·출처 검사 실패는 실패 근거로 보존한다. 실패를 통과시키려고 실행 중 지침이나 원문 체크리스트를 바꾸거나 재호출하지 않는다.

## 결론 범위와 다음 단계의 조건

단 한 번의 중요한 의미 왜곡·정보 누락도 해당 사례의 생성 성공이 아니다. 구조와 인용만 통과한 결과는 의미 성공으로 세지 않는다. 후보의 더 확정적인 표현을 현실의 사실로 해석하는 등 새로운 오류가 있으면 그 경로를 그대로 후속 판단에 연결하지 않는다.

세 고정 사례에서 얻은 단회 관찰로 일반 정확도·통계적 효과·사용자 판단 효과를 주장하지 않는다. 개선이 없으면 같은 구성을 더 반복하지 않는다. 일부 정보 보존이 나아져도 누락과 새 오류를 함께 기록하며 제품 채택으로 이어 붙이지 않는다.

모든 중요 정보가 보존된 제안 목록을 확보한 경우에만, 고정된 명제를 각 문장에 독립 대조하는 후속 설계를 검토한다. 그때도 명제 생성과 후속 판단의 오류를 분리하고 기존 전체 동등성 실험과 비교할 기준을 새로 확정해야 한다. **이번 결과는 변화 판정·완성 설명·제품 적용·#22 완료를 뜻하지 않는다.**
