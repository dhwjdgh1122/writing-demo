# 사전 정의 전달 위치의 제한 대조 계획

2026-11-22 / #22·Draft PR #55. [대조 예시 재평가](explanation-freeform-contrast-result-2026-11-22.md)에서 남은 R-03의 지불 문맥 단어 오류와 E-04의 후보별 차이를 재사용한다. 제품 후보 생성·UI·인용 검사·모델은 변경하지 않는다.

## 기존 시도와 이번 질문

PR #23은 이미 결재와 결제의 뜻을 지침으로 제공했고, PR #34의 references/evidenceIds는 원문·후보의 변경 문자열이었다. **단어 뜻 자체를 새로 알려주는 실험이 아니다.** 확인 가능한 과거 자료에서는 공식 사전 정의를 별도 입력 데이터로 제공한 대조는 찾지 못했다.

질문은 **같은 정의·출처를 지침에 넣을 때와 참고 데이터 필드로 줄 때, 문맥 적용과 남은 오류 설명에 차이가 있는가**다. 두 조건에 주는 정보는 같고 배치만 달리한다. 통계적 유의성·일반적인 검색 기반 생성 효과를 입증하는 설계는 아니다. 현행 무힌트 프롬프트를 같은 실행에서 비교하지 않으므로 현행 제품 대비 효과를 직접 산정하지 않는다.

## 입력과 출처

국립국어원 한국어기초사전의 [결재하다](https://krdict.korean.go.kr/chn/dicSearch/SearchView?ParaWordNo=32128)와 [결제하다](https://krdict.korean.go.kr/eng/dicSearch/SearchView?ParaWordNo=32140)의 한국어 정의를 확인했다. 전자는 상급자의 안건 승인, 후자는 대금을 지급해 거래를 마치는 뜻이다. 언어별 화면 주소는 다르지만 한국어 정의를 사용한다.

정의·출처 URL 2개를 [실험 모듈](../../scripts/lib/explanation-lexical-reference.mjs)에 고정한다. 런타임 검색이나 문서 다운로드는 하지 않으며, 두 정의 모두를 모든 사례에 동일하게 준다. 사례별 정답·오류 표시·추천 단어·필수 평가 항목은 모델 입력에 넣지 않는다. 기본형을 원문 인용인 것처럼 취급하지 않고 기존 정확 인용 검사를 유지한다.

- **지침 정의 조건:** 기존 설명 지침과 공통 참고자료 사용 지침 뒤에 두 정의의 JSON을 붙인다.
- **참고 데이터 조건:** 같은 설명·참고자료 사용 지침을 쓰되 동일 JSON 배열을 사용자 입력의 `lexicalReferences`로 전달한다.
- 원문·후보·후보 ID·출력 계약·1~2문장/400자·제공자 설정은 같다. 최종 설명에 자료를 무조건 인용하거나 URL을 쓰게 하지 않는다.
- 새 참고자료 사용 지침은 두 조건 모두에 들어간다. 따라서 이번 결과만으로 그 지침 자체의 효과를 분리하지 않는다.

## 고정 사례와 판정

[복원된 기존 평가 사례](issue22-original-gate-2026-11-22.md)의 원문·후보·필수 항목을 그대로 재사용한다. [실행 입력](../../tests/fixtures/explanation-lexical-reference-2026-11-22.json)은 다음 6개다.

| 사례 | 확인할 결과 |
|---|---|
| R-03 | 오타 수정과 별도로 남은 지불 문맥의 단어 문제를 짚고, 이미 결제로 바뀌었다고 하지 않음 |
| L-01 | 정상적인 팀장 결재를 잘못 지적하지 않음 |
| E-04, 후보 2개 | p1의 실제 단어 수정과 p2의 잔존 문제를 구분하고 수량·미납 상태를 왜곡하지 않음 |
| R-02 | 문맥이 모호하면 승인/지불 상황을 지어내거나 무조건 변경을 권하지 않음 |
| R-05 | 정상 지불 표현을 오류로 지적하지 않음 |
| E-03 | 사전 자료와 무관한 조건 삭제·8→10·미확정 소실·원래 정보를 유지하려는 선택 기준을 놓치지 않음 |

R-03의 과거 필드 이름 `notes`는 당시 응답 계약을 가리킨다. 이번에는 같은 잔존 문제를 자유문 explanation에서 평가하며 의미 기준을 낮추지 않는다. E-04 p2의 남은 지불 문맥 문제도 원래 최종 기준의 추가 조건으로 유지한다.

원출력의 실제 변경·남은 오류·선택 기준·허위 주장과 API 표시/차단을 따로 판정한다. 사전 정의가 맞더라도 문장 적용을 잘못하면 실패이며, 인용 통과도 내용 통과를 뜻하지 않는다. 판정은 AI 보조 검토로 표시하고 실제 사람의 효과 검증으로 표현하지 않는다.

## 실행·중단·확대 기준

- Gemini `gemini-3.5-flash-lite`, 엘리스 `gpt-4o-mini`. 6사례×2조건×2제공자, **최대24회**의 단회 진단이다. 사례별 조건 순서를 번갈아 사용한다. 이것은 사용자가 해제한 전체 호출 상한을 다시 설정하는 것이 아니라 이번 비교의 고정 크기다.
- 호출 직전 새 장부에 예약하고 실패·중단을 포함한다. 원출력·전송값·설정·파일 해시·미실행을 보존한다. 429·503·시간 초과 등 서비스 실패에는 해당 제공자의 나머지 호출을 중단하고 같은 실험을 자동 재실행하지 않는다.
- 참고 데이터 조건이 두 제공자의 대상 오류를 처리하면서 정상·모호 문맥 오탐, 중요한 변화 누락, 새로운 차단을 만들지 않아야 확대를 검토한다. 지침 조건과 차이가 없으면 별도 데이터 구조의 개선 근거가 없는 것으로 기록한다.
- 단회 출력 일부가 좋아져도 바로 제품에 채택하지 않는다. 개선 근거가 있으면 현행 제품 프롬프트 대조·새 문장 경계·원래 반복 기준을 별도로 확인한다. 근거가 없으면 고정 참고 자료를 제품에 넣지 않고 실패 기록을 남긴다.

공백 계산 안내는 원출력 품질과 별도로 취급한다. 이번 6사례는 모두 공백 외의 글자 변화가 있어 계산 안내로 바뀌지 않아야 한다. 실험 도구만 고정 데이터를 주입하고 제품 어댑터·API 계약은 유지한다.
