# 명제 출처 연결·검토 기록의 오프라인 구현

**후속 준비:** 이후 [출처별 명제 제안의 제한 평가 계획·실행기](explanation-proposition-review-plan-2026-11-22.md)를 준비했다. 아래 실행기·지침 미추가와 다음 계획 검토는 이 오프라인 구현 당시의 상태다. 후속 준비도 실제 모델 추가 호출은 0회이며 제품 설명 품질 개선을 입증한 결과가 아니다.

2026-11-22 / #22·Draft PR #55 / 기준 `c14ce90`. [후속 설계](explanation-propositions-followup-design-2026-11-22.md)의 계약 검사·출처 문맥 연결·검토 기록 결합·묶음 조건을 구현했다. **새 실제 모델 호출은 0회이며 제품 API·프롬프트·화면은 변경하지 않았다.**

## 무엇이 달라졌는가

이 도구는 모델 설명을 대신 생성하거나 의미를 자동 판정하지 않는다. 저장된 입력과 명제 제안을 받아 원문 문맥을 그대로 연결하고, 별도로 작성한 검토 기록이 현재 요청에 속하는지 확인한다. 묶음은 검토된 항목을 정리하는 진단 결과이며 제품 교정 이유가 아니다.

| 구분 | 구현한 처리 | 보장하지 않는 것 |
|---|---|---|
| 원문 연결 | 출처 ID로 해당 입력 전체를 그대로 연결. 공백·빈 줄·Unicode·어미 보존 | 명제가 원문을 정확히 해석했는지, 정보를 빠뜨리지 않았는지 |
| 명제 중복 | 같은 출처의 동일 문자열만 거부. 다른 출처의 같은 문장과 다른 표현은 보존 | 표현이 비슷한 명제의 자동 동등성 판정 |
| 검토 기록 | 요청·계약·입출력 해시와 활성 검토 버전 검사 | 검토자의 신원 인증이나 판단 정확성 |
| 묶음 | 모든 구성원의 출처 지지가 확인되고 모든 쌍이 같은 의미로 검토된 경우에만 생성 | 자동 의미 중복 해결이나 #22 품질 통과 |

기존 CT-03의 중복 출력과 E-03의 인용 어미 재작성 실패는 그대로 남는다. 새 계약에서 quote를 제외했으므로 과거 출력을 변환해 통과시킨 결과를 인용 정확도 향상이나 모델 성공으로 계산하지 않는다.

## 사용 계약

[구현 모듈](../../scripts/lib/explanation-proposition-review.mjs)은 기존 `propositionInput`을 재사용한다. 네트워크·모델 제공자·장부 쓰기·파일 저장 기능이 없는 순수 오프라인 모듈이다. 실제 호출용 실행기나 새 모델 프롬프트는 추가하지 않았다.

1. `createPropositionReviewSnapshot(input, rawResponse, { runId, requestId })`는 원응답 JSON을 검사한다. 입력은 t1·t2 두 텍스트, 출력은 `propositions` 안의 `id`·`statement`·`originId`만 허용한다. 기존 1~8항목·h1~h8·300 Unicode 문자 제한을 유지한다.
2. 성공하면 `snapshot`에 입력·명제·`sourceContext`와 결합 키를 보관한다. 입력/출력 해시는 설계의 필드 순서와 원래 배열 순서로 직렬화한 SHA-256이다. 문자열·항목을 정규화하거나 정렬하지 않는다.
3. `applyPropositionReview(snapshot, history, proposedGroups)`는 별도 검토 기록을 검사한다. 명제별 지지, 명제 쌍의 관계, 원문 정보별 누락·보존 기록을 구분한다. 미기록 지지·관계는 명시적으로 `unreviewed`로 남긴다.
4. 묶음 요청의 대표 ID는 구성원 중 하나여야 한다. 원래 명제·출처·문맥을 모두 보존하며 대표 문장을 새로 쓰지 않는다. 모든 쌍의 검토가 필요하므로 A=B·B=C만으로 A=C를 합치지 않는다.

입력과 로컬 메타데이터가 잘못되면 생성 함수는 오류를 던진다. 잘못된 원응답은 `ok: false`와 원응답 해시를 반환하며 성공 스냅샷·출력 해시는 만들지 않는다. 검토 기록이나 묶음 요청이 잘못돼도 일부를 조용히 복구하지 않고 거부한다. 반환값은 호출자가 원자료를 바꾸지 않도록 독립 복제·동결한다.

### 검토 기록과 변경 처리

`history`는 `activeRevisions`와 `revisions`를 받는다. 각 검토 버전에는 `reviewRevision` 양의 정수, 요청 결합 키, `reviewer`(human/ai-assisted와 로컬 ID), `withdrawn`, `supports`, `relations`, `coverage`가 있다. 실제 저장은 호출자 책임이며 이 모듈은 이전 검토 기록을 쓰거나 지우지 않는다.

- 활성 버전은 0개 또는 최신 버전 1개다. 여러 활성 버전, 존재하지 않는 버전, 과거 버전으로의 후퇴, 철회된 버전 활성화는 거부한다. 활성 버전이 없으면 검토되지 않은 상태이며 묶음을 만들 수 없다.
- 모든 과거 버전도 같은 요청 결합 키여야 한다. 최신 검토에서 빠진 지지·관계를 과거의 긍정 판정으로 대신하지 않는다.
- 같은 명제의 중복 지지 기록, 같은 쌍의 정방향·역방향 중복, 자기 자신과의 관계, 없는 명제 ID는 거부한다. 충돌을 임의로 골라 해결하지 않는다.
- `coverage`는 검토자가 원문 정보별로 작성한 기록이다. 보존으로 표시하려면 같은 출처의 명제를 하나 이상 연결해야 하지만, 연결 사실이 보존 판단의 정확성을 증명하지는 않는다. 체크리스트의 완전성을 자동 판정하거나 생성 명제 개수를 분모로 점수를 내지 않는다.
- 묶음은 현재 활성 `reviewRevision`으로 매번 검사한다. 그룹 간 구성원 중복과 미검토·불확실·다른 의미 관계가 있으면 거부한다. 검토를 변경하면 새 버전으로 다시 계산해야 하며, 이전 반환값을 현재 결과로 사용해서는 안 된다.

### 해시와 원자료의 경계

결합 키는 runId·requestId·contractVersion·inputSha256·outputSha256이다. 같은 내용도 별도 요청이면 검토를 자동 재사용하지 않는다. 파싱 성공 내용의 해시와 원응답 바이트 해시는 다르다. 문자열 원응답은 UTF-8로, Uint8Array 원응답은 받은 바이트 그대로 해시하며 잘못된 UTF-8·JSON을 복구하지 않는다.

직렬화된 스냅샷을 검토할 때는 입력·명제의 해시와 원문 문맥을 다시 대조한다. 다만 원응답 바이트가 스냅샷에 들어 있지 않으므로 그 안의 `rawResponseSha256`만으로 원응답을 재검증하거나 인증할 수는 없다. 원응답 보존 책임은 실행·저장 계층에 있으며 이번에는 새 계층을 추가하지 않았다.

모든 결과의 `semanticAssessment`는 `not-performed`다. `ok: true`는 구조·결합 규칙을 통과했다는 뜻이며 사람이 작성한 검토가 맞는지까지 코드가 판단했다는 뜻이 아니다.
