# 설명 정확성 보완 평가 — D·E

관련 작업: [#22](https://github.com/dhwjdgh1122/writing-demo/issues/22), [PR #23](https://github.com/dhwjdgh1122/writing-demo/pull/23). 기준: [교정 설명 평가 기준](../교정%20설명%20평가%20기준.md). 이전 결과: [보완 C](부드러운%20선택%20안내%20추가%20평가.md).

**현재 E에서도 원문 인용 불일치와 중요 정보 누락이 남았다. 일부 기존 오류가 이번 출력에 없었다는 사실만으로 해결 완료로 판단하지 않으며, main 병합 전 초안을 유지한다.** 아래 판정은 Codex 단독 AI 보조 예비 평가다. 사람의 평가나 사용자 효과 검증이 아니다.

## 변경과 실행

C에서는 후보에 없는 `주주세요.`를 인용했고 오탈자 수정을 띄어쓰기 수정으로 설명했다. 생성 지침은 이미 정확한 인용을 요구했지만 실제 응답이 따르지 않았다. 문자열 검사에서는 없는 인용을 차단했으나 인용되지 않은 수정 분류 오류는 걸러지지 않았다. 이것은 관찰한 동작이며 모델 내부 오류 원인을 확정한 것은 아니다.

- **D (`0740a80`)**: 입력 그대로의 짧은 인용, 공백 변경과 글자 변경 구분, 구체적인 정보 유지 안내를 명시했다. 기존 오류 대신 숫자 변화 누락·문법 성분 오분류가 다시 나타났다.
- **E (`e227ed7`)**: 지시를 계속 추가하는 대신 중복을 줄여 `비교 기준 → 설명 구성 → 정확성과 어조`로 정리했다. 날짜·숫자·조건·부정·확정·관계 비교, 오탈자와 띄어쓰기 구분, 실제 인용, 부드러운 유지 안내, 임의의 근거·정당화 금지 원칙을 보존했다.
- 제품 변경은 설명 프롬프트뿐이다. 교정 생성 지침·제공자 설정·인용 검사·UI는 바꾸지 않았다. API·평가 도구도 C와 같다. 인용 검사 한계를 피하려고 응답을 후처리하거나 검사 조건을 완화하지 않았다.
- 제공자·모델: Gemini `gemini-3.5-flash-lite`. 개발자 작성 고정 원문·후보만 사용했다. 새 교정 후보 생성·기업 데이터 전송·모델 전환·자동 재시도는 없다.

각 버전·사례당 한 번, D 12회와 E 12회로 이번 추가 호출은 **24회**다. #22 누적 45회, #20의 기준선까지 포함하면 51회다. 실패 결과를 포함해 6개 JSON에 입력·후보 ID·실행 ID·출처·필수 요소·실제 설명·API 결과·프롬프트·해시·커밋·시각을 보존했다. API 반환과 차단 전 어댑터 출력을 구분한다.

[S 입력](../../tests/fixtures/explanation-accuracy-extra.json)은 D 실행 전에 작성했다. S-01은 오탈자+띄어쓰기, S-02는 띄어쓰기만, S-03은 단순 수정 후보와 의미가 달라진 후보의 독립 비교다. S는 D에서는 새 사례였지만 E에서는 이미 관찰한 사례다. 독립적인 일반화 시험이나 반복 안정성 시험으로 보지 않는다. 모든 실행에서 E-06은 제외하고 E-05 고정 안내는 모델 평가에서 제외한다.

## 실제 응답과 남은 문제

### E-01: 이전 오타 인용이 이번에는 나오지 않음

최종 E:

> 보내 주세여를 보내 주세요로 고쳐서 맞춤법을 바르게 수정했습니다.

C에서 후보에 없는 `주주세요.`를 만들었던 오류는 D·E에서 관찰되지 않았다. 두 번의 결과로 앞으로 발생하지 않는다고 보장하지 않는다.

### E-03: D의 인원 변화 누락을 E에서 설명

D는 현재 후보의 10명을 언급했으나 **원문의 8명에서 바뀌었다는 비교를 생략**했다. E는 다음과 같이 설명했다.

> 담당자의 확인 조건이 사라지고 인원이 8명에서 10명으로 바뀌었으며, 발송 예정이 확정 발송으로 변경되었습니다. 원래 뜻을 전달하려면 담당자의 확인 조건과 화요일까지 8명에게 보낼 예정이라는 점, 그리고 발송이 확정되지 않았음을 유지하는 편이 좋습니다.

### E-04: 분류 오류는 안 나왔지만 남은 단어 문제 누락

E의 p2 설명:

> 결재하지 않앗습니다를 결재하지 않았습니다로 수정하여 맞춤법을 맞추었습니다.

C의 ‘띄어쓰기만’이라는 잘못된 설명은 없어졌다. 그러나 등록비 지불 문맥에서 `결재`가 그대로 남았다는 문제를 알려주지 않는다. p1·p2 모두 `8명중 → 8명 중` 수정도 따로 설명하지 않았다. API 성공을 내용 완전성으로 간주하지 않는다. D에서는 대안 표현 `결제하지`를 인용해 p1·p2가 함께 차단됐으며 이 기록도 보존한다.

### S-03: 원문의 오타를 고친 표현을 원문처럼 인용

원문은 `승인되면 5명에게 안내할수 잇습니다.`이고 c2 후보는 `5명에게 안내합니다.`다. E의 c2 설명:

> '승인되면'이라는 조건과 '수 있습니다'라는 가능성을 삭제하고 5명에게 안내한다고 단정적으로 바꾸었습니다. 원래 뜻을 전달하려면 승인 조건과 안내할 수 있다는 가능성을 유지하는 편이 좋습니다.

의미 변화 설명은 맞지만 `수 있습니다`는 원문·c2 어디에도 없다. 원문의 실제 문자열은 `수 잇습니다`다. 정확한 인용 기준을 어겨 **502 `EXPLANATION_QUOTE_MISMATCH`로 c1·c2 설명이 함께 차단**됐다. 따옴표만 없애서 검사를 통과시키는 방식으로 해결하지 않는다.

D의 같은 c2는 새 교정 문장 전체를 제안해 차단됐고, 가능성에서 확정으로 바뀐 점도 충분히 설명하지 않았다. D와 E의 차단 이유는 다르다.

### G-02: 확정 여부 변화 누락

E는 날짜·수량·재고 조건 변화를 설명했지만 `발송할 수 있습니다 → 발송합니다`의 가능성·확정 변화는 설명하지 않았다. 이 부분은 D·C에서는 설명했다. 한 영역의 개선이 다른 영역의 품질을 보장하지 않음을 보여주는 관찰이다. 또한 ‘발송 가능한 날짜’라는 요약보다 기한이라는 표현이 더 정확하다.

E 출력에는 외부 출처·사용자 의도 발명이 관찰되지 않았다. 사실이 맞더라도 필수 변화나 선택 정보가 빠지면 보완으로 두었다. E에서 적용 금지·회피 명령은 관찰되지 않았으며 모두 1~2문장이었다. 읽기 편의는 사람에게 검증하지 않았다.

후보 품질은 별개다. E-02·03·07, G-01·02, S-03 c2는 일부러 의미가 달라지는 후보를 준비했고, E-04 p2는 용례상 문제가 남은 후보다. 나머지는 단순 수정 또는 동일 후보이며 이 시험에서 새 교정 모델의 성능을 평가하지 않았다.

## 집계·검증과 다음 판단

| 항목 | D | E | 정의 |
|---|---|---|---|
| API 성공 | 10/12 요청 | 11/12 요청 | E-04·S-03 차단 → S-03 차단. 화면 표시율 아님 |
| 모델 설명 API 반환 | 9/13 후보 | 11/13 후보 | 동일 후보 고정 안내 1/1은 각각 별도 |
| 기존 E 중요 변화 | 6/7 | 7/7 | E-02 1개 + E-03 3개 + E-07 3개 |
| G 중요 변화 | 7/7 | 6/7 | G-01 3개 + G-02 4개 |
| S 중요 변화 | 1/2 | 2/2 | S-03 c2의 조건·가능성 변화. 인용 오류와 별개 |
| 사용자 효과 | 미측정 | 미측정 | 실제 이해·선택 도움·위험 감소 실험 없음 |

- D·E의 타입 검사와 최종 단위/API 테스트 **42개 통과**. E 정리 중 두 제공자 테스트가 기존 지침의 ‘정당화하지 않는다’ 문구를 확인하다 실패했다. 해당 원칙을 명시적으로 복원한 뒤 42개가 통과했다. 테스트를 삭제하거나 완화하지 않았다.
- 새 S fixture는 실제 호출 전 dry run으로 형식을 확인했다. UI 변경이 없어 로컬 브라우저 검사를 반복하지 않았다. CI는 해당 커밋의 PR Checks에서 별도 확인한다.
- 각 실행 입력과 fixture의 동일성, 실제 응답·프롬프트·실행 커밋의 대응, 교정 생성 지침·검사·평가 도구 미변경을 대조했다. 변경 문서 7개의 내부 링크·앵커 141개와 `git diff --check`도 통과했다.
- 이번 추가 비교는 D·E 두 버전으로 마쳤다. 잘 나온 응답만 선택하거나 이후 성공할 때까지 반복하지 않았다. 작은 고정 표본이며 통계적 개선이나 일반화 성능을 주장하지 않는다.
- 완료 기준의 사실 일치·필수 정보 충족이 남아 **PR #23은 초안·Issue #22는 미완료**다. 다음에는 긴 지침을 더 붙이기보다 실제 변경 구간을 코드로 추출해 설명에 전달하는 방법, 인용과 의미 점검의 분리 등을 검토할 수 있다. 이는 이번에 구현한 기능이 아니며 별도 범위를 정해야 한다.
