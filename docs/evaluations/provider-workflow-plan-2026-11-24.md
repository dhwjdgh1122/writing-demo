# 최신 서비스의 Gemini·엘리스 제한 비교 계획

2026-11-24 / [#9](https://github.com/dhwjdgh1122/writing-demo/issues/9). 시작 기준 main `6ca0f52`. 사용자가 승인한 순서는 #9 비교 → #59 재시도 점검 → #7 같은 내용 붙여넣기 점검이며, 확인한 변경과 기록을 제출용 main에 반영한다. 배포 여부는 이번 작업에서 결정하지 않는다.

## 목적과 비교 조건

현재 웹 기능으로 두 제공자를 실제 사용하고 관찰한 결과를 발표 근거로 남긴다. 현재 제품의 제공자별 설정을 그대로 사용하므로 모델 자체만의 우열을 판정하는 통제 실험이 아니다. Gemini와 엘리스는 출력 상한 등 제공자 설정이 다르며 실제 값은 요청 기록에 보존한다. 과거 #22의 종료한 장시간 목표·무제한 호출·미병합 Draft를 재개하지 않는다.

- 같은 제품 코드·빌드·입력·조작 순서·브라우저 크기를 사용한다. 제공자마다 새 브라우저 저장 공간에서 시작한다.
- 실제 `.env`의 기본 제공자를 변경하지 않고 독립 로컬 서버에 해당 제공자를 연결한다. 키·인증 헤더·키가 포함될 수 있는 URL은 기록하지 않는다.
- 교정 출력의 차이를 관찰하는 웹 흐름과, 동일 원문·동일 후보에 대한 설명 비교를 분리한다.
- 실제 모델 호출은 제공자별 정상 경로 7회 예상, 안전 상한 8회(두 제공자 합계 최대 16회)다. 자동·수동 재시도나 대체 제공자 호출은 하지 않는다. 성공을 얻기 위한 반복 시험을 하지 않는다.
- 설정·인증·사용량 제한·통신·시간 초과·일시 서비스 실패는 해당 제공자의 후속 호출을 중단하고 미실행으로 기록한다. 응답 형식·후보별 설명 오류는 실제 실패로 보존하며 유효한 후보로 할 수 있는 독립 화면 동작만 이어간다.

## 웹 흐름 사례

앞뒤에는 교정 대상이 아닌 문장을 두고 아래 부분만 선택한다.

```text
안녕 하세요. 다음주 목요일 오후 3시에 팀 회의를 진행할 예정 입니다.
참석 가능하신 분들은 수요일 까지 댓글로 알려 주시기바랍니다.
회의 자료는 미리 읽어보시고, 궁금한점은 따로 적어 주세요.
참석이 어려우신 분들에게는 회의가 끝난뒤 내용을 공유 하겠습니다.
```

1. 교정 실행으로 후보 3개를 받고 원문 비교를 연다.
2. 교정 이유를 요청한다. 후보별 유효·오류, 구간별 이유 유무를 따로 기록하고 제공된 표현별 이유의 클릭 연결을 확인한다.
3. 후보 3에서 `더 담백하게`를 선택해 재교정한다. 해당 후보 1개 교체, 다른 후보 보존, 열린 설명 자동 연결을 확인한다.
4. 현재 원문과 다른 후보를 적용하고 다른 후보로 전환한다. 주변 원문·후보 3개·비교·설명이 유지되는지 확인한다. 적용할 차이가 없으면 억지로 바꾸지 않고 미실행 사유를 기록한다.
5. 적용한 카드에서 `더 정중하게`로 재교정해 현재 적용 문장 기준 새 후보 3개와 열린 설명의 자동 연결을 확인한다. 새 후보를 적용하기 전까지 편집기 내용을 유지하는지 확인한다.

후보 내용은 목요일 오후 3시, 수요일까지 댓글, 자료 사전 읽기, 질문 따로 기록, 불참자에게 회의 종료 후 공유라는 정보를 대조한다. 의미 변화·남은 오류·중복 후보를 관찰하되 형식 통과와 구분한다. 이 체크리스트와 평가 정답은 모델 입력에 추가하지 않는다.

## 고정 후보 설명 사례

- 원문: `담당자의 확인을 받은 경우에만 화요일까지 8명에게 자료를 보낼 예정이며, 발송은 확정되지 않았습니다.`
- 후보: `화요일까지 10명에게 자료를 발송합니다.`

현재 `/api/explanations` 계약으로 동일한 원문·후보 1개를 두 제공자에 보낸다. 담당자 확인 조건의 삭제, 8명에서 10명으로 변경, 예정·미확정에서 단정 표현으로 바뀐 점을 설명하는지 대조한다. 날짜가 바뀌었다는 등 없는 변화, 인용 재작성, 변화의 영향·확인할 점 누락도 기록한다. 내용 평가는 AI 보조 검토이며 사람의 독립 평가나 사용자 효과 실험이 아니다.

## 기록·완료 범위

수동 실행기는 기본 dry-run이며 명시적 `--live`에서만 호출한다. 각 실행의 코드·핵심 파일 해시, 모델·요청 설정, 입력·원출력·종료 사유·토큰 사용량(제공된 경우), 앱 HTTP 응답과 후보별 설명 상태, 지연, 화면 관찰·캡처, 호출 전 예약 기록·실패·미실행을 보존한다. 실행된 실제 요청 수와 화면 동작 수를 구분한다. 기존 기록을 덮어쓰지 않는다.

이 제한 사례의 결과와 발표 가능한 주장·한계를 정리하면 이번 비교 범위를 마친다. 전체 모델 우열·일반 성공률·사용자 판단 개선·KPI 달성, #22 설명 품질 해결을 주장하지 않는다. #59·#7의 주입 응답/클립보드 시험은 별도 검증으로 기록한다.
