# 출처별 명제 제안의 제한 평가 준비

**후속 실행:** 이후 사용자의 실행 지시에 따라 계획 6요청 중 5회를 실행했다. Gemini 503 이후 1회는 미실행이며, 4개 형식 통과 중 2개 사례의 정보 보존 확인·2개 판단 유보를 [결과와 원자료](explanation-proposition-review-result-2026-11-22.md)에 남겼다. 아래 호출 0회·실행 전 표시는 준비 당시의 기록이다. 제품 적용·#22 품질 통과로 확대하지 않았다.

2026-11-22 / #22·Draft PR #55 / 실행 전 고정 계획. **이번 작업은 지침·실행기·평가 기준의 준비이며 실제 모델 호출은 0회다.** 아래 최대 6요청은 추후 실행 지시가 있을 때의 범위다. 제품 API·프롬프트·UI, 기존 진단·원출력·품질 기준은 변경하지 않는다.

## 확인할 질문과 과거 결과의 보존

[후속 설계](explanation-propositions-followup-design-2026-11-22.md)와 [오프라인 구현](explanation-proposition-review-offline-2026-11-22.md)을 바탕으로, **모델이 인용문 복사와 의미 중복 제거를 맡지 않고 출처별 명제를 제안할 때 각 입력의 중요한 정보와 조건을 보존하는가**를 확인한다. 같은 내용의 제안은 출처별로 남기고 의미 관계는 별도로 검토한다.

[이전 진단](explanation-propositions-result-2026-11-22.md)은 6요청 계획 중 5회 실행·4개 원출력·3개 구조/정확 인용 통과였다. CT-03은 두 모델 모두 같은 의미를 두 번 적었고, 엘리스 E-03은 주요 정보를 보존했지만 인용 어미를 다시 써 실패했다. Gemini EQ-03은 503, E-03은 미실행이었다. 이 실패와 미실행을 바꾸거나 새 계약으로 다시 통과시켜 성공 실적으로 계산하지 않는다.

이번에는 생성 과제와 출력 계약이 달라진다. quote가 없다는 사실을 인용 정확도 향상으로, 출처별 중복을 허용한 사실을 의미 중복 해결로, 형식 통과율의 차이를 설명 품질 개선율로 계산하지 않는다. 과거 고정 근거 ID·조건 추출·동등성 판단과의 연결과 한계는 [후속 설계의 선행 작업 표](explanation-propositions-followup-design-2026-11-22.md#2-기존-시도를-재사용하는-범위)를 따른다.

## 고정 입력·지침·출력 계약

- [기존 fixture](../../tests/fixtures/explanation-propositions-2026-11-22.json)의 CT-03·EQ-03·E-03 문장 쌍을 그대로 사용한다. fixture를 수정하거나 새로운 사용자 사례로 소개하지 않는다. 역순 대조는 기존 오프라인 검사의 범위이며 이번 실제 호출 계획에 추가하지 않는다.
- 모델 입력은 두 문장을 함께 담은 `texts: [{id: 't1', text}, {id: 't2', text}]`뿐이다. 사례 ID·원문/후보 역할·`required`·`expected`·출처 메타데이터·과거 출력·합성 검토 fixture·아래 판정표·검토 결합 키는 보내지 않는다.
- [진단 지침·스키마](../../scripts/lib/explanation-proposition-review-prompt.mjs)는 출처별 명제 제안만 요청한다. 정답 명제 예시나 사례별 정답을 지침에 넣지 않는다. 변화·동등성·함의·선택 기준·교정 이유·점수는 생성하지 않는다.
- 출력은 `propositions` 배열 1~8개, 각 항목의 고유 `id`(h1~h8)·`statement`(1~300 Unicode 문자)·`originId`(t1/t2)다. `quote`와 다른 필드는 받지 않는다. 동일 출처의 동일 문자열 중복은 거부하고, 출처가 다른 동일 문자열과 표현이 다른 제안은 보존한다.
- [새 계약 모듈](../../scripts/lib/explanation-proposition-review.mjs)이 출처 ID에 해당하는 현재 입력 전체를 `sourceContext`로 연결한다. 명제의 문장을 인용문으로 바꾸거나 원문을 정규화하지 않는다. 이 연결은 명제의 의미 지지를 증명하지 않는다.
- [실행기](../../scripts/evaluate-explanation-proposition-review.mjs)는 실험 ID `issue22-proposition-review-20261122`를 사용한다. 실제 지침·스키마·fixture·코드·입력의 해시는 dry-run과 추후 실행 기록으로 고정한다. 파일 내용이 달라지면 같은 설정의 반복으로 취급하지 않는다.

기존 fixture의 `required`에는 최종 설명 과제의 변화 분류·선택 기준도 포함되어 있다. 원문 기록은 보존하되 이번 명제 생성에서 그 출력을 요구하지 않는다. 선택 기준이 없다는 이유만으로 이번 생성 실패라고 하지 않으며, 이번 내용이 정확하다는 이유로 [#22 원래 품질 기준](issue22-original-gate-2026-11-22.md)의 선택 안내까지 충족했다고 하지 않는다.

준비 시 두 제공자의 dry-run에서 확인한 SHA-256은 다음과 같다. fixture·스키마는 객체 키를 정렬한 JSON 내용, 지침은 UTF-8 문자열 기준이다. 실제 실행 기록에는 파일 바이트 해시도 별도로 남긴다. 요청의 `sentInputSha256`은 입력 객체의 canonical JSON 해시이며, 검토 snapshot의 `inputSha256`은 계약에서 정한 texts 배열 직렬화 해시이므로 두 필드를 혼용하지 않는다.

| 대상 | SHA-256 |
|---|---|
| 기존 고정 fixture | `35bad461e5fef6686e8f342e7a8501b6d0cd73f59bc50112552b40ff1306c5dd` |
| 새 지침 | `3b711f2974c6f232429ec3b25d448aa2e0b1f309f5ce5ecc6bce2453f5074f98` |
| 새 응답 스키마 | `9857ed391a098caa90bfd7e6afe701d6b82b0dac1d339ffef45dab478c174398` |

## 원문 기준 정보 체크리스트

모델이 출력한 명제 개수 대신 **각 입력이 전달하는 정보**를 기준으로 보존·누락·과잉 진술·검토 필요를 기록한다. 하나의 명제에 여러 정보가 들어가도 되고 여러 명제로 나눠도 되지만, 조건·부정·예정의 적용 범위가 해당 행동에서 떨어져 의미가 강화되면 실패다. 특정 단어·명제 수·정해진 문장 형태만으로 정답을 판정하지 않는다.

| 사례·출처 | 보존해야 할 정보 | 금지할 과잉 해석·누락 |
|---|---|---|
| CT-03·t1 | 회원인 경우에만 자료를 받을 수 있다는 제한과 수령 가능성 | 비회원도 받음, 회원이면 반드시/이미 받음, 회원 자격 외에는 다른 요건이 전혀 없음으로 강화하지 않음 |
| CT-03·t2 | 회원만 자료를 받을 수 있다는 제한과 수령 가능성 | t1과 같은 뜻이라고 한쪽 제안만 남겨 다른 출처의 정보 검토를 생략하지 않음. 두 제안의 수나 표현 차이를 조건 변화로 해석하지 않음 |
| EQ-03·t1 | 승인을 받은 경우에만 공개한다는 명시적 제한 | 승인만 받으면 반드시 공개한다는 충분조건으로 강화하지 않음 |
| EQ-03·t2 | 승인을 받으면 공개한다는 조건부 진술 | 원문에만 있는 `만` 제한을 추가하지 않음. 실제 무승인 공개가 허용된다고 추론하지 않음 |
| E-03·t1 | 담당자 확인 전제, 화요일까지라는 기한, 8명, 자료 발송 예정, 별도로 명시된 발송 미확정 | 담당자가 이미 확인함·실제 발송 완료·무조건적 발송으로 바꾸지 않음. 기한을 담당자 확인과 같은 논리적 전제로 분류하지 않음 |
| E-03·t2 | 화요일까지라는 기한, 10명, 자료를 발송한다는 서술 | 실제 발송이 완료되었거나 현실에서 확정되었다는 증거로 해석하지 않음. t1의 확인 조건·8명·미확정을 t2로 옮기지 않음 |

E-03·t1은 다섯 정보, t2는 세 정보를 각각 추적한다. `예정`이 있다는 이유만으로 별도 `발송은 확정되지 않았습니다.`까지 자동 보존 처리하지 않는다. 반대로 뜻을 정확히 유지한 표현에 특정 낱말이 없다는 이유만으로 누락 처리하지 않는다. `sourceContext` 전체에 해당 표현이 남아 있어도 모델의 명제에 정보가 보존되었다는 뜻은 아니다. 애매한 경우 판단 근거와 불확실성을 남긴다.

## 내용·관계 검토와 지표

실행기의 JSON·계약 검사와 내용 검토를 분리한다. 코드의 `ok: true`·`semanticAssessment: not-performed`는 의미 합격이 아니다. 내용 검토는 원출력을 바꾸지 않고 별도 기록에 검토 주체가 사람인지 AI 보조인지 명시한다. 다른 모델을 자동 판단자로 추가하지 않는다.

| 확인 단위 | 기록할 내용 |
|---|---|
| 요청 | 계획·실제 호출·서비스 실패·미실행을 분리. 원출력 미확보는 내용 오류나 성공으로 세지 않음 |
| 원출력 | JSON 파싱·새 계약 통과/실패와 실패 이유. 형식 실패 원문도 보존하고 사람이 수정해 성공으로 대체하지 않음 |
| 각 명제 | 자기 출처의 지지됨/지지되지 않음/불확실/미검토와 이유. 유효한 출처 ID만으로 지지됨 판정 금지 |
| 각 입력의 정보 | 위 체크리스트의 보존·누락·과잉 진술·검토 필요. 생성 명제 목록에 없는 정보도 검토 대상에 포함 |
| 명제 사이 관계 | 같은 의미/다른 의미/불확실/미검토와 근거. 다른 의미는 반드시 모순된다는 뜻이 아님 |
| 중복 부담 | 같은 의미의 제안이 얼마나 남는지, 8항목 한도나 검토 부담에 어떤 영향을 주는지. 출처별 보존 허용을 자동 중복 해결로 표현하지 않음 |

CT-03은 각 제안의 회원 제한·수령 가능성을 먼저 확인하고 같은 의미 관계를 검토한다. EQ-03은 명시적 제한과 조건부 진술의 차이를 지운 묶음을 만들지 않는다. E-03은 수량·조건·예정·미확정의 차이나 정보의 일부 포함을 동일 의미로 단순화하지 않는다.

묶음을 만들 경우 [오프라인 모듈](explanation-proposition-review-offline-2026-11-22.md)의 요청 결합 키·활성 검토 버전·전 구성원 지지·모든 쌍의 같은 의미 조건을 그대로 적용한다. 기존 합성 fixture의 h1/h2 판정을 새 응답의 같은 ID에 복사하지 않는다. 검토 미완료·철회·불확실 항목은 과거의 긍정 판정으로 대체하지 않는다. 검토된 묶음도 코드가 의미를 자동 판단했다는 결과는 아니다.

한 번의 중요한 의미 왜곡·정보 누락도 해당 사례의 내용 충족으로 세지 않는다. 일부가 정확한 출력은 보존된 정보와 남은 오류를 나누어 기록한다. 서비스·형식·내용을 하나의 성공률로 합치거나 일부 성공으로 다른 제공자의 미실행을 상쇄하지 않는다.

## 실행량·기록·중단 조건

추후 실행 범위는 **CT-03 → EQ-03 → E-03, 3사례 × 두 제공자 × 사례당 1회 = 최대 6요청**이다. Gemini `gemini-3.5-flash-lite`와 엘리스 `gpt-4o-mini`의 기존 설정을 유지한다. 모델 선택·토큰·추론 설정을 성과에 맞춰 중간에 바꾸지 않는다. 제품 API·브라우저를 거치지 않는 별도 진단이며 후보 생성이나 최종 교정 이유의 시험이 아니다.

- 요청 직전에 기존 후속 장부에 예약하고 요청 식별자·모델·실제 입력·지침·스키마·해시·원출력·원응답 해시·출처 snapshot·검사 결과·지연·토큰을 남긴다. 파싱/계약 실패에는 성공 snapshot을 만들지 않는다. 키·인증 헤더와 불필요한 제공자 응답 봉투는 저장하지 않는다.
- 원자료 파일명은 `explanation-proposition-review-2026-11-22-{provider}.json`이다. 기존 진단 결과 파일과 구분하며, 이미 생성된 결과를 덮어쓰거나 실패를 지워 다시 실행하지 않는다.
- 서비스·쿼터·설정/요청 거절·시간 초과·원출력 미확보가 발생하면 해당 제공자의 남은 사례를 중단한다. 실패·결과 불명 요청도 기록하며 자동 재시도·모델 전환은 없다. 다른 제공자는 그 제공자의 사전 고정 사례만 실행할 수 있고 실패 요청의 대체로 계산하지 않는다.
- 원출력을 확보했으나 JSON·새 계약 검사가 실패한 경우에는 실패를 기록하고 남은 고정 사례를 진행한다. 응답을 자동 수정하거나 같은 사례를 다시 요청하지 않는다. 내용 검토 실패가 발견되어도 실행 중 지침·체크리스트·정답 기준을 바꾸지 않는다.
- 준비 단계의 실제 추가 호출은 **0회**다. 기존 후속 장부 **88회**, 이전 19회와 연결한 **107회**를 보존한다. 이 문서의 최대 6회는 새 진단의 크기이며 현재 실행 승인이나 장시간 목표 재개가 아니다.

```powershell
# 입력·지침·스키마 확인만 수행. 실제 모델 호출 없음.
node scripts/evaluate-explanation-proposition-review.mjs --provider=elice
node scripts/evaluate-explanation-proposition-review.mjs --provider=gemini

# 추후 별도 실행 지시가 있을 때만 사용. 이번 준비 작업에서는 실행하지 않는다.
node scripts/evaluate-explanation-proposition-review.mjs --provider=elice --live --confirm-authorized
node scripts/evaluate-explanation-proposition-review.mjs --provider=gemini --live --confirm-authorized
```

## 다음 단계로 넘어갈 조건과 결론의 한계

각 제공자의 세 사례에서 새 계약과 양쪽 입력의 중요 정보 보존을 함께 확인하고, 잘못된 출처 지지·과잉 진술·누락이 없어야 그 제공자의 결과를 바탕으로 다음 설계를 검토할 수 있다. 원출력 미확보나 불확실 판정은 통과가 아니다. 일부 제공자만 충족해도 양 모델 기준을 충족했다고 하지 않는다.

성공적인 목록이 있어도 후속 함의 판단·최종 설명 생성·제품 연결을 자동 시작하지 않는다. 필요한 관계 검토와 남은 누락을 먼저 확인하고, 새 호출이나 단계가 필요하면 목적·입력·판정·실행량을 별도 확정한다. 정보 보존이 부족하거나 새 오류가 있으면 현재 구성을 확대하지 않고 실패 근거와 다음 가설을 먼저 정리한다. 표본을 늘리거나 성공할 때까지 같은 배치를 반복하지 않는다.

이것은 알려진 세 문장 쌍의 단회 진단이다. 역방향 안정성·일반 정확도·모델 우열·실제 사용자의 판단 도움을 입증하지 않는다. Gemini의 과거 서비스 실패·미실행에는 비교할 내용이 없고, 엘리스의 기존 출력도 다른 생성 계약이므로 단순 전후 개선율로 비교할 수 없다. [기존 14사례·15후보·두 모델·3회 품질 기준](issue22-original-gate-2026-11-22.md)은 유지하며 #22 완료·main 반영과 구분한다.
