# 명제의 의미 중복·인용 재작성 후속 설계

**후속 상태:** 아래는 설계 시점의 기록이다. 이후 [오프라인 계약 구현·검증](explanation-proposition-review-offline-2026-11-22.md)과 [제한 평가 계획·실행기 준비](explanation-proposition-review-plan-2026-11-22.md)를 진행했다. 아래의 ‘미구현’·‘다음 구현’ 표현은 당시 범위로 보존하며 최신 구현·검증 결과는 후속 기록을 따른다. 실제 모델 추가 호출·제품 적용·#22 품질 통과는 수행하지 않았다.

2026-11-22 / #22·Draft PR #55 / 설계 기준 `abe8092`. **설계 문서이며 새 계약·파서·실행기는 아직 구현하지 않았다. 실제 모델 호출은 0회다.** 기존 제품 API·프롬프트·인용 검사와 [#22 원래 품질 기준](issue22-original-gate-2026-11-22.md)은 유지한다.

## 1. 해결하려는 문제와 이번 결정

[직전 진단](explanation-propositions-result-2026-11-22.md)에서 두 모델은 CT-03의 회원 제한을 보존했지만 같은 뜻을 두 명제로 작성했다. 엘리스 E-03은 중요한 정보를 보존했으나 인용의 `예정이며,`를 `예정이다.`로 바꿔 출처 검사에 실패했다. 두 문제를 조건 누락이나 설명 내용 전체의 실패로 묶지 않는다.

예를 들어 `회원인 경우에만 자료를 받을 수 있습니다.`와 `회원만 자료를 받을 수 있습니다.`를 두 항목으로 적었다고 해서 조건이 달라졌다고 설명하면 안 된다. 반대로 `승인을 받은 경우에만`과 `승인을 받으면`은 비슷하게 보여도 명시적 제한의 차이를 지우면 안 된다.

**선택한 방향은 명제 제안·출처 연결·의미 관계 검토를 분리하는 것이다.** 모델이 인용문을 다시 쓰는 작업은 제외하고 코드가 해당 입력 전체를 그대로 연결한다. 명제끼리 같은 뜻인지 여부는 별도 검토 기록으로 남기며, 확실하지 않으면 합치지 않는다. 중복 없는 명제 생성에서 출처별 제안·관계 검토로 진단 과제를 바꾸는 설계이지, 기존 중복 실패를 성공으로 바꾸는 처리가 아니다.

이번 설계의 완료 범위는 아래 계약·예외·검증 기준과 다음 오프라인 구현 범위를 정하는 데까지다. 자동 의미 중복 해결, 최종 교정 이유 생성, 제품 적용, 새 실제 모델 평가와 main 병합은 포함하지 않는다.

## 3. 제안 계약과 처리 순서

```text
현재 요청의 t1·t2 텍스트 스냅샷
  → 출처별 검토 명제 제안
  → 형식·ID 검사와 원문 문맥 연결
  → 명제별 원문 지지·누락 검토
  → 명제 사이 의미 관계 검토
  → 검토가 끝난 항목만 진단용 묶음으로 정리
```

마지막 두 검토는 이번 설계에서는 별도 기록이다. 자동 모델 판단기를 붙이거나 제품 설명을 생성하지 않는다. 미검토·불확실 항목이 남으면 다음 의미 판단 단계로 자동 전달하지 않는다.

### 입력과 명제 제안

- 기존 [fixture](../../tests/fixtures/explanation-propositions-2026-11-22.json)의 CT-03·EQ-03·E-03과 `propositionInput` 검사를 재사용한다. 입력은 `texts: [{id: 't1', text}, {id: 't2', text}]`이며 두 텍스트를 함께 제공한다. 각 입력 최대 2,000 Unicode 문자와 역할 없는 ID를 유지한다.
- 새로운 모델 출력 계약을 시험한다면 `propositions`에 `id`·`statement`·`originId`만 받는다. `quote`는 받지 않는다. 1~8항목, h1~h8의 고유 ID, statement 1~300자, originId는 t1/t2, 추가 필드 금지를 유지한다. 이 변경은 기존 계약과 다른 진단 버전으로 기록한다.
- `statement`는 지정한 출처 하나로 뒷받침되어야 한다. 조건·부정·가능성·예정·수량·기한을 떼어 확정 사실로 만들거나 양쪽 정보를 섞으면 안 된다. 양쪽이 같은 내용을 말해도 출처별 제안을 남길 수 있다.
- ID 중복과 **같은 originId·같은 statement 문자열**의 단순 중복은 형식 오류로 거부한다. 다른 출처의 같은 문자열, 같은 출처의 다른 표현은 보존하고 의미 검토 대상으로 둔다. 문자 정규화나 유사도로 자동 삭제하지 않는다.
- 사례 ID·정답·필수 정보 체크리스트·관계 판정·기존 출력은 모델 입력에서 제외한다. 기존 8항목 상한을 중복이 소모해 정보를 빠뜨릴 수 있으므로 누락 검토는 계속 필요하다. 상한을 조용히 늘리거나 넘친 항목을 잘라 통과시키지 않는다.

### 인용을 재작성하지 않는 출처 연결

코드는 `originId`로 **현재 요청에서 보관한 해당 텍스트 전체**를 찾아 `sourceContext`에 연결한다. 공백·줄바꿈·문자·어미를 정규화하지 않으며 명제에서 역으로 인용문을 만들지 않는다. E-03의 입력은 끝까지 보존되므로 별도 `발송은 확정되지 않았습니다.`도 문맥에서 사라지지 않는다.

`sourceContext`는 출처 문맥이며 최소 인용 구간이나 검증된 의미 근거가 아니다. 정상 t1 ID를 가진 잘못된 명제도 이 검사만으로 거부할 수 없고, 실제로 t1이 명제를 뒷받침하는지는 별도로 검토해야 한다. 모델이 원문 지정을 잘못했을 가능성도 남는다. 과거 출력의 잘못된 quote를 덮어써 성공으로 복구하지 않는다.

검토 결합 키는 로컬 `runId`·`requestId`·`contractVersion`(`proposition-review-v1`)·입력 해시·출력 해시다. 내용이 같아도 별도 요청의 검토를 자동 재사용하지 않는다. 입력 해시는 검사한 `texts`를 원래 배열 순서와 `{id, text}` 필드 순서로, 출력 해시는 검사한 `propositions`를 원래 배열 순서와 `{id, statement, originId}` 필드 순서로 `JSON.stringify`한 UTF-8 바이트의 SHA-256으로 계산한다. 문자열 정규화·항목 정렬은 하지 않는다. 원응답 바이트 해시는 별도로 보존하며, 파싱 실패 원응답에도 성공 출력 해시를 만들어 주지 않는다.

검토 기록의 결합 키가 현재 진단과 다르면 거부한다. 이것은 기록의 결합 검사이며, 유효한 ID로 제출된 명제 내용의 정확성을 증명하는 장치가 아니다. 이 메타데이터는 모델 입력에 넣지 않는다.

### 의미 관계와 묶음 검토

원래 명제·출처는 삭제하지 않는다. 아래 값은 별도 검토 기록이며 모델 생성 결과나 자동 정답이 아니다. 검토 주체가 사람인지 AI 보조인지, 근거와 대상 입력·응답 해시를 함께 남긴다.

| 검토 단위 | 값과 의미 |
|---|---|
| 명제 → 자기 출처 | 미검토 / 지지됨 / 지지되지 않음 / 불확실. 정확한 출처 연결과 별개 |
| 명제 ↔ 명제 | 미검토 / 같은 의미 / 다른 의미 / 불확실. ‘다른 의미’는 반드시 모순된다는 뜻이 아님 |
| 원문 기준 정보 | 보존 / 누락 / 과잉 진술 / 검토 필요와 근거. 모델이 만든 명제 수를 분모로 삼지 않음 |

CT-03은 양쪽 제한·가능성을 보존했는지 확인한 뒤 같은 의미의 묶음 후보로 검토한다. EQ-03의 명시적 제한과 조건부 진술, E-03의 8명/10명·예정·별도 미확정은 표현 유사성만으로 묶지 않는다. 한 명제가 다른 명제의 일부만 포함하는 경우도 불확실 또는 다른 의미로 남기며 짧은 항목에 맞춰 정보를 버리지 않는다.

진단용 묶음을 만들더라도 구성 명제의 자기 출처 지지가 검토되고 구성원 사이의 모든 관계가 같은 의미로 확인된 경우에만 허용한다. A=B, B=C만으로 미검토 A/C까지 자동 연결하지 않는다. 대표 ID는 원래 항목 중에서 고르고 구성원 ID·출처·원문은 모두 보존하며 새 대표 문장을 생성하지 않는다. 검토가 변경·취소되면 묶음도 무효화한다. 이 규칙을 코드가 지켜도 검토자의 판단 자체가 맞다는 보장은 없으며, 제품 적용이나 #22 품질 통과로 승격하지 않는다.

각 요청의 검토는 전체 판정표의 `reviewRevision`으로 보존하고 명시적으로 활성화한 버전 하나만 사용한다. 활성 버전이 둘이거나 같은 명제·관계에 상충하는 판정이 있으면 묶음을 보류한다. 최신 `불확실`·철회 상태를 과거의 긍정 판정으로 대신하지 않으며 변경 이력은 삭제하지 않는다. 묶음에도 사용한 검토 버전을 연결한다.

## 4. 다음 구현의 범위와 오프라인 확인표

다음 구현을 진행할 때는 제품과 기존 진단을 수정하지 않고 `scripts/lib/explanation-proposition-review.mjs`에 새 계약 검사·출처 연결·검토 기록 결합·묶음 안전 조건을 둔다. 기존 `propositionInput`은 재사용하고 기존 validator·지침·fixture·원자료는 그대로 둔다. 별도 테스트와 합성 검토 fixture에 아래 경우를 고정한다. 새 실제 호출용 실행기는 아직 만들지 않는다.

| 확인 항목 | 기대 결과 |
|---|---|
| 공백·빈 줄·CRLF·Unicode·반복 구절 | 입력 전체가 그대로 연결됨. 부분 구절을 임의로 찾거나 바꾸지 않음 |
| 없는 출처·ID 중복·추가 필드·빈 값·상한 초과 | 명시적 오류, 자동 보정·잘라내기·모델 재요청 없음 |
| 이전 요청의 검토 기록 재사용 | runId·requestId·계약 버전·입력/출력 해시 중 하나라도 다르면 결합 거부. 내용·t1/h1 이름이 같아도 자동 재사용하지 않음 |
| 정상 출처 ID + 잘못된 명제 | 형식 연결 성공과 의미 미검토를 분리. `qualityPassed` 등 자동 의미 합격값을 만들지 않음 |

| E-03의 복합 정보·별도 미확정 | 원문 체크리스트의 담당자 확인·기한·8명·예정·별도 미확정과 후보 10명·발송 서술을 유지. quote 필드 제거를 정보 보존 성공으로 대신하지 않음 |
| 일부 관계만 검토된 3개 명제, 검토 충돌·변경·철회 | 미검토 관계의 연쇄 병합, 복수 활성 검토 및 오래된 묶음 사용 거부 |
| 과거 실패 출력의 재사용 | 원출력·실패 판정·장부 불변. 별도 파생 예제는 ‘어댑터 시험용 변환’으로 표시하며 실제 모델 성공으로 세지 않음 |

위 테스트는 코드의 계약·보존·거부 동작을 확인한다. 수동 작성한 관계 정답을 읽어 처리하는 테스트로 모델이 같은 뜻을 잘 판단한다고 주장하지 않는다. 아직 이 모듈·시험은 작성하거나 실행하지 않았다.

## 5. 평가 기준과 중단 조건

| 구분 | 유지할 해석 |
|---|---|
| 과거 진단 | 계획 6회·실제 5회·확보 출력 4개·구조/정확 인용 통과 3개와 CT-03 중복 실패를 그대로 보존 |
| 새 출처 연결 | 모델 quote가 없으므로 ‘인용 정확도 100%로 개선’이라고 계산하지 않음. 코드의 입력 보존·출처 연결 무결성만 별도로 확인 |
| 새 명제 내용 | 원문 기준의 정보 보존·과잉 진술·조건 오류·의미 중복을 계속 검토. 생성 과제가 달라져 기존 합격률과 단순 전후 비교 불가 |
| 중복 처리 | 관계 검토를 미루거나 제안을 보존한 것은 자동 중복 해결이 아님. 중복이 누락·검토 부담에 미치는 영향도 기록 |
| #22 완료 | 기존 14사례·15후보×두 모델×3회=84앱 요청·90후보 계획과 고정 안내 제외 규칙을 유지. 실제 모델 호출 수는 실행 경로에 따라 별도로 기록한다. 실제 설명 품질·사용자 효과는 별도이며 이번 설계로 충족하지 않음 |

오프라인 구현에서 문맥이 변하거나, 미검토 항목이 묶이거나, 출처 연결을 의미 합격으로 표시하면 다음 단계로 넘어가지 않는다. 내용 검토에서 조건·부정·미확정 소실이나 잘못된 묶음이 발견돼도 해당 경로를 최종 설명에 연결하지 않는다. 표본 수를 늘리거나 기준을 낮춰 해결하지 않는다.

오프라인 검사가 통과하더라도 새 모델 호출을 자동 시작하지 않는다. 실제 실행을 검토할 때는 기존 인용 계약과 무엇을 비교할지, 과제 변경에 따른 지표, 고정 입력·출력 계약·모델·실행량·서비스 실패 중단 기준을 먼저 확정한다. 현재 설계에는 새 호출 배치나 무제한 재개가 포함되지 않는다. 모델이 정보 보존을 더 잘한다는 근거가 없으면 같은 구성을 반복하지 않는다.
