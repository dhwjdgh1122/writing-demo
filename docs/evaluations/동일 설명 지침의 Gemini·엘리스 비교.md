# 동일 설명 지침의 Gemini·엘리스 비교

관련 작업: [#22](https://github.com/dhwjdgh1122/writing-demo/issues/22), [PR #23](https://github.com/dhwjdgh1122/writing-demo/pull/23), [제공자 비교 계획 #9](https://github.com/dhwjdgh1122/writing-demo/issues/9).

**이번 사례에서는 엘리스로 바꾸는 것만으로 설명 문제가 해결되지 않았다.** 두 제공자 모두 정보 누락·어색한 조사가 남았고, 엘리스에는 서로 다른 전후 날짜·수량을 함께 유지하라는 모순된 안내도 있었다. 모델 가격·규모가 원인이라고 단정하거나 어느 모델이 전반적으로 우수하다고 결론 내리지 않는다. #22와 초안 PR은 미완료로 유지한다.

## 비교 조건과 범위

- 제공자에 따른 설명 품질 차이를 확인하기 위해 같은 조건으로 엘리스를 평가했다. 범위는 기본 E 6 + G 3 + S 3의 **12요청·14후보**다. 고정 후보의 설명 평가이며 새 교정 후보를 생성한 시험이 아니다. 모두 개발자가 작성한 합성 사례이며 기업 데이터는 사용하지 않았다.
- Gemini 비교 자료는 [인용 분리 G](인용%20분리와%20선택%20안내%20평가.md)의 2026-11-16 22:23~22:24 KST 실행이다. 이번에 Gemini를 재호출하지 않았다. 엘리스 실행은 같은 날 22:35~22:36 KST다.
- Gemini는 `gemini-3.5-flash-lite`, 엘리스는 현재 설정된 `gpt-4o-mini`다. 엘리스 실행 코드 커밋은 `f0cf879`, Gemini G는 `4c77f44`다. 그 사이 변경은 문서·실행 기록뿐이며 프롬프트·입력·출력 처리 코드는 같다.
- 같은 원문·후보·프롬프트·서버 파생 변경 구간·출력 검사·평가 기준을 사용했다. 세 묶음의 fixture·프롬프트·출력 계약·실행 도구 해시와 실제 파생 입력을 대조했다. 제공자별 요청 방식은 동일하지 않다: Gemini는 JSON Schema 응답·최대 8,192토큰·LOW thinking, 엘리스는 JSON object 응답·최대 2,000토큰이다. 별도의 temperature 설정은 보내지 않았다. **현재 앱의 두 제공자 연결 경로 비교이며 모델 자체만 분리한 통제 실험은 아니다.**
- `.env`를 수정하지 않고 평가 프로세스의 `LLM_PROVIDER=elice`만 지정했다. 실행 전후 `.env` 해시가 같음을 확인했다. 기존 앱 기본 제공자 설정은 바꾸지 않았다. 기존 키·URL 설정을 사용했으며 키·인증 헤더·원시 응답 봉투는 결과에 저장하지 않았다.
- 사례당 한 번만 호출했다. 오류를 재시도하거나 다른 모델로 대체하지 않았다. R 4사례는 Gemini와 양쪽 결과가 없어 이번 12사례 비교 범위에서 제외했다. #9의 전체 모델 비교·후보 품질 평가를 완료한 것으로 처리하지 않는다.

## 응답 제공과 오류 — 내용 품질 점수와 별개

| 항목 | Gemini G | 엘리스 |
|---|---|---|
| 앱 API 성공 요청 | 10/12 | 9/12 |
| 형식·참조 등 유효성 실패 502 | S-01, 1요청 | E-07·G-01·S-03, 3요청 |
| 모델 서비스 오류 503 | S-03, 1요청 | 없음 |
| 반환된 모델 설명 / 대상 후보 | 10/13 | 9/13 |
| 원문 동일 후보의 코드 고정 안내 | 1/1, 별도 집계 | 1/1, 별도 집계 |
| 양쪽 모두 반환돼 내용을 비교할 수 있는 모델 설명 | 8개 | 동일한 8개 |

502는 `MODEL_RESPONSE_INVALID`이며 유효한 설명을 반환하지 못했다는 뜻이다. 검증 전 모델 구조 응답을 보존하지 않아 구체적으로 어느 항목이 거부됐는지는 알 수 없다. 인용 오류나 토큰 부족 때문이라고 추정해 확정하지 않는다. 503은 서비스 가용성 문제로 내용 품질 점수에 포함하지 않는다. 미제공 사례를 숨기거나 양쪽의 다른 분모로 정확도를 비교하지 않는다.

| S-03 두 후보 | 서비스 오류로 미제공 | 유효성 오류로 미제공. 어느 쪽도 내용 평가 불가 |

### 엘리스의 대표 실제 응답

E-03:

> ‘8명’이 ‘10명’으로 바뀌어 발송 인원이 변경되었습니다. 원래 인원인 ‘8명’을 유지하면 뜻이 명확합니다.

인원 변화는 맞지만 담당자 확인 조건과 미확정 상태가 빠진 것은 설명하지 않았다. 같은 원문·후보에 대한 Gemini G는 이 두 변화도 설명했다. 이 한 사례로 전체 모델 성능의 우열을 확정하지 않는다.

G-02:

> ‘12월 3일까지 4개를 발송할 수 있습니다.’이 ‘12월 5일까지 6개를 발송합니다.’으로 바뀌어 날짜와 발송 수량이 변경되었습니다. 원래 뜻을 전달하려면 ‘12월 3일까지 4개를 발송할 수 있습니다.’과 ‘12월 5일까지 6개를 발송합니다.’을 유지하는 편이 좋습니다.

각 인용은 입력에 실제 존재하므로 출처 검사를 통과했지만, 서로 다른 두 날짜·수량을 함께 유지하라는 안내는 원래 뜻을 보존하는 선택 기준이 될 수 없다. **정확한 인용과 타당한 설명은 별개의 문제**임을 보여준다.

## 판단과 다음 확인 대상

- 이번 관찰에서는 모델 교체만으로 완료 기준이 충족되지 않았다. 엘리스가 E-02의 구체성 감소를 더 명시한 사례는 있지만 E-03·G-02에서는 필수 변화 누락이 더 많았다. 일괄적인 개선으로 볼 수 없다.
- 양쪽 모두 어색한 조사를 생성했다. `{{0}}` 같은 참조를 읽기 쉬운 문장에 연결하는 현재 출력 방식이 영향을 줄 가능성은 있으나, 원인 분리 실험은 하지 않았다. 모델 가격·규모가 원인이라는 근거도 없다.
- 다음 보완 후보는 의미 변화별 원래 정보와 유지 안내의 연결, 직접 만든 참조 앞뒤 문장의 자연스러움, 형식 거부 원인의 안전한 분류다. 아직 구현한 내용이 아니다. 단순히 인용 검사를 느슨하게 하거나 설명을 모두 차단해 품질 문제를 해결했다고 보지 않는다.
- 이번에는 코드·프롬프트·검사·기본 모델을 변경하지 않았다. 코드 검사를 불필요하게 반복하지 않고 비교 자료·문서 링크·설정 보존을 검증한다. 기존 G 코드의 자동 테스트 통과와 이번 실제 모델 결과는 별개다.
- 검증 결과: 세 묶음의 실제 입력·파생 입력·프롬프트·실행 도구·출력 계약 해시 일치, 두 커밋의 제공자/설명 코드 일치, 양쪽 제공 모델 설명 8개 대응 확인. 문서 5개의 내부 링크·앵커 128개와 `git diff --check`를 통과했다. 실행 자료에서 알려진 키·토큰 형식도 검사했으며 원시 인증값은 읽어 출력하지 않았다.
- #22는 이번 12회까지 누적 82회 호출이며, #20 6회는 별도다. 비용·크레딧 잔액·성능 전체·실제 사용자 도움은 측정하지 않았다. PR #23은 초안이며 main에는 병합하지 않는다.
