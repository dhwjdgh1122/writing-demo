## G 구현 범위와 확인 기준

코드 `4c77f44`에서 설명 모델의 내부 응답을 아래처럼 변경했다. 공개 API·화면·교정 후보 생성·모델 설정·기존 HTTP 인용 검사는 유지한다.

- `references`: 원문(`source`) 또는 해당 후보(`candidate`)에서 복사한 짧은 표현. 코드가 선언된 쪽에 실제 존재하는지 정확히 검사한다. 공백·오타를 정규화하지 않는다. 다른 후보에서만 찾을 수 있는 표현은 거부한다.
- `changeSummary`: 실제 변경과 영향을 설명하는 문장. `{{0}}`처럼 참조 번호를 사용하며 코드가 검증한 표현을 따옴표와 함께 삽입한다.
- `guidance`: 의미가 바뀌면 원래 유지할 구체적인 정보를 안내하고, 단순 수정이면 빈 문자열을 사용하도록 지시한다. 두 문장은 서버에서 합쳐 기존 `{candidateId, explanation}`으로 반환한다.
- 구조 검사에서 없는 번호·잘못된 참조 문법·미사용 참조·직접 작성한 따옴표·ID 누락/중복·최종 400자 초과를 거부한다. 동일 후보는 기존 고정 문구를 유지한다. 형식/참조 오류는 502 `MODEL_RESPONSE_INVALID`로 안내하며 자동 재시도나 모델 전환은 하지 않는다.
- **인용 출처 확인은 의미의 정확성 검사가 아니다.** 일반 서술에 없는 사실을 적거나, 참조를 문법적으로 반대로 연결하거나, 중요한 정보를 빠뜨리는 문제는 여전히 생길 수 있다. 의미 변화가 있을 때 guidance를 채우는 것과 1~2문장 목표도 모델 지침이며 코드가 의미를 판단해 강제하는 조건은 아니다.
- 두 제공자에 같은 파서를 적용했다. 엘리스는 모의 응답 연결 검사만 수행했고 실제 출력 품질은 미확인이다. 구조화 필드가 늘어 출력량이 증가할 수 있으며 비용·지연 비교는 하지 않았다.
- 이전 `evaluate-explanations.mjs`는 과거 자유 서술 프롬프트와 현재 형식이 호환되지 않아 호출 전에 안내하고 종료하도록 바꿨다. 과거 기록은 보존한다. 현재 도구 `evaluate-explanation-criteria.mjs`는 새 출력 처리 코드의 해시도 저장한다. 어댑터 검증 전 원시 구조 응답은 저장하지 않으므로 형식 오류의 세부 원인을 이 기록만으로 확정할 수 없다.

## 자동 검증과 남은 작업

- 타입 검사·단위/API 테스트 **55개**, 빌드, 로컬 **Edge 브라우저 20개 통과**. 실제 AI 품질을 보증하는 검사가 아니다.
- 변경 문서 8개의 내부 링크·앵커 151개, 새 실행 자료 6개의 코드 커밋·프롬프트 해시 대조, `git diff --check`를 확인했다. 6개 자료의 실제 요청 수는 F 재개 7 + G 12 = 19회다.
- 새 테스트는 인용 출처·후보 독립성, 원문 오타 정규화 거부, 없는 표현/참조, 최종 확장 길이·유니코드·문자 그대로 삽입, 두 제공자 및 HTTP 응답 계약을 확인한다. 의미 오류를 통과시킬 수 있다는 검사 한계도 테스트에 남겼다.
- 샌드박스의 Node 접근 오류 때문에 동일 명령을 정상 실행 권한에서 수행했다. 빌드의 기존 의존성 주석 경고는 빌드 실패가 아니다.
- 완료 전 남은 항목: 의미 변화와 유지 안내의 빠짐없는 연결, 미수정 용례 문제 설명, 일상적이고 자연스러운 조사 표현, S-01 실패 원인 확인, S-03과 R 미실행/실패 사례의 별도 재개. 새로운 시도는 현재 실패 기록을 대체하지 않는다.
- 현재 범위의 인용 파서만으로 의미 누락 문제까지 해결됐다고 볼 수 없다. 다음 보완에서는 단순 프롬프트 추가 전에 **의미 변화별 원래 정보와 유지 안내를 연결하는 출력 구조**와 **형식 거부 원인을 안전하게 구분하는 평가 기록**을 검토한다. 이번에 구현 완료한 기능으로 기록하지 않는다.
