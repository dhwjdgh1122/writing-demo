# 제품 기획 — 웹 데모

> 역할: 제품 목적·사용자·범위·검증 목표를 정의한다. 2026-11-06 검토한 기준안과 현재 구현 범위를 정리한다. 개인 검토·구현과 팀 전체 합의·사용자 효과 검증은 구분한다. 작업 관리 방법과 최신 상태의 확인 위치는 [TASKS](TASKS.md)에서 안내한다.

## 1. 목적과 결정된 방향

센틴스파이 데스크톱 앱의 화면과 사용 흐름을 참고해 웹사이트(웹 데모)로 구현했다. 웹페이지 안에서 기본 교정 흐름과 필요할 때 교정 이유를 확인하는 기능을 제공한다. 2026-11-11 중간발표 이후 선택·비교 흐름과 줄바꿈 보존 지침을 보완하고 제한된 사례로 검증했다. 현재 교정 진입은 드래그 후 근처 버튼 또는 상단 실행 버튼을 누르면 확인창 없이 바로 요청하는 방식이다([#64](https://github.com/dhwjdgh1122/writing-demo/issues/64)). 현재 구현은 [기능명세](FEATURE_SPEC.md), 수행 결과와 미검증 범위는 [검증 기록](검증%20기록.md)을 따른다. 이를 전체 품질이나 사용자 효과 검증 완료로 보지 않는다.

사용자는 페이지 안에서 원문 일부를 선택하고 교정 후보를 받는다. 변경 부분을 확인해 후보를 적용할 수 있으며, 궁금할 때만 ‘교정 이유’ 버튼을 눌러 원문과 후보의 변화 및 의미에 미치는 영향에 대한 AI 설명을 확인한다.

### 이미 선택한 기준

- 실행 환경은 웹사이트이며, 교정 패널의 화면 기준은 센틴스파이 데스크톱 앱이다.
- 페이지 안에 원문 입력·선택 공간을 마련한다. 외부 앱의 문서를 가져오거나 OS 전역 단축키로 호출하는 기능은 첫 웹 데모에 포함하지 않는다.
- 센틴스파이의 화면과 사용 흐름을 참고한 독립 웹 데모로 구현한다. 코드와 AI 연결은 프로젝트 설계에 맞춰 작성한다.
- 기본 교정 흐름을 먼저 구현한 뒤 설명 기능을 추가했다. 후속 작업은 이 흐름을 유지하며 진행한다.
- 개인 시제품을 바탕으로 후속 작업을 나눈다. 담당·범위·일정의 관리 방법은 [작업 목록](TASKS.md)을 따른다.

오정호가 검토한 아래 범위안을 후속 설계의 기준으로 사용한다. 명시적으로 미정인 기술·모델·평가 세부 조건까지 확정된 것은 아니다. 이후 변경은 해당 설계 문서에 반영한다.

## 2. 사용자와 문제 가설

- 기능은 누구나 이용할 수 있으며, 라이트·헤비 사용자 구분에 따라 설명 접근을 제한하지 않는다.
- 문제 가설: 변경 위치를 색으로 확인하더라도, 후보가 원래 의도를 유지하는지와 표현 변화의 의미를 판단하기 어려울 수 있다.
- 설명 효과를 우선 살펴볼 사용자 상황: 후보의 표현 차이나 의미 변화를 확인하고 자신의 의도에 맞는 후보를 선택하려는 경우.
- 기대 효과: 원문과 후보의 실제 차이에 근거한 짧은 설명이 비교·선택에 참고할 정보를 제공한다.
- 우선 줄이려는 위험: 날짜·수치·조건·부정·확정 여부·주체·대상·행동 등 중요한 의미 변화를 놓친 채 후보를 적용하는 것. 설명을 통해 변화를 더 잘 발견하는지 검증할 목표이며, 위험 감소를 달성한 결과로 보지 않는다.
- 설명 열람 자체를 도움이나 만족의 증거로 보지 않는다. 어려움의 빈도와 설명의 효과는 아직 검증 전이다.

사용 기록과 멘토링은 문제를 탐색한 근거다. 이를 실제 고객 전체의 요구나 서비스 재이용 효과로 일반화하지 않는다. 관찰·멘토링·팀 의견과 데이터의 기여는 [프로젝트 선정 근거](research/프로젝트%20선정%20근거.md), 실제 서비스 관찰은 [서비스 사용 기록](research/서비스%20사용%20기록.md)에서 확인한다. 웹 데모 사용 의견은 [사용자 피드백](사용자%20피드백.md)에 기록한다. 최신 작업 상태는 [GitHub Projects](https://github.com/users/dhwjdgh1122/projects/7), 작업 관리 방법과 Issue 링크는 [TASKS](TASKS.md)에서 확인한다.

기업에서 제공한 문장 CSV와 행동 로그는 구조·중복·연결 가능성을 탐색하는 데 활용했다. 원문과 선택된 교정문은 있지만 선택되지 않은 후보 전체와 교정 이유는 없어, 후보별 설명이나 사용자의 선택 이유를 직접 평가할 수 없다. 재실행 로그만으로 불만이나 설명의 필요성을 확정할 수도 없다. 이 데이터는 현재 웹 데모의 모델 학습·후보 생성에 사용하지 않았으며, 설명 기능의 정확성과 사용자 효과는 별도로 검증해야 한다.

## 3. 단계별 범위

| 단계 | 내용 | 완료 시 확인할 결과 |
|---|---|---|
| 기본 교정 기반 | 원문 입력·드래그 선택, 실행, 후보 제공, 변경 강조, 선택 적용 | 선택한 문장에 대해 실제 모델 응답을 받고 해당 위치에 적용 |
| 설명 기능 추가 | 교정 이유 버튼으로 실제 변화와 의미 영향 설명 | 결과는 기본으로 표시하고 버튼을 눌렀을 때 현재 후보의 설명 확인 |
| 별도 개선 | 재실행 후보 중복 제외 | 첫 구현에서 보장하지 않는 임시 개선안 |
| 확장 | 주변 문맥 활용·허용 후 확보·참고 문맥 입력 | 추후 논의 |

현재 기본 교정·비교·적용과 버튼형 설명 기능을 구현하고 실제 예문으로 연결 동작을 확인했다. 전반적인 교정·설명 품질과 사용자 효과는 별도 검증 대상이다. 기능별 완료 조건과 확인 범위는 [기능명세](FEATURE_SPEC.md)에서 확인한다.

### 첫 구현 범위 — 검토 완료 기준안

- 한국어 일반 문장 다듬기 한 가지 동작으로 시작한다. 사용자가 선택한 범위만 교정한다.
- 당시 후보는 최대 3개를 표시하는 기준이었다. 현재 새 교정·재교정은 아래 11/21 후속 결정을 따른다.
- 입력·교정 결과는 현재 페이지에서 관리하고, 첫 구현에는 로그인·문서 저장·히스토리·DB를 추가하지 않는다. 새로고침 시 작업이 사라질 수 있음을 안내한다.
- 번역·요약·확장·카테고리 선택·문체 선택·프리셋·사용자 프롬프트는 우선 보류하는 안이다. 기존 화면의 모든 설정을 작동하는 기능처럼 배치하지 않는다.
- 같은 선택에서 ‘교정 실행’을 다시 누르는 재요청은 가능하다. 별도 재실행 버튼·페이지 내 단축키·이전 실행과의 후보 중복 제외는 구현하지 않았다.

위 보류 목록은 최종 삭제 결정이 아니다. 이후 구현 범위를 조정할 때 함께 재검토할 수 있다.

**11/21 후속 결정 — 후보 3개:** 당시 새 교정·재교정은 모두 정확히 3개를 받도록 정했다. **11/23부터 후보 카드의 재교정은 선택한 후보 1개만 다듬는 방식으로 구분한다.** 최초·일반 교정과 적용 후 재교정의 3개 기준은 유지한다. 어느 경우든 서버에서 선택한 제공자 한 곳에 한 번 요청하며 두 모델 동시 호출·추천 순위는 제공하지 않는다. 요청별 개수가 맞지 않거나 출력이 잘리면 실패로 안내하고 자동 재시도·후보 채우기·복제를 하지 않는다. 의미 보존 지침은 유지하며 중복 없는 생성이나 의미 보존을 보장하는 기능은 아니다. 기존에 저장한 후보 1~3개의 이력과 설명 부분 실패 재요청은 계속 지원한다. 세부 계약은 [F-02](FEATURE_SPEC.md#4-f-02-교정-요청후보-제공)를 따른다.

**11/21 후속 채택 — 교정 이력:** [#8](https://github.com/dhwjdgh1122/writing-demo/issues/8)의 필요성 논의를 이어 현재 브라우저의 저장·조회·삭제·JSON 내보내기를 추가했다. 선택 원문·후보·실제로 생성한 설명과 적용 사실을 보관하며, 전체 문서 자동 복원·계정/서버 동기화는 포함하지 않는다. 저장 실패·손상·다른 탭 변경 처리와 읽기 전용 조회는 [F-06](FEATURE_SPEC.md#correction-history)을 따른다. 이력 보관을 실제 사용자 효과나 설명 품질 개선으로 해석하지 않는다.

## 4. 입력과 실행 환경

**11/21 후속 채택 — 요구 재교정·행동 기록:** [#49](https://github.com/dhwjdgh1122/writing-demo/issues/49)에서 적용 전/후의 선택 요구를 실제 후보 생성에 전달하고 이후 요청·결과·적용을 연결한다. 요구 선택은 선택 사항이며 행동 JSON/CSV의 기본값은 문장 미포함이다. 목적은 요구 이후 결과를 관찰할 기반 마련이며, 요구 충족·설명의 판단 도움을 이미 입증했다는 뜻이 아니다. [입력·보관·통계 기준](FEATURE_SPEC.md#demand-rerun)을 따른다. 첫 구현 때 보류한 일반 문체 메뉴와 구분한다.

**11/24 후속 결정 — 행동 기록 기본 비활성화:** 사용자가 최종 프로젝트에서 사용하지 않기로 한 행동 기록은 화면과 새 수집을 함께 끈다. 코드와 기존 브라우저 자료는 보존하고, 교정 이력·요구 재교정은 계속 제공한다. 기능 설정으로 다시 켤 수 있게 두며 #49의 과거 구현·검증 완료와 이번 사용 범위 변경을 구분한다. [동작과 인수조건](FEATURE_SPEC.md#activity-recording-default-off)을 따른다.

**11/22~23 후속 구현 — 재교정 진입과 후보별 수정:** [#62](https://github.com/dhwjdgh1122/writing-demo/issues/62)에서 큰 상시 ‘다시 다듬기’ 영역을 후보별 적용 버튼과 동일한 크기의 진입 버튼 및 적용 완료 안내 옆의 작은 진입 버튼으로 바꿨다. 작은 적용 후 버튼은 당시 배치이며 현재 배치는 아래 #71의 후보 유지 방식을 따른다. 11/23 사용자 검토 후에는 카드에서 실행한 후보만 다듬고 나머지 후보·설명·비교를 유지하도록 범위를 확정했다. 실행한 자리의 화면 위치와 포커스를 유지하되 대기 중 사용자가 다른 곳으로 이동하면 포커스를 빼앗지 않는다. 새 유효 결과가 올 때까지 기존 결과를 보존하고 실패하면 같은 자리에서 다시 시도한다. 최초 원문과 적용 위치는 유지하며 적용 후 재교정은 현재 문장으로 후보 3개를 만드는 기존 동작을 따른다. #49의 요구 전달·이력·행동 연결 목적은 유지한다. [동작과 인수조건](FEATURE_SPEC.md#rerun-entry-plan), [화면 배치](DESIGN.md#rerun-entry-plan), [PR #63](https://github.com/dhwjdgh1122/writing-demo/pull/63)을 연결한다. 실제 사용자 편의와 요구 충족·설명 품질을 입증한 것은 아니다.

**11/23 후속 개선 — 비교·설명 읽기 유지:** [#66](https://github.com/dhwjdgh1122/writing-demo/issues/66)에서 카드 재교정 후 비교를 다시 펼치거나 새 설명을 다시 요청해야 하는 조작을 줄인다. 실행 카드의 비교 열림·닫힘을 유지하고, 이유가 열린 상태라면 새 후보의 설명을 자동으로 이어서 생성한다. 닫혀 있으면 다음 열기까지 생성하지 않는다. 요구 선택 영역만 성공 후 닫고 초기화하며, 내용 품질 개선·실패 자동 재시도와 구분한다. [동작 기준](FEATURE_SPEC.md#rerun-entry-plan)과 [검증 기록](검증%20기록.md#rerun-reading-continuity-01)을 따른다.

**11/23 후속 변경 — 적용 후에도 후보 비교 유지:** [#71](https://github.com/dhwjdgh1122/writing-demo/issues/71)을 [PR #72](https://github.com/dhwjdgh1122/writing-demo/pull/72)로 반영해 적용 뒤에도 후보 3개와 비교·설명을 남겨 다른 후보로 바꿀 수 있게 했다. 적용한 카드의 같은 크기·위치에 ‘다시 교정하기’를 유지하며 현재 적용 문장으로 새 후보 3개를 요청한다. 다른 카드에서는 먼저 해당 후보로 바꾼 뒤 재교정한다. 재교정 중·실패에는 기존 후보와 문장을 유지하고 성공 시 새 원문 기준 결과로 전환한다. 직접 편집·선택 변경·Undo/Redo의 무효화는 유지한다. #62의 작은 적용 후 버튼과 빈 결과 안내는 당시 구현으로 보존하며 현재 동작은 [F-04](FEATURE_SPEC.md#6-f-04-후보-적용)·[F-07](FEATURE_SPEC.md#rerun-entry-plan)을 따른다. 서버 생성 품질이나 사용자 효과 검증의 완료를 뜻하지 않는다.

**11/23 후속 구현 — 변경 표현과 이유 연결:** 긴 설명 전체를 읽고 변경 위치를 찾는 부담을 줄이기 위해, 원문 비교의 변경 표현을 직접 선택하면 대응하는 전후 표현과 이유를 한 번에 하나씩 확인하도록 했다([#68](https://github.com/dhwjdgh1122/writing-demo/issues/68)·[PR #69](https://github.com/dhwjdgh1122/writing-demo/pull/69)). 번호 배지 대신 표현을 탐색 대상으로 삼고 현재 순서·전체 개수와 이전·다음을 제공한다. 설명 높이는 내용에 맞추며, 직접 선택했을 때 설명이 화면 밖이면 해당 설명으로 이동한다. 실제 문자열에서 계산한 변경 묶음에 모델의 설명을 연결하고, 표현별 자료가 없는 응답·과거 설명은 전체 설명으로 보존한다. [상세 동작](FEATURE_SPEC.md#7-f-05-교정-이유-열기)을 따르며, 이 UI 변경은 #22의 설명 품질 목표 완수나 사용자 판단 도움의 입증을 뜻하지 않는다.

- 교정 대상: 페이지 안에서 사용자가 선택한 텍스트. 전체 문서도 사용자가 직접 전체 선택하면 대상이 될 수 있으나 선택 길이 제한을 적용한다.
- 교정 요청에는 선택하지 않은 주변 문장을 포함하지 않는다. 페이지에 원문 전체가 있다는 이유로 서버에 함께 보내지 않는다.
- 한 번에 교정할 수 있는 선택 텍스트는 최대 1,000자다. 더 긴 범위를 드래그하는 것은 가능하지만 실행을 막고 범위를 줄이도록 안내한다. 원문 전체 입력 한도 20,000자와 구분하며 계산과 경계 처리는 기능명세에서 정의한다.
- 초기 제공자는 Gemini API이며 무료 구간에서 실제 호출을 확인했다. 기존 연결을 유지하면서 엘리스 Serverless GPT-4o mini 연결을 추가했다. 11/24에는 [같은 웹 흐름의 제한 비교](evaluations/provider-workflow-result-2026-11-24.md)를 제공자별 실제 7회 요청으로 마쳤으며, 기본 제공자는 변경하지 않았다. 제공자·모델은 개발자가 서버 설정에서 선택하며 사용자용 모델 선택 화면은 이번 범위에 포함하지 않는다. 팀원은 각자의 키·모델 접근과 지원 한도를 확인해야 한다. 제한 비교를 전반적 교정·설명 품질이나 사용자 효과 검증으로 보지 않으며 공개 배포 방식도 별도로 검토한다.
- 센틴스파이 API 연동이 확보된 것은 아니다. 자체 연결 모델의 후보는 ‘데모 생성 결과’로 구분하며 실제 서비스와 동일한 출력이라고 안내하지 않는다.
- 서버 DB에는 원문·후보를 저장하지 않는다. 11/21 추가한 교정 이력은 선택 원문·후보·받은 설명을 현재 브라우저에 보관하며 사용자가 삭제·내보낼 수 있다. 전체 문서 복원과 외부 모델 제공자의 보관 정책은 보장하지 않는다. API 인증정보는 서버에서만 관리한다.
- 설명에 사용하는 정보는 선택 원문·현재 후보와 실제 전달된 설정이다. 확보하지 않은 글 전체 맥락이나 사용자 의도를 추정해 사실처럼 설명하지 않는다.

## 5. 완료와 검증

<a id="problem-kpi-framework"></a>

### 문제 정의와 KPI의 연결 — 2026-11-22 보강

**핵심 질문은 ‘설명이 추가되면 사용자가 원래 의도에 맞는 후보를 더 정확하고 수월하게 선택하는가’다.** 요청이 성공하거나 설명이 화면에 나타나는 것은 필요한 작동 조건이지만, 이 질문의 답은 아니다. 예를 들어 조건·인원·확정 여부가 달라진 후보를 설명이 정확히 짚고, 사용자가 그 변화를 이해해 원문을 유지한 경우도 유용한 결과일 수 있다. 실제 어려움의 빈도와 설명의 효과는 아직 검증하지 않았다.

| 검증 축 | 확인할 질문 | 기준과 현재 한계 |
|---|---|---|
| 설명 내용 품질 | 실제 변경을 정확히 설명하고 중요한 변화·영향·선택 정보를 빠뜨리지 않는가? | 기존 #5·#20·#22의 사실 오류·중요 변화 포착·선택 정보 기준을 유지한다. #22 전체 기준은 미충족이다. |
| 동작 신뢰성 | 결과를 제공하고 오류를 분리하며 원문을 안전하게 유지하는가? | 교정 완료·설명 제공·오류 재시도와 원문 보존 등을 구분한다. 자동 테스트의 통과 비율을 실사용 성공률로 쓰지 않는다. |
| 사용자 판단 도움 | 의도에 맞는 선택과 중요한 변화 인지가 실제로 나아지는가? | 설명 유무 비교와 짧은 판단 이유가 필요하다. 열람·적용·재요청 횟수만으로 만족이나 설명 효과를 확정하지 않는다. 현재 미측정이다. |

검토한 KPI 안의 **교정 완료 98%·설명 제공 95%·오류 후 재시도 성공 90%는 검토용 제안 목표**다. 실제 성과나 확정된 출시 기준이 아니며, 관측 기간·표본·계측 범위와 기준값을 확인한 뒤 결정한다. 원문 보존·오류 격리 100%, 무효 후보 적용·선택 밖 변경 0%는 관측한 범위에서 확인할 무결성 조건이지 모든 실행에 대한 보증은 아니다. 이 수치로 #22의 기존 사례별 필수 정보·반복 평가 조건을 낮추거나 대체하지 않는다.

계산식·분모·판정 제외·목표 상태는 [평가 기준의 KPI 정의](교정%20설명%20평가%20기준.md#kpi-contract), 행동 기록을 켰을 때 확인 가능한 범위는 [기능명세의 계측 경계](FEATURE_SPEC.md#kpi-measurement-boundary)를 따른다. 11/24부터 행동 기록은 기본 비활성화이며, 수집 코드가 남아 있다는 사실이나 기능을 끈 결정을 KPI 실측·사용자 효과 검증으로 보지 않는다. KPI 전체 자동 집계·관리자 통계·중앙 수집·새 DB는 구현 범위에 없다.

**버전 구분:** 이 보강 당시 제품 기준은 main `17a2a20`이었다. 공백 변경 사실 안내와 11/22 추가 실험은 [PR #55의 `98cd8be`](https://github.com/dhwjdgh1122/writing-demo/pull/55)에 보존된 미병합 변경이다. 당시 #22 품질 개발은 일시 중지하고 문제 정의·측정 기준만 정리했다. 이후 기존 장시간 개선 목표는 사용자 결정으로 [미달성 종료](검증%20기록.md#explanation-goal-closeout-01)했으며, #22 품질 미완료와 원래 평가 기준은 유지한다. [문서 대조 기록](검증%20기록.md#problem-kpi-review-01)은 새 모델 평가 결과가 아니다.

### 작동 여부

- 정상 경로뿐 아니라 빈 선택·요청 실패·선택 변경·원문 편집 시에도 잘못된 위치를 덮어쓰지 않아야 한다.
- 핵심 인수조건은 [기능명세](FEATURE_SPEC.md)의 확인 목록으로 검증한다. 기본 화면·요청·오류·후보 적용과 실제 모델 연결·설명 기능을 구현했다. 수행한 검증과 남은 한계는 [README](../README.md)와 [검증 기록](검증%20기록.md)에 구분해 기록한다.
- 중간발표는 제출한 PPT를 화면 공유하며 실제 실행 캡처로 기능·사용 흐름·한계를 설명했다. 당일 실시간 시연이나 영상 촬영은 하지 않았다. 이후에도 저장 화면과 실시간 결과, 사용 모델과 미완료 기능을 구분한다. 실제 발표 방식과 재사용할 실행 절차는 [시연 안내](DEMO_GUIDE.md)를 참고한다.

### 설명 품질과 사용자 도움

2026-11-16 #5에서 오정호는 ‘수정 내용을 납득하고 자신의 의도에 맞는 후보인지 판단하도록 돕는 설명’을 우선 방향으로 확인했다. 외부 사전·문법 출처 연계는 후속 검토로 둔다. [교정 설명 평가 기준](교정%20설명%20평가%20기준.md)에 내부 품질 평가의 사례·계산·기록 방법을 구체화했으며, 이를 사용자 효과 검증 결과나 팀 전체 합의로 보지 않는다.

| 구분 | 확인 방법 제안 | 해석 범위 |
|---|---|---|
| 설명의 사실 일치 | 날짜·숫자·조건·확정 여부·표현만 변경·원문 동일 사례에서 설명과 실제 차이를 대조 | 오류와 누락을 확인하며 사례 몇 개 통과를 전체 품질로 일반화하지 않음 |
| 사용자의 이해·선택 | 같은 원문·후보에 대해 설명 없는 화면과 설명을 볼 수 있는 화면을 비교 | 의미 변화 인지, 선택 근거, 도움 여부와 읽는 부담을 관찰 |
| 이용 부담 | 설명 열기 전후 소요 시간과 의견 확인 | 빠른 선택이 항상 좋은 선택이라고 가정하지 않음 |

사용자 실험의 참여자 수·평가 문항·비교 순서·목표 수치와 출시 판단을 위한 오류 허용 수준은 아직 미정이다. 내부 설명 품질의 사례별 판정 기준은 위 평가 문서를 따른다. 혼자 진행하는 점검은 내부 품질 확인이며 실제 사용자 효과 검증으로 기록하지 않는다.

사람 대상 평가에 앞서 [AI 사용성 사전 점검](AI%20사용성%20사전%20점검.md)으로 조작 문제와 설명의 부족한 정보를 탐색할 수 있다. [11/18 첫 기록](검증%20기록.md#ai-precheck-01)은 화면 과제 수행 보고와 고정 날짜 사례의 AI 판단이며, 실제 사용자 효과 검증을 대체하지 않는다.

## 6. 후속 확인과 검토 방향

### 다음에 확인·결정할 사항

1. 두 팀원의 기본 실행 확인 답변은 받았다([TEAM-02](검증%20기록.md#team-02)). 추가로 필요한 환경별 설정·API 접근·테스트 결과를 구분해 확인한다. 기본 실행 확인을 모든 환경·입력의 성공이나 모델 품질 검증으로 간주하지 않는다.
2. 내부 설명 품질의 사례·판정 기준은 [기존 평가 기준](교정%20설명%20평가%20기준.md)에 마련돼 있다. 실제 사용자 판단 도움을 확인할 참여자·비교 순서·문항·표본은 미정이며, 종료한 #22 목표의 재개와 구분해 후속 여부를 결정한다.
3. 후보 비교와 설명을 읽는 과정의 불편을 확인하고, [화면 설계](DESIGN.md)의 개선 필요 여부를 논의한다.
4. 요구 재교정은 11/21 후속 범위로 추가했다. 단축키·완전한 후보 중복 제외·선택하지 않은 주변 문맥 활용은 별도 검토한다.

### 데스크톱 앱 사용 환경 확장

중간발표에서는 독립 웹 데모의 실행 화면을 소개했다. 이후 데스크톱 앱 사용 환경으로 확장하는 방향을 검토한다. 실제 센틴스파이 데스크톱 앱에 기능을 추가해 시험할 수 있는 환경은 아직 확보된 것으로 확인되지 않았다. 확장 방식은 웹 데모의 검증 결과와 기업에서 제공 가능한 연동 환경을 확인한 뒤 팀원들과 논의한다. 현재 구현이나 확정된 후속 개발 범위로 보지 않는다.

### 기업 CSV를 활용한 설명 품질 평가

기업 자료의 구조·채택 특성으로 프로젝트 가설을 살펴보는 [기업 데이터 탐색](research/기업%20데이터%20탐색.md)은 아래 설명 품질 평가와 목적을 구분한다. 11/20에는 집계 확인에 이어 [원문·선택문 24쌍을 대조](research/기업%20데이터%20탐색.md#enterprise-pair-review)해 실제 변경과 선택 시 확인할 질문을 정리했다. 단순 표기와 상태 정보 변화, 번역·맥락 부족을 구분한 AI 내부 검토이며, 설명을 생성·채점하거나 실제 사람의 판단 도움을 평가한 것은 아니다. 같은 날 [4차 멘토링 정리본과 대조](research/기업%20데이터%20탐색.md#mentoring-4-summary)해 기존 데이터로 필요성과 사용 상황을 보강하자는 취지를 반영했다. 전달된 운영 설명과 CSV 필드 대응·집계 정의는 구분하며, 탐색만으로 제품 방향이나 설명 효과를 확정하지 않는다.

원문과 사용자가 선택한 교정문 일부를 고정된 문장 쌍으로 삼아 설명의 정확성을 평가하는 후속 아이디어다. 데이터 사용·외부 API 전송 가능 범위와 개인정보를 먼저 확인하고, 사례와 평가 기준을 팀원들과 정한다. 사람이 실제 변경 내용과 의미 영향을 정리한 뒤 같은 문장 쌍에 대한 AI 설명과 비교한다. 교정문을 새로 생성하는 시험과 구분한다.

**11/21 평가 준비:** [24쌍의 적합성·필수 설명 기준](evaluations/enterprise-case-suitability-2026-11-21.md)을 추가했다. 실제 원문·선택문 대응을 재확인하고 준비 적합 7개(설명 평가 후보 6개·동일 문장 고정 안내 1개), 문맥·대응 범위 보류 12개, 번역 범위 제외 5개로 구분했다. 단회 AI 보조 판단이며, 사례를 삭제하거나 기존 #22의 품질 평가 표본·기준을 대체하지 않는다.

선택된 교정문도 반드시 올바른 것은 아니므로, 잘못된 수정이나 정보 누락을 설명이 짚어내는지도 확인한다. 기업 원문을 외부 모델에 입력하는 실제 설명 평가는 아직 수행하지 않았으며, 설명 정확성 평가만으로 사용자의 비교·선택에 도움이 된다고 결론 내리지 않는다.
