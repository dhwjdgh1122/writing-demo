# 제품 기획 — 웹 데모

> 역할: 제품 목적·사용자·범위·검증 목표를 정의한다. 2026-11-06 검토한 기준안과 현재 구현 범위를 정리한다. 개인 검토·구현과 팀 전체 합의·사용자 효과 검증은 구분한다. 작업 관리 방법과 최신 상태의 확인 위치는 [TASKS](TASKS.md)에서 안내한다.

## 1. 목적과 결정된 방향

센틴스파이 데스크톱 앱의 화면과 사용 흐름을 참고해 웹사이트(웹 데모)로 구현했다. 웹페이지 안에서 기본 교정 흐름과 필요할 때 교정 이유를 확인하는 기능을 제공한다. 2026-11-11 중간발표를 진행했으며, 현재는 후속 개선 범위와 검증 계획을 구체화할 단계다. 제품 범위나 검증 가설을 새로 확정한 것은 아니다.

사용자는 페이지 안에서 원문 일부를 선택하고 교정 후보를 받는다. 변경 부분을 확인해 후보를 적용할 수 있으며, 궁금할 때만 ‘교정 이유’ 버튼을 눌러 원문과 후보의 변화 및 의미에 미치는 영향에 대한 AI 설명을 확인한다.

### 이미 선택한 기준

- 실행 환경은 웹사이트이며, 교정 패널의 화면 기준은 센틴스파이 데스크톱 앱이다.
- 페이지 안에 원문 입력·선택 공간을 마련한다. 외부 앱의 문서를 가져오거나 OS 전역 단축키로 호출하는 기능은 첫 웹 데모에 포함하지 않는다.
- 센틴스파이의 화면과 사용 흐름을 참고한 독립 웹 데모로 구현한다. 코드와 AI 연결은 프로젝트 설계에 맞춰 작성한다.
- 기본 교정 흐름을 먼저 구현한 뒤 설명 기능을 추가했다. 후속 작업은 이 흐름을 유지하며 진행한다.
- 개인 시제품을 바탕으로 후속 작업을 나눈다. 담당·범위·일정의 관리 방법은 [작업 목록](TASKS.md)을 따른다.

오정호가 검토한 아래 범위안을 후속 설계의 기준으로 사용한다. 명시적으로 미정인 기술·모델·평가 세부 조건까지 확정된 것은 아니다. 이후 변경은 해당 설계 문서에 반영한다.

## 2. 사용자와 문제 가설

- 기능은 누구나 이용할 수 있으며, 라이트·헤비 사용자 구분에 따라 설명 접근을 제한하지 않는다.
- 문제 가설: 변경 위치를 색으로 확인하더라도, 후보가 원래 의도를 유지하는지와 표현 변화의 의미를 판단하기 어려울 수 있다.
- 설명 효과를 우선 살펴볼 사용자 상황: 후보의 표현 차이나 의미 변화를 확인하고 자신의 의도에 맞는 후보를 선택하려는 경우.
- 기대 효과: 원문과 후보의 실제 차이에 근거한 짧은 설명이 비교·선택에 참고할 정보를 제공한다.
- 설명 열람 자체를 도움이나 만족의 증거로 보지 않는다. 어려움의 빈도와 설명의 효과는 아직 검증 전이다.

사용 기록과 멘토링은 문제를 탐색한 근거다. 이를 실제 고객 전체의 요구나 서비스 재이용 효과로 일반화하지 않는다. 관찰·멘토링·팀 의견과 데이터의 기여는 [프로젝트 선정 근거](research/프로젝트%20선정%20근거.md), 실제 서비스 관찰은 [서비스 사용 기록](research/서비스%20사용%20기록.md)에서 확인한다. 웹 데모 사용 의견은 [사용자 피드백](사용자%20피드백.md)에 기록한다. 최신 작업 상태는 [GitHub Projects](https://github.com/users/dhwjdgh1122/projects/7), 작업 관리 방법과 Issue 링크는 [TASKS](TASKS.md)에서 확인한다.

기업에서 제공한 문장 CSV와 행동 로그는 구조·중복·연결 가능성을 탐색하는 데 활용했다. 원문과 선택된 교정문은 있지만 선택되지 않은 후보 전체와 교정 이유는 없어, 후보별 설명이나 사용자의 선택 이유를 직접 평가할 수 없다. 재실행 로그만으로 불만이나 설명의 필요성을 확정할 수도 없다. 이 데이터는 현재 웹 데모의 모델 학습·후보 생성에 사용하지 않았으며, 설명 기능의 정확성과 사용자 효과는 별도로 검증해야 한다.

## 3. 단계별 범위

| 단계 | 내용 | 완료 시 확인할 결과 |
|---|---|---|
| 기본 교정 기반 | 원문 입력·드래그 선택, 실행, 후보 제공, 변경 강조, 선택 적용 | 선택한 문장에 대해 실제 모델 응답을 받고 해당 위치에 적용 |
| 설명 기능 추가 | 교정 이유 버튼으로 실제 변화와 의미 영향 설명 | 결과는 기본으로 표시하고 버튼을 눌렀을 때 현재 후보의 설명 확인 |
| 별도 개선 | 재실행 후보 중복 제외 | 첫 구현에서 보장하지 않는 임시 개선안 |
| 확장 | 주변 문맥 활용·허용 후 확보·참고 문맥 입력 | 추후 논의 |

현재 기본 교정·비교·적용과 버튼형 설명 기능을 구현하고 실제 예문으로 연결 동작을 확인했다. 전반적인 교정·설명 품질과 사용자 효과는 별도 검증 대상이다. 기능별 완료 조건과 확인 범위는 [기능명세](FEATURE_SPEC.md)에서 확인한다.

### 첫 구현 범위 — 검토 완료 기준안

- 한국어 일반 문장 다듬기 한 가지 동작으로 시작한다. 사용자가 선택한 범위만 교정한다.
- 후보는 최대 3개를 표시한다. 동일 후보·원문과 동일한 결과·후보 부족 처리 기준은 기능명세를 따른다.
- 입력·교정 결과는 현재 페이지에서 관리하고, 첫 구현에는 로그인·문서 저장·히스토리·DB를 추가하지 않는다. 새로고침 시 작업이 사라질 수 있음을 안내한다.
- 번역·요약·확장·카테고리 선택·문체 선택·프리셋·사용자 프롬프트는 우선 보류하는 안이다. 기존 화면의 모든 설정을 작동하는 기능처럼 배치하지 않는다.
- 같은 선택에서 ‘교정 실행’을 다시 누르는 재요청은 가능하다. 별도 재실행 버튼·페이지 내 단축키·이전 실행과의 후보 중복 제외는 구현하지 않았다.

위 보류 목록은 최종 삭제 결정이 아니다. 이후 구현 범위를 조정할 때 함께 재검토할 수 있다.

## 4. 입력과 실행 환경

- 교정 대상: 페이지 안에서 사용자가 선택한 텍스트. 전체 문서도 사용자가 직접 전체 선택하면 대상이 될 수 있으나 선택 길이 제한을 적용한다.
- 교정 요청에는 선택하지 않은 주변 문장을 포함하지 않는다. 페이지에 원문 전체가 있다는 이유로 서버에 함께 보내지 않는다.
- 현재 선택 길이는 최대 1,000자다. 계산과 경계 처리는 기능명세에서 정의한다.
- 초기 제공자는 Gemini API이며 무료 구간에서 실제 호출을 확인했다. 기존 연결을 유지하면서 엘리스 Serverless GPT-4o mini 연결을 추가해 비교 시험할 수 있게 한다. 제공자·모델은 개발자가 서버 설정에서 선택하며 사용자용 모델 선택 화면은 이번 범위에 포함하지 않는다. 팀원은 각자의 키·모델 접근과 지원 한도를 확인해야 한다. 엘리스 실호출 확인 상태는 검증 기록을 따르며, 전반적 교정 품질과 공개 배포 방식은 별도로 검토한다.
- 센틴스파이 API 연동이 확보된 것은 아니다. 자체 연결 모델의 후보는 ‘데모 생성 결과’로 구분하며 실제 서비스와 동일한 출력이라고 안내하지 않는다.
- 앱 자체에는 원문·후보를 영구 저장하지 않는다. 외부 모델 제공자의 보관 정책까지 보장하는 문구는 쓰지 않는다. API 인증정보는 서버에서만 관리한다.
- 설명에 사용하는 정보는 선택 원문·현재 후보와 실제 전달된 설정이다. 확보하지 않은 글 전체 맥락이나 사용자 의도를 추정해 사실처럼 설명하지 않는다.

## 5. 완료와 검증

### 작동 여부

- 정상 경로뿐 아니라 빈 선택·요청 실패·선택 변경·원문 편집 시에도 잘못된 위치를 덮어쓰지 않아야 한다.
- 핵심 인수조건은 [기능명세](FEATURE_SPEC.md)의 확인 목록으로 검증한다. 기본 화면·요청·오류·후보 적용과 실제 모델 연결·설명 기능을 구현했다. 수행한 검증과 남은 한계는 [README](../README.md)와 [검증 기록](검증%20기록.md)에 구분해 기록한다.
- 중간발표는 제출한 PPT를 화면 공유하며 실제 실행 캡처로 기능·사용 흐름·한계를 설명했다. 당일 실시간 시연이나 영상 촬영은 하지 않았다. 이후에도 저장 화면과 실시간 결과, 사용 모델과 미완료 기능을 구분한다. 실제 발표 방식과 재사용할 실행 절차는 [시연 안내](DEMO_GUIDE.md)를 참고한다.

### 설명 품질과 사용자 도움

| 구분 | 확인 방법 제안 | 해석 범위 |
|---|---|---|
| 설명의 사실 일치 | 날짜·숫자·조건·확정 여부·표현만 변경·원문 동일 사례에서 설명과 실제 차이를 대조 | 오류와 누락을 확인하며 사례 몇 개 통과를 전체 품질로 일반화하지 않음 |
| 사용자의 이해·선택 | 같은 원문·후보에 대해 설명 없는 화면과 설명을 볼 수 있는 화면을 비교 | 의미 변화 인지, 선택 근거, 도움 여부와 읽는 부담을 관찰 |
| 이용 부담 | 설명 열기 전후 소요 시간과 의견 확인 | 빠른 선택이 항상 좋은 선택이라고 가정하지 않음 |

참여자 수·평가 문항·비교 순서·목표 수치·오류 허용 기준은 아직 미정이다. 혼자 진행하는 점검은 내부 품질 확인이며 실제 사용자 효과 검증으로 기록하지 않는다.

## 6. 후속 확인과 검토 방향

### 다음에 확인·결정할 사항

1. 팀원 환경에서 [실행 안내](../README.md)에 따라 설정·실행을 확인한다. 개인 환경의 실제 호출 성공을 모든 환경의 성공으로 간주하지 않는다.
2. 구현한 교정·설명 흐름의 품질과 사용자 도움을 검증할 사례·평가 기준·방법을 구체화한다.
3. 후보 비교와 설명을 읽는 과정의 불편을 확인하고, [화면 설계](DESIGN.md)의 개선 필요 여부를 논의한다.
4. 단축키·별도 재실행 버튼·후보 중복 개선·문맥 활용은 필요성과 범위를 검토한 뒤 채택 여부를 정한다.

### 데스크톱 앱 사용 환경 확장

중간발표에서는 독립 웹 데모의 실행 화면을 소개했다. 이후 데스크톱 앱 사용 환경으로 확장하는 방향을 검토한다. 실제 센틴스파이 데스크톱 앱에 기능을 추가해 시험할 수 있는 환경은 아직 확보된 것으로 확인되지 않았다. 확장 방식은 웹 데모의 검증 결과와 기업에서 제공 가능한 연동 환경을 확인한 뒤 팀원들과 논의한다. 현재 구현이나 확정된 후속 개발 범위로 보지 않는다.

### 기업 CSV를 활용한 설명 품질 평가

원문과 사용자가 선택한 교정문 일부를 고정된 문장 쌍으로 삼아 설명의 정확성을 평가하는 후속 아이디어다. 데이터 사용·외부 API 전송 가능 범위와 개인정보를 먼저 확인하고, 사례와 평가 기준을 팀원들과 정한다. 사람이 실제 변경 내용과 의미 영향을 정리한 뒤 같은 문장 쌍에 대한 AI 설명과 비교한다. 교정문을 새로 생성하는 시험과 구분한다.

선택된 교정문도 반드시 올바른 것은 아니므로, 잘못된 수정이나 정보 누락을 설명이 짚어내는지도 확인한다. 아직 진행하지 않은 제안이며, 설명 정확성 평가만으로 사용자의 비교·선택에 도움이 된다고 결론 내리지 않는다.

담당·기한·작업 진행 상태의 확인 위치는 [작업 목록](TASKS.md)에서 안내한다. GitHub Projects 운영 전에는 TASKS를, 운영 후에는 연결된 Issues·Projects를 기준으로 한다. 이 문서에 팀 역할 배분표를 중복 작성하지 않는다.
