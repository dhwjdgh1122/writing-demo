# 공동 작업과 중간발표 준비

> 역할: 공동 작업 후보·준비 일정과 작업 관리 방법을 안내한다. GitHub Projects 준비 중에는 이 문서에서 상태를 관리하며, 개인 준비 상태와 실제 팀 합의·배정을 구분한다. 최신화: 2026-11-09.

## 현재 확인한 상태

- 오정호가 개인 시제품을 먼저 구현했다. 원문 선택 → 교정 후보 표시·변경 강조 → 선택 범위 적용과 버튼형 설명 기능을 구현·시험했다. 세부 근거는 [README](../README.md)와 [검증 기록](검증%20기록.md)에 있다.
- 대상 사용자·설명 방향에 관한 기존 팀원 의견은 [프로젝트 선정 근거](research/프로젝트%20선정%20근거.md)에 정리했다. 이후 웹 데모 사용 피드백과 구분한다.
- 두 팀원 모두 저장소 초대를 수락하고 README를 읽어 실행했다는 오정호의 전달을 확인했다. 병찬님의 웹 데모 피드백은 수령했고, 희원님의 이번 웹 데모 사용 피드백은 대기 중이다. 앞서 받은 희원님의 방향성 답변과는 별개다.
- 설명 품질·사용자 효과는 아직 검증 중이다. 위 의견 수령은 구현 전체에 대한 팀 승인이나 역할 배정 완료를 뜻하지 않는다.
- [GitHub 저장소](https://github.com/dhwjdgh1122/writing-demo)를 생성하고 `main`에 문서·코드·시연 자료를 업로드했다. 팀원별 OS·Node 버전·API 설정과 전체 테스트 통과 여부까지 확인한 것은 아니다.

- 전달 준비 점검: 개인 자료·키를 제외한 임시 복사본에서 새 설치, 타입 검사·빌드, 자동 테스트 36개·Edge 테스트 15개 통과. 기존 개발 서버로 교정·설명 각 1회와 적용을 확인했다. [시연 안내](DEMO_GUIDE.md)·화면 5개를 준비했으며, 상세 근거는 [공유 전 설치·실행 점검](검증%20기록.md#handoff-01)에 있다. 같은 컴퓨터의 점검이며 팀원 환경 검증은 별도다.

- 팀원에게 목적·구현 범위의 이해 여부와 사용 중 느낀 UI·불편·개선 의견을 요청했다. 아래 작업표대로 역할을 배정한 것은 아니다. 최신 안내는 저장소의 [README](../README.md)와 관련 문서에서 확인한다.

- 추가 연결 시험 완료: Gemini 연결을 유지하고 엘리스 GPT-4o mini를 서버 설정으로 선택할 수 있게 했다. 교정 응답을 확인했으나 잘못된 후보와 설명 인용 차단이 있어 품질 검증은 남아 있다. 중간발표 전에는 기존 기능 점검과 발표 준비를 우선하며 모델 비교·최종 선택은 후속 검토로 둔다. [ELICE-01](검증%20기록.md#elice-01) 참고.

## GitHub Projects 준비와 문서 역할

공동 대시보드는 GitHub Projects를 사용하기로 했다. 현재는 도입 결정 단계이며, 보드·Issue 생성과 접근 권한 설정 완료는 확인되지 않았다.

- **준비 중:** 이 문서의 작업 후보를 검토하고 담당·범위·완료 기준을 협의한다. 보드가 준비되기 전까지 작업 목록과 상태를 유지한다.
- **보드 운영 시작 후:** Issues에는 작업 내용·재현 절차·완료 기준·논의를, Projects에는 상태·담당·우선순위를 관리한다. 이 문서에는 실제 대시보드 링크와 사용 안내를 남기고, 옮긴 작업의 상태표는 중복 갱신하지 않는다.
- 작업 카드에는 사용자 행동과 기대 결과를 적고 필요한 저장소 내부 문서를 연결한다. 저장소 밖의 개인 공유 문서를 읽어야만 이해할 수 있는 카드로 만들지 않는다.
- 상태별 보기와 작업 영역별 보기를 준비할 예정이다. 상태·영역·우선순위와 담당은 아직 확정하지 않았다. Markdown 수정이 보드에 자동 반영되도록 구성된 상태도 아니다.

준비 순서는 작업 후보 검토 → 보드 생성·팀원 접근 확인 → 채택한 작업의 Issue 등록·보드 연결 → TASKS에 실제 링크와 관리 기준 반영이다. 이 문서 갱신만으로 GitHub에 보드나 Issue가 생성되는 것은 아니다.

## 발표 전 일정

오정호가 정리한 중간발표 준비 계획이며, 개별 담당은 팀원들과 협의해 정한다.

| 날짜 | 작업 | 완료 기준 | 상태 |
|---|---|---|---|
| 11/7 토요일 | 공유 자료·시제품의 실제 실행 화면 준비·공유 | 문제·기능·현재 구현·한계를 설명하고 자유로운 의견 요청 | 문서·실행 화면 준비 완료. 목적·범위 이해와 사용 의견 요청. 별도 수신 확인을 진행 조건으로 두지 않음 |
| 11/8 일요일 | GitHub 계정 수집·저장소 생성·초대·실행 안내 | 개발 폴더만 공유하고 팀원 환경의 실행 결과·문제 기록 | 저장소 업로드·두 팀원 초대 수락·README 기반 실행 확인 전달받음. 완료 날짜별 세부 시각은 미확인 |
| 11/9 월요일 | 의견 정리·필요 문서 갱신·공통 규칙·역할 협의·작업 시작 | 담당·수정 범위·완료 기준 결정, 첫 통합 확인, 발표 목차·화면 설명 흐름 초안 | 병찬님 사용 피드백 수령·GitHub Projects 도입 결정. 회의·역할 확정·코드 통합 완료는 미확인 |
| 11/10 화요일 오후 2~3시 | 새 기능 작업 마감 목표 | 이후 통합 점검·오류 수정에 집중 | 예정 |
| 11/10 화요일 오후 6시 | 발표 버전 확정 목표 | 핵심 흐름·실패 상태 점검, PPT/PDF에 넣을 실행 화면 확보, 이후 자료 마무리·리허설 | 예정 |
| 11/11 수요일 | 최종 확인·중간발표 | PPT/PDF의 화면 표시·발표 순서 최종 확인 후 발표 | 예정 |

기존에 작동하는 데모를 기준으로 추가 작업을 검증한다. 안정화되지 않은 기능은 발표 버전에서 보류한다. 발표자료는 오정호가 최종 정리하고, 작업이 일찍 끝나면 함께 준비한다. 발표는 PPT 또는 PDF 중심으로 실제 실행 화면을 설명하며, 당일 실시간 시연이나 영상 촬영은 필수로 두지 않는다.

### 이번 사용 피드백에서 구체화할 작업 후보

아래는 오정호가 전달한 병찬님의 사용 피드백을 분류한 것이다. 의견·질문은 [사용자 피드백](사용자%20피드백.md#feedback-01), 실제 출력은 [검증 기록의 TEAM-01](검증%20기록.md#team-01)을 참고한다. 모두 담당·기한·채택 여부 미정이며, 현재는 제보 접수 또는 논의 단계다.

| 구분 | 사용자 행동·기대 결과 중심의 작업 후보 | 확인할 내용·완료 기준 후보 |

| 오류 재현 | 여러 문장을 교정해도 문장 내용이 임의로 누락되지 않는지 확인 | 입력·선택 범위·실제 응답을 재현하고, 문장 누락과 줄바꿈 변경을 구분해 기록 |

| 기대·설명 검토 | 설명을 읽고 실제 변경과 의미 영향을 이해하기 | 설명의 명칭·내용에 대한 기대를 확인하고 평가 기준 정리 |

## 관리 기준

팀원은 [README](../README.md)에서 프로젝트 전체를 파악하고 이 문서에서 할 일을 확인한다. 별도 전달용 문서의 작성·수신을 작업 조건으로 두지 않는다.

- 작업 시작 전에 담당·수정 범위·완료 기준을 기록하고, 완료 표시에는 확인 근거를 붙인다.
- PR 절차와 검증 명령은 [협업 안내](../CONTRIBUTING.md), 제품 범위는 [PRD](PRD.md)를 기준으로 한다.
- 공동 버전의 검토·통합은 오정호가 담당한다. 팀원 PR의 승인·병합과 오정호 본인의 직접 반영 기준은 협업 안내를 따른다. 이 역할은 개별 기능의 담당 배정과 구분한다.
- 보드 운영 전에는 담당·일정·진행 상태를 이 문서에서 갱신한다. 운영 시작 후에는 위 역할 구분에 따라 Issues·Projects에서 관리하고 기능·설계 변경은 해당 명세에 반영한다.
- 팀원 제보와 직접 재현, 개선 제안과 채택된 작업, 구현과 검증 완료를 구분한다. 피드백 접수만으로 제품 요구사항이나 완료 상태를 바꾸지 않는다.
