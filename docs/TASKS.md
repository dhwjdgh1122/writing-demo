### 최초 등록과 이후 운영

1. TASKS의 공통 일정·작업 후보를 사용자 피드백·검증 기록과 대조해 Issue와 기존 보드에 일괄 등록했다.
2. 새 작업은 Issue로 작성하고 보드에 추가된 것을 확인한다. 아래 최신화 기준에 따라 TASKS의 작업 제목·Issue 링크·출처도 함께 반영한다. 채택 전이면 ‘작업 후보’로 두고 역할 협의 후 담당·범위·완료 기준을 정한다.
3. 작업 시작 시 ‘진행 중’, 검토 요청 시 ‘검토 중’으로 바꾼다. 완료 기준과 검증 근거를 확인한 후 완료 처리한다.
4. 기능·설계 변경과 실제 검증 결과는 해당 기준 문서에 반영한다. 저장소 밖 개인 공유 문서를 필수 입력으로 사용하지 않는다.

**자동화 확인 범위:** 최초 구성 시 새 Issue의 보드 자동 추가를 확인했다. 11/12에는 #12를 완료 사유로 종료한 뒤 연결된 보드 카드가 자동으로 ‘완료’가 된 것을 GitHub API로 확인했다. 팀원의 접속·사용과 완료 전환 확인 답변도 받았다. 다만 이 기록을 모든 종료 사유·재개·양방향 전환 조건의 검증 완료로 확대하지 않으며, 이후 변경 때도 Issue와 보드 상태를 함께 확인한다. 새 Issue의 초기 상태가 ‘진행 예정’으로 들어오면 미채택 후보는 ‘작업 후보’로 변경한다.

### 최초 구성과 자동화 범위

TASKS.md의 작업 후보·준비 일정을 참고해 Issue 17개를 만들고, 해당 Issue들을 Projects 대시보드에 연결했다.

TASKS.md를 수정하거나 커밋·푸시해도 Issue와 Projects는 자동으로 변경되지 않는다. GitHub에서 Issue를 생성·수정해도 TASKS.md에는 자동 반영되지 않는다. 문서와 GitHub 사이의 상시 동기화는 구성되어 있지 않으므로 관련 변경은 별도로 반영해야 한다.

새 Issue의 보드 자동 추가는 문서 동기화와 별개의 기능이다.

### Issue 변경 시 TASKS 최신화

**어떤 경로로 Issue를 생성·수정하더라도 TASKS의 작업 제목·링크·출처·일정 안내에 미치는 영향을 확인하고, 달라진 항목만 최신화한다.**

| 변경 경로 | 함께 반영할 내용 |
|---|---|
| GitHub에서 직접 Issue 생성·수정 | 새 작업은 제목·Issue 링크·제안 배경 또는 근거 문서를 추가한다. 기존 작업은 TASKS의 안내와 달라진 항목을 갱신한다. |
| TASKS에 먼저 적지 않고 AI에게 Issue 생성·수정 요청 | AI는 Issue 처리와 함께 TASKS에 미치는 영향을 확인하고 필요한 항목을 추가·갱신한다. |
| TASKS에서 작업을 추가하거나 안내 내용 변경 | 연결된 Issue에도 반영할 사항을 확인하고 별도로 생성·수정한다. |

TASKS는 작업 안내·출처·링크를, Issue는 상세 작업 내용·완료 기준·논의를, Projects는 최신 상태·담당·목표일을 관리한다. 단순 댓글·체크리스트·상태·담당·목표일 변경만으로 TASKS를 수정하거나 상태표를 중복 작성하지 않는다. 다만 변경 때문에 TASKS에 적힌 작업 설명·근거·공동 일정도 달라지면 그 부분은 갱신한다. 예를 들어 ‘진행 중 → 검토 중’은 보드에서 관리하고, 새 작업 생성·제목 변경·발표 준비로의 일정 전환은 관련 색인·안내에도 반영한다.

근거 문서가 없는 직접 제안은 Issue에 제안 배경을 기록하고 TASKS에서 해당 Issue로 연결한다. 출처가 확인되지 않으면 임의로 작성하지 않는다.

## 11/9 월요일 준비 순서

아래는 당시 계획과 준비 기록이다. 이후 실행 확인·발표 준비 전환은 상단 실제 진행 경과와 연결된 Issue를 따른다.

오늘 목표는 팀원이 다음 날 맡은 작업을 시작할 수 있도록 실행 안내·공통 문서·작업 관리 공간을 준비하는 것이다. 아래는 11/9 준비·이관 시점의 기록이며 이후 진행 상태는 연결한 Issue와 보드에서 확인한다. 역할 배정과 팀원 실행 확인의 완료를 뜻하지 않는다.

| 순서 | 할 일 | 완료 기준 | 상태 |

- 오늘 최신 코드의 설치·실행 확인은 오정호가 먼저 진행한다. 팀원들은 **11/10 화요일 오전에 최신 코드를 받아 README에 따라 실행을 확인한 뒤**, 배정된 작업의 브랜치를 만들어 개발을 시작하는 계획이다. 팀원별 확인 완료 여부는 실제 결과를 받은 후 갱신한다.
- 실제 실행·테스트 결과는 [검증 기록](검증%20기록.md)에 남긴다. 기존 설치 성공·팀원 실행 보고·자동 검증 통과를 이번 최신 코드의 실행 확인 완료로 간주하지 않는다.
- 공유 메시지는 변경 요약과 링크 중심으로 작성한다. 실행·제공자 설정은 README, 협업 규칙은 CONTRIBUTING, 작업 안내는 이 문서를 기준으로 하며 내용을 중복 작성하지 않는다.

## 발표 전 일정

아래 일정표와 시각은 **당초 준비 계획**이며 현재 할 일 목록이 아니다. 실제 변경 경과는 상단에 기록하고, 후속 개발 일정은 새 합의 후 Issue·Projects에서 정한다.

오정호가 정리한 중간발표 준비 계획이며, 개별 담당은 팀원들과 협의해 정한다. 아래 상태는 보드 이관 시점의 기록이다. 이후 최신 상태·담당·목표일은 Projects에서 확인하며, 화요일 오후 2~3시 새 기능 마감·오후 6시 발표 버전 확정 목표는 발표 버전 통합 Issue에서 함께 관리한다.

**11/12 확인한 계획 변경:** 오정호의 전달에 따르면 11/10 오전 신규 개발 역할 배정·브랜치 개발 착수와 변경분 통합을 보류하고 발표 준비로 전환했다. 팀원별 실행 확인 답변을 받았으며, 발표 준비 중 기존 데모의 후보 표시·비교·설명·적용 흐름을 다시 점검하고 11/11 중간발표를 진행했다. 아래 표는 당초 계획으로 보존한다. 변경된 작업 범위와 점검 근거는 [#12](https://github.com/dhwjdgh1122/writing-demo/issues/12)에서 관리하며, 당초 통합 일정이나 신규 변경분의 자동 검사·전체 실패 흐름 재점검까지 완료했다는 의미는 아니다.

## 관리 기준

팀원은 [README](../README.md)에서 프로젝트 전체를 파악하고 이 문서에서 할 일을 확인한다. 별도 전달용 문서의 작성·수신을 작업 조건으로 두지 않는다.

- 작업 시작 전에 담당·수정 범위·완료 기준을 기록하고, 완료 표시에는 확인 근거를 붙인다.
- PR 절차와 검증 명령은 [협업 안내](../CONTRIBUTING.md), 제품 범위는 [PRD](PRD.md)를 기준으로 한다.
- 공동 버전의 검토·통합은 오정호가 담당한다. 팀원 PR의 승인·병합과 오정호 본인의 직접 반영 기준은 협업 안내를 따른다. 이 역할은 개별 기능의 담당 배정과 구분한다.
- 담당·일정·진행 상태는 Projects, 작업 내용·완료 기준·논의는 Issue에서 관리하고 기능·설계 변경은 해당 명세에 반영한다.
- 팀원 제보와 직접 재현, 개선 제안과 채택된 작업, 구현과 검증 완료를 구분한다. 피드백 접수만으로 제품 요구사항이나 완료 상태를 바꾸지 않는다.
