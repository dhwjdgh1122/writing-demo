[#9의 두 제공자 제한 비교](evaluations/provider-workflow-result-2026-11-24.md)와 [#7의 실제 붙여넣기 정책 판단](검증%20기록.md#clipboard-selection-20261124)은 PR #73으로 main에 반영했다. [#59](https://github.com/dhwjdgh1122/writing-demo/issues/59)는 지정 조건 재시도 정상·최초 현상 미재현이며, [#22](https://github.com/dhwjdgh1122/writing-demo/issues/22)의 설명 내용 품질은 미완료이고 기존 장시간 목표는 미달성 종료다. 구현 기준은 [기능명세](FEATURE_SPEC.md), 실제 확인 결과는 [검증 기록](검증%20기록.md)을 따른다. 아래 11/12 경과와 11/9 계획은 과거 기록이며 현재 상태표가 아니다.

### 기존 구현·공유 근거

- 오정호가 개인 시제품을 먼저 구현했다. 원문 선택 → 교정 후보 표시·변경 강조 → 선택 범위 적용과 버튼형 설명 기능을 구현·시험했다. 세부 근거는 [README](../README.md)와 [검증 기록](검증%20기록.md)에 있다.
- 대상 사용자·설명 방향에 관한 기존 팀원 의견은 [프로젝트 선정 근거](research/프로젝트%20선정%20근거.md)에 정리했다. 이후 웹 데모 사용 피드백과 구분한다.
- 두 팀원 모두 저장소 초대를 수락하고 README를 읽어 실행했다는 오정호의 전달을 확인했다. 병찬님과 희원님의 웹 데모 피드백을 모두 수령했다. 희원님은 현재 방향과 필요할 때만 설명을 여는 사용 흐름에 긍정적인 의견을 주었으며, 현재 추가 기능 제안은 없다. 상세 내용은 [희원님 의견](사용자%20피드백.md#feedback-02)에 기록했으며, 이 의견에 따른 기존 작업·역할 배정 변경은 없다.
- 설명 품질·사용자 효과는 아직 검증 중이다. 위 의견 수령은 구현 전체에 대한 팀 승인이나 역할 배정 완료를 뜻하지 않는다.
- [GitHub 저장소](https://github.com/dhwjdgh1122/writing-demo)를 생성하고 `main`에 문서·코드·시연 자료를 업로드했다. 팀원별 OS·Node 버전·API 설정과 전체 테스트 통과 여부까지 확인한 것은 아니다.

- 전달 준비 점검: 개인 자료·키를 제외한 임시 복사본에서 새 설치, 타입 검사·빌드, 자동 테스트 36개·Edge 테스트 15개 통과. 기존 개발 서버로 교정·설명 각 1회와 적용을 확인했다. [시연 안내](DEMO_GUIDE.md)·화면 5개를 준비했으며, 상세 근거는 [공유 전 설치·실행 점검](검증%20기록.md#handoff-01)에 있다. 같은 컴퓨터의 점검이며 팀원 환경 검증은 별도다.

- 팀원에게 목적·구현 범위의 이해 여부와 사용 중 느낀 UI·불편·개선 의견을 요청했다. 아래 작업표대로 역할을 배정한 것은 아니다. 최신 안내는 저장소의 [README](../README.md)와 관련 문서에서 확인한다.

- 추가 연결 시험 완료: Gemini 연결을 유지하고 엘리스 GPT-4o mini를 서버 설정으로 선택할 수 있게 했다. 교정 응답을 확인했으나 잘못된 후보와 설명 인용 차단이 있어 품질 검증은 남아 있다. 중간발표 전에는 기존 기능 점검과 발표 준비를 우선했다. 모델 비교·최종 선택은 후속 검토 대상이며, 기존 [ELICE-01](검증%20기록.md#elice-01)과 병찬님의 추가 제보 [ELICE-02](검증%20기록.md#elice-02)를 구분한다.

### 이슈·작업 카드 공통 양식

신규·기존 작업과 작업 후보·진행 중·보류·완료 여부에 관계없이 **아래 6개 제목의 문구와 순서를 유지**한다. Projects에서 연결된 Issue의 본문을 편집하며 보드용 설명을 별도로 복제하지 않는다. Draft 카드에도 같은 양식을 사용한다. PR 설명·팀원 댓글·과거 검증 보고서까지 이 양식으로 바꾸지는 않는다.

| 고정 제목 | 작성할 내용 |
|---|---|
| 사용자 상황과 문제 | 누가 어떤 상황에서 무엇을 어려워하는지. 필요하면 짧은 가상 예시를 넣되 실제 재현 결과와 구분한다. 내부 작업은 개발자·팀의 상황을 설명한다. |
| 목적과 작업 범위 | 해결하려는 문제, 포함·제외 범위. 제안·채택·구현을 구분한다. |
| 현재 상태 | 확인일과 현재 결과. 구현·검증·main 반영 여부 및 미확인 사항을 구분하고 상세 상태·담당·목표일은 Projects를 따른다. |
| 완료 기준 | 확인 가능한 체크리스트. 완료 작업도 실제 완료한 범위와 근거를 남긴다. 단순 양식 정리로 기준을 낮추거나 미완료 항목을 체크하지 않는다. |
| 관련 작업과 근거 | 이슈·PR·기준 문서·검증 기록 링크와 각각의 관계. 선행 조건·후속 개선·참고 자료를 구분하고 번호만 나열하지 않는다. |
| 다음 작업 및 남은 과제 | 다음 행동, 보류 이유·재개 조건, 완료 범위 밖의 한계. 완료된 작업도 후속 과제가 있으면 연결한다. |

- 제목을 삭제하거나 바꾸지 않는다. 해당하지 않으면 `해당 없음`, 확인이 필요하면 `확인 필요`, 남은 과제가 없으면 `없음`으로 적어 누락과 구분한다. 본문 길이는 작업에 맞게 조절한다.
- 처음 읽는 팀원이 목적과 현재 상태부터 이해할 수 있도록 쓴다. 개인 대화 지시·승인 경과를 반복하거나 최신 작은 변경을 전체 목적처럼 소개하지 않는다. 작성자·확인 주체는 근거 구분에 필요할 때만 적는다.
- 완료 카드의 과거 테스트 숫자·환경은 당시 결과로 표시한다. 코드 분석·팀원 제보·직접 재현·실제 모델 평가·사용자 효과 검증을 구분한다. 작업 브랜치 결과를 main의 기능으로 표시하지 않는다.
- 현재 본문에는 최신 요약을 두고 상세 실험·실패·이전 결정은 기존 검증 기록과 PR로 연결한다. 기존 본문에만 있는 과거 기록을 줄일 때에는 접근 가능한 이력 자료를 먼저 보존하고 연결한다. 과거 본문 전체를 중첩된 접기 영역으로 계속 덧붙이지 않는다. 팀원 댓글·첨부와 원자료는 보존한다.
- 본문을 정리한 뒤 Issue 상태·Projects 상태·담당·목표일·라벨이 의도치 않게 바뀌지 않았는지 확인한다. 내용 수정만으로 완료 처리하거나 새 작업을 채택하지 않는다.
- 새 Issue는 [공통 템플릿](../.github/ISSUE_TEMPLATE/work-item.md)을 사용한다. 템플릿의 안내 주석을 실제 내용으로 바꾸고 빈 항목 처리 기준을 따른다. 이 문서를 양식의 기준으로 유지한다.

2026-11-19 기존 카드 정리 전 본문은 [이슈 본문 이력 자료](history/issue-bodies-2026-11-19.json)에 이슈 번호·URL·당시 상태·본문·해시로 보존한다. 현재 상태표나 새 검증 결과가 아니며, 해당 시점의 표현은 이후 이슈 본문과 구분한다.

### 최초 등록과 이후 운영

1. TASKS의 공통 일정·작업 후보를 사용자 피드백·검증 기록과 대조해 Issue와 기존 보드에 일괄 등록했다.
2. 새 작업은 Issue로 작성하고 보드에 추가된 것을 확인한다. 아래 최신화 기준에 따라 TASKS의 작업 제목·Issue 링크·출처도 함께 반영한다. 채택 전이면 ‘작업 후보’로 두고 역할 협의 후 담당·범위·완료 기준을 정한다.
3. 작업 시작 시 ‘진행 중’, 검토 요청 시 ‘검토 중’으로 바꾼다. 완료 기준과 검증 근거를 확인한 후 완료 처리한다.
4. 기능·설계 변경과 실제 검증 결과는 해당 기준 문서에 반영한다. 저장소 밖 개인 공유 문서를 필수 입력으로 사용하지 않는다.

‘작업 후보’에는 채택 전 작업과 재개 대기 작업을 둔다. 이미 착수했다가 보류한 경우에는 해당 Issue에 보류 사유·보존 브랜치·재개 조건을 명시한다. 후보 상태만으로 미착수 또는 구현 완료라고 판단하지 않는다.

**자동화 확인 범위:** 최초 구성 시 새 Issue의 보드 자동 추가를 확인했다. 11/12에는 #12를 완료 사유로 종료한 뒤 연결된 보드 카드가 자동으로 ‘완료’가 된 것을 GitHub API로 확인했다. 팀원의 접속·사용과 완료 전환 확인 답변도 받았다. 다만 이 기록을 모든 종료 사유·재개·양방향 전환 조건의 검증 완료로 확대하지 않으며, 이후 변경 때도 Issue와 보드 상태를 함께 확인한다. 새 Issue의 초기 상태가 ‘진행 예정’으로 들어오면 미채택 후보는 ‘작업 후보’로 변경한다.

### 최초 구성과 자동화 범위

TASKS.md의 작업 후보·준비 일정을 참고해 Issue 17개를 만들고, 해당 Issue들을 Projects 대시보드에 연결했다.

TASKS.md를 수정하거나 커밋·푸시해도 Issue와 Projects는 자동으로 변경되지 않는다. GitHub에서 Issue를 생성·수정해도 TASKS.md에는 자동 반영되지 않는다. 문서와 GitHub 사이의 상시 동기화는 구성되어 있지 않으므로 관련 변경은 별도로 반영해야 한다.

새 Issue의 보드 자동 추가는 문서 동기화와 별개의 기능이다.

### Issue 변경 시 TASKS 최신화

**어떤 경로로 Issue를 생성·수정하더라도 TASKS의 작업 제목·링크·출처·일정 안내에 미치는 영향을 확인하고, 달라진 항목만 최신화한다.**

| 변경 경로 | 함께 반영할 내용 |
|---|---|
| GitHub에서 직접 Issue 생성·수정 | 새 작업은 제목·Issue 링크·제안 배경 또는 근거 문서를 추가한다. 기존 작업은 TASKS의 안내와 달라진 항목을 갱신한다. |
| TASKS에 먼저 적지 않고 AI에게 Issue 생성·수정 요청 | AI는 Issue 처리와 함께 TASKS에 미치는 영향을 확인하고 필요한 항목을 추가·갱신한다. |
| TASKS에서 작업을 추가하거나 안내 내용 변경 | 연결된 Issue에도 반영할 사항을 확인하고 별도로 생성·수정한다. |

TASKS는 작업 안내·출처·링크를, Issue는 상세 작업 내용·완료 기준·논의를, Projects는 최신 상태·담당·목표일을 관리한다. 단순 댓글·체크리스트·상태·담당·목표일 변경만으로 TASKS를 수정하거나 상태표를 중복 작성하지 않는다. 다만 변경 때문에 TASKS에 적힌 작업 설명·근거·공동 일정도 달라지면 그 부분은 갱신한다. 예를 들어 ‘진행 중 → 검토 중’은 보드에서 관리하고, 새 작업 생성·제목 변경·발표 준비로의 일정 전환은 관련 색인·안내에도 반영한다.

근거 문서가 없는 직접 제안은 Issue에 제안 배경을 기록하고 TASKS에서 해당 Issue로 연결한다. 출처가 확인되지 않으면 임의로 작성하지 않는다.

## 발표 전 일정

아래 일정표와 시각은 **당초 준비 계획**이며 현재 할 일 목록이 아니다. 실제 변경 경과는 상단에 기록하고, 후속 개발 일정은 새 합의 후 Issue·Projects에서 정한다.

오정호가 정리한 중간발표 준비 계획이며, 개별 담당은 팀원들과 협의해 정한다. 아래 상태는 보드 이관 시점의 기록이다. 이후 최신 상태·담당·목표일은 Projects에서 확인하며, 화요일 오후 2~3시 새 기능 마감·오후 6시 발표 버전 확정 목표는 발표 버전 통합 Issue에서 함께 관리한다.

**11/12 확인한 계획 변경:** 오정호의 전달에 따르면 11/10 오전 신규 개발 역할 배정·브랜치 개발 착수와 변경분 통합을 보류하고 발표 준비로 전환했다. 팀원별 실행 확인 답변을 받았으며, 발표 준비 중 기존 데모의 후보 표시·비교·설명·적용 흐름을 다시 점검하고 11/11 중간발표를 진행했다. 아래 표는 당초 계획으로 보존한다. 변경된 작업 범위와 점검 근거는 [#12](https://github.com/dhwjdgh1122/writing-demo/issues/12)에서 관리하며, 당초 통합 일정이나 신규 변경분의 자동 검사·전체 실패 흐름 재점검까지 완료했다는 의미는 아니다.
