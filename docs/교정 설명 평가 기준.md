# 교정 설명의 사용자 기대와 평가 기준

> 역할: F-05 설명의 내용 기준을 사례와 수동 평가 절차로 구체화한다. 2026-11-16 [#5](https://github.com/dhwjdgh1122/writing-demo/issues/5)에서 오정호가 선택한 작업 방향을 정리했다. 팀 전체 동의나 사용자 효과 검증 결과를 뜻하지 않는다. 제품 목적은 [PRD](PRD.md), 실제 동작·오류 처리는 [기능명세](FEATURE_SPEC.md), 실행 결과는 [검증 기록](검증%20기록.md)이 기준이다.

## 1. 어떤 판단을 돕는가

**사용자가 수정 내용을 납득하고, 자신의 의도에 맞는 교정 후보인지 판단하도록 돕는다.**

특히 중요한 정보가 바뀐 것을 모르고 후보를 적용해 잘못 전달할 위험을 줄이는 것이 목표다. 교정은 원문의 중요한 정보를 보존하도록 요청하고, 설명은 실제 후보에서 그 정보가 달라지거나 빠졌다면 사용자가 알아차리도록 돕는다. 설명도 틀릴 수 있으므로 완전한 방지나 위험 감소가 검증됐다고 표현하지 않는다. 실제 사용자가 의미 변화를 더 잘 발견하는지는 후속 사용자 평가에서 확인한다.

사용자는 같은 상황에서도 오탈자만 빠르게 고치고 싶을 수 있고, 날짜나 조건이 바뀌었는지 확인하고 싶을 수 있다. 사용 빈도로 사람을 나누지 않고, 현재 글에서 확인할 필요가 생긴 순간에 설명을 이용하도록 한다. 설명 없이 후보를 적용하는 흐름도 유지한다.

| 사용자가 궁금한 점 | 설명이 제공할 정보 | 피해야 할 답변 |
|---|---|---|
| 무엇을 고쳤나? | 해당 후보의 실제 변경 | 다른 후보에서만 바뀐 표현을 가져옴 |
| 바꾸면 무엇이 달라지나? | 날짜의 구체성, 조건, 수치, 확정 여부 등 전달 내용의 차이 | “더 자연스럽다”만 반복 |
| 내 글에 이 후보를 써도 되나? | 유지하거나 잃는 정보를 짚고 필요한 경우 조건부 선택 기준 제시 | 사용자 의도를 추정해 무조건 추천 |

‘왜 고쳤는가’는 실제 변화와 그 효과를 통해 납득할 수 있게 설명한다는 뜻이다. 교정 모델의 내부 판단을 복원하거나 원래 수정 의도를 알고 있다고 말하는 것은 아니다. 외부 사전·문법 출처 검색, RAG, 규칙 번호 제시는 이번 범위의 필수 조건이 아니다. 없는 근거를 만들어 채우지 않는다.

## 2. 기존 근거와 현재 기능의 차이

| 근거 | 확인한 내용 | 이번 기준에 반영할 점 |
|---|---|---|
| [FEEDBACK-01](사용자%20피드백.md#feedback-01) | 병찬님은 ‘어떻게 바뀌었는지’보다 ‘왜 바뀌었는지’를 기대했다고 전달 | 변경 나열을 넘어 전달 내용에 미치는 영향을 평가 |
| [FEEDBACK-03](사용자%20피드백.md#feedback-03), [ELICE-02](검증%20기록.md#elice-02) | 변경된 후보를 동일하다고 설명하거나 실제 변경과 맞지 않는 설명이 제보됨 | 사실 일치와 후보별 대응을 우선 확인. 이번 문서 작성으로 재현·수정 완료가 되지는 않음 |
| [설명 프롬프트](../server/llm/prompt.ts) | 실제 차이·의미 영향, 후보별 독립 비교, 근거 없는 정당화 금지를 이미 지시 | 새 방향을 처음 구현한 것으로 표현하지 않고 실제 출력이 지침을 따르는지 평가 |
| [인용 검사](../server/llm/explanation-check.ts), F-05 | 일부 인용 문자열 불일치를 차단 | 검사 통과가 의미 판단의 정확성을 보장하지 않음. 표시 차단과 설명 품질을 따로 기록 |
| [고정 평가 사례](../tests/fixtures/explanation-cases.json) | 숫자·날짜·조건·원문 동일 등의 문장 쌍이 존재 | 기존 사례와 출처를 유지하고 아래 기준에 연결 |

현재 설명은 선택 원문과 후보를 받아 교정과 별도로 생성된다. 선택하지 않은 주변 문맥과 사용자의 실제 의도는 입력되지 않는다. 별도 요청이라는 사실만으로 설명 품질 문제의 원인을 확정할 수 없다.

## 3. 설명 내용과 명칭

기본 구성은 **실제 변경 → 전달 내용에 미치는 영향 → 필요한 경우 선택 시 고려점**이다. 모든 설명에 세 부분을 기계적으로 채우지는 않는다. 단순 오탈자에는 짧게 답하고, 의미 변화가 있으면 그 영향을 먼저 다룬다. 기존의 후보당 1~2문장 목표·최대 400자 제한을 따른다.

- 날짜·수치·조건·부정·확정 여부·요청 강도뿐 아니라 누가, 누구에게, 무엇을 하는지에 해당하는 주체·대상·행동의 변화나 핵심 문장 누락을 우선 짚는다. 목록에 없더라도 전달 내용에 영향을 주는 변경은 평가 대상이다.
- 단순 오탈자는 실제 수정 내용을 짧게 설명한다. 중요한 의미 변화는 그 영향과 선택 기준까지 설명한다. 정보가 부족해 선택을 권하기 어렵다면 무엇을 확인해야 하는지 알려준다.
- 잘못된 후보도 무조건 개선으로 설명하지 않는다. 후보가 부적절하다는 사실을 정확히 알리는 설명은 적절할 수 있다.
- 의도가 입력되지 않았다면 “목요일 일정을 전달하려는 경우”처럼 조건을 붙인다. 사용자가 실제로 그 의도를 가졌다고 단정하지 않는다.
- 의미가 유지됐다는 표현은 비교한 범위에서 뒷받침될 때만 사용한다. 모든 오류가 해결됐다고 보증하지 않는다.
- 원문과 완전히 같은 후보에는 변경 없음만 안내한다. 현재 이 문구는 서버의 고정 처리이며 모델 설명 품질 점수와 구분한다.

**현재 화면 명칭은 ‘교정 이유 보기’다.** 이번 작업에서 화면을 바꾸지 않는다. 후속 화면 개선 시 검토할 명칭은 ‘변경 설명 보기’, 안내 문구는 ‘바뀐 표현과 의미에 미치는 영향을 확인하세요.’를 제안한다. 내부 사고 과정이나 외부 문법 출처까지 제공한다는 오해를 줄이려는 제안이며, 명칭 변경의 효과는 아직 확인하지 않았다.

## 4. 대표 평가 사례

아래 적절·부적절 설명은 기준을 설명하기 위해 작성한 예시다. 모델의 실제 출력이나 정답 문자열이 아니며, 같은 필수 내용을 다른 표현으로 전달해도 된다. **모든 사례는 이번 작업에서 추가 실행하지 않았다.**

위 내용은 #5 기준 작성 당시의 범위다. 이후 #20에서 E-01·02·03·04·05·07을 실제 호출한 결과는 [1차 평가](evaluations/교정%20설명%201차%20평가.md)에 별도로 보존했다. 아래 기대 예시는 실제 출력으로 교체하지 않는다.

### E-01 단순 오탈자

- 출처: 기준 설명용 작성 사례. 과거 화면을 재현한 기록이 아니다.
- 원문: `금요일까지 자료를 보내 주세여.`
- 후보: `금요일까지 자료를 보내 주세요.`
- 필수: ‘주세여’가 ‘주세요’로 바뀌었음을 설명하고 날짜·요청 내용에 없는 변화를 만들어내지 않는다.
- 적절한 예: “‘주세여’를 ‘주세요’로 고쳤습니다. 금요일까지 자료를 보내 달라는 요청 내용은 유지됩니다.”
- 부족한 예: “더 자연스러운 문장이 되었습니다.”
- 잘못된 예: “목요일이라는 날짜를 금요일로 바로잡았습니다.”

### E-02 안내 날짜의 구체성 감소

- 출처: 기준 설명용 작성 사례. 실제 서비스 관찰을 그대로 복사한 원문·후보 쌍이 아니다.
- 원문: `목요일에 다시 안내하겠습니다.`
- 후보: `이후에 다시 안내하겠습니다.`
- 필수: 특정 요일이 사라졌고 재안내 시점이 덜 구체적이라는 점을 짚는다.
- 적절한 예: “‘목요일’이 ‘이후’로 바뀌어 다시 안내할 날짜가 구체적으로 드러나지 않습니다. 목요일 일정을 전달하려는 경우 원래 표현을 유지하는 편이 적절합니다.”
- 부족한 예: “‘목요일’을 ‘이후’로 바꿨습니다.”
- 잘못된 예: “일정이 더 명확해졌습니다.”

### E-03 조건·숫자·확정 여부 변화

- 출처: 기존 fixture `NEW-meaning` / `m2`. 개발자가 만든 설명 시험용 후보이며 서비스가 생성한 후보가 아니다.
- 원문: `담당자의 확인을 받은 경우에만 화요일까지 8명에게 자료를 보낼 예정이며, 발송은 확정되지 않았습니다.`
- 후보: `화요일까지 10명에게 자료를 발송합니다.`
- 필수: 확인 조건 삭제, 8명→10명, 예정·미확정 표현 삭제를 모두 짚는다.
- 적절한 예: “담당자 확인 조건이 빠지고 대상이 8명에서 10명으로 바뀌었습니다. 예정·미확정이라는 표현도 사라져 발송을 확정적으로 전달하므로, 원문의 조건과 정보를 유지하려는 경우 이 후보를 그대로 적용하지 않는 편이 적절합니다.”
- 부족한 예: “대상 인원이 바뀌었습니다.” — 나머지 중요한 변화를 누락.
- 잘못된 예: “같은 뜻을 더 간결하게 전달합니다.”

### E-04 후보별 변경 구분

- 출처: 기존 fixture `NEW-payment` / `p1`, `p2`. 개발자가 만든 고정 문장 쌍이다.
- 원문: `참가자 8명중 2명은 등록비를 아직 결재하지 않앗습니다.`
- 후보 p1: `참가자 8명 중 2명은 등록비를 아직 결제하지 않았습니다.`
- 후보 p2: `참가자 8명 중 2명은 등록비를 아직 결재하지 않았습니다.`
- 필수: p1에는 ‘결재→결제’가 있지만 p2에는 없음을 구분한다. 8명·2명·미납 상태를 왜곡하지 않는다.
- p1 설명 예: “띄어쓰기와 ‘않앗습니다’를 고치고, 등록비 지불 상황에 맞게 ‘결재’를 ‘결제’로 바꿨습니다.”
- p2 설명 예: “띄어쓰기와 ‘않앗습니다’를 고쳤지만 ‘결재’는 그대로입니다. 등록비 지불을 뜻하려는 경우 해당 표현을 추가로 확인할 필요가 있습니다.”
- 잘못된 예: p2에서 “‘결재’를 ‘결제’로 수정했습니다”라고 하거나 없는 문법 조항을 인용함.

### E-05 원문과 동일한 후보

- 출처: 기존 fixture `NEW-meaning` / `m3`. 원문·후보는 E-03의 원문과 완전히 같다.
- 필수: 변경이 없음을 알린다. 새로운 변경 이유나 개선 효과를 만들지 않는다.
- 현재 고정 문구: `원문과 동일하여 변경된 표현이나 의미가 없습니다.`
- 잘못된 예: “승인 조건을 더 명확하게 수정했습니다.”
- 구분: 고정 처리 동작 확인용이다. 모델이 설명을 잘 생성했다는 평가에 포함하지 않는다.

### E-06 바뀐 후보를 동일하다고 설명한 제보

- 출처: [ELICE-02](검증%20기록.md#elice-02)의 문장 2·후보 3에서 확인할 발췌. 원문 전체가 아닌 변경 구간만 아래에 제시한다.
- 원문 구간: `선택한 문장에 선택된 것을 확인합니다.`
- 후보 구간: `선택한 문장을 확인합니다.`
- 전달된 설명: `이候 보기에 제안된 내용은 원문과 동일합니다.`
- 필수: ‘원문과 동일’이라는 주장이 실제 차이와 맞는지 확인한다. 혼합 문자 문제와 내용 오류를 별도로 기록한다.
- 해석: 보존된 제보에 나타난 불일치다. 현재 모델의 재현 결과가 아니며, API 원응답·전체 연결 상태를 추가 확보해야 원인을 좁힐 수 있다. 이 발췌만으로 새 실험의 전체 입력을 대신하지 않는다.

### E-07 부정·행동 주체 변화

- 출처: 기준 설명용 작성 사례. 실제 실행 결과가 아니다.
- 원문: `신청자는 운영진에게 자료를 보내지 않습니다.`
- 후보: `운영진은 신청자에게 자료를 보냅니다.`
- 필수: 보내지 않는다는 부정이 사라지고, 보내는 사람과 받는 사람이 서로 바뀌었음을 모두 짚는다.
- 적절한 예: “자료를 보내지 않는다는 내용이 보낸다는 내용으로 바뀌고, 보내는 사람과 받는 사람도 서로 바뀌었습니다. 원문의 전달 관계와 부정 내용을 유지하려는 경우 이 후보를 그대로 적용하지 않는 편이 적절합니다.”
- 부족한 예: “문장의 주어가 바뀌었습니다.” — 부정과 수신 대상 변화를 누락.
- 잘못된 예: “같은 내용을 능동적으로 표현했습니다.”

## 5. 사람이 평가하는 기준

평가 단위는 **고정 원문 + 후보 하나 + 그 후보의 설명**이다. 먼저 사람이 원문·후보를 비교해 필수 요소를 적고, 그다음 설명을 읽는다. 후보의 교정 품질과 설명 품질은 별도 열에 기록한다. E-03처럼 후보가 의도를 훼손해도 설명이 이를 정확히 짚으면 설명은 통과할 수 있다.

| 항목 | 통과 조건 | 실패·보완 예 |
|---|---|---|
| 사실 일치 | 실제 차이와 인용·후보 대응이 일치 | 없는 수정, 다른 후보의 변화, 변경됐는데 동일하다고 주장하면 실패 |
| 중요한 의미 변화 포착 | 사례별 필수 변화와 영향이 빠짐없이 포함 | E-03에서 숫자만 언급하면 보완 필요 |
| 근거 범위 준수 | 제공된 문장에 근거하고 모르는 의도·출처를 만들지 않음 | 확인하지 않은 사용자 목적·문법 조항 단정은 실패 |
| 선택에 참고할 정보 | 단순 변경에는 구체적 설명, 중요한 의미 변화에는 영향과 조건부 선택 기준 또는 확인할 정보 제공 | E-02에서 단어 치환만 나열하거나 영향만 말하고 고려점을 생략하면 보완 필요 |
| 읽기 편의 | 이해 가능한 한국어로 짧게 설명, 모순·불필요한 반복 없음 | 혼합 문자·불명확한 지칭 등은 보완 필요 |

사례 종합 판정은 `통과 / 보완 필요 / 실패 / 판정 보류`로 기록한다. 사실 오류·근거 없는 단정이 있으면 다른 장점으로 상쇄하지 않고 실패로 본다. 사실 오류 없이 필수 정보가 부족하면 보완 필요다. 자료가 부족하면 보류하고 필요한 자료를 적는다. 요청 실패·표시 차단으로 설명을 못 본 경우에는 품질 판정 대신 `설명 미제공`으로 기록한다.

### 지표와 수집 방법

아래는 #5에서 정의한 **내부 평가용 지표**다. 기준 작성 당시에는 미측정이었으며, 이후 #20의 [1차 평가](evaluations/교정%20설명%201차%20평가.md#분모를-구분한-예비-집계)에서 AI 보조 예비 집계를 수행했다. 사람의 최종 평가·실제 사용자 효과 검증과 구분하며, 출시 합격률·사용자 효과의 목표 수치는 정하지 않았다.

| 지표 | 정의·계산 | 수집 방법·현재 상태 |
|---|---|---|
| 사실 오류율 | 사실 오류가 1개 이상인 설명 수 ÷ 사실 판단 가능한 모델 설명 수 | 원문·후보·설명 대조. #20 AI 예비 집계 완료, 사람의 최종 평가 대기 |
| 중요 변화 포착률 | 정확히 설명한 필수 의미 변화 수 ÷ 평가 가능한 사례의 사전 정의 필수 의미 변화 수 | E-03은 조건·숫자·확정 여부 3개로 집계. 단순 오탈자·동일 후보 제외. #20 AI 예비 집계 완료, 사람의 최종 평가 대기 |
| 선택 정보 충족률 | 위 ‘선택에 참고할 정보’ 조건을 만족한 설명 수 ÷ 해당 항목 평가 가능한 모델 설명 수 | 사례별 기준으로 판정. #20 AI 예비 집계 완료, 사람의 최종 평가 대기. 실제 선택 도움의 간접 지표이며 사용자 효과 아님 |
| 설명 제공률 | 화면에서 설명을 확인한 후보 수 ÷ 설명을 요청한 후보 수 | 후속 앱 실행에서 후보별 표시·오류 기록. 모델 설명 대상과 동일 후보 고정 안내를 분리. 미측정 |

항상 분자·분모와 표본 구성, 제외·보류 이유를 함께 제시한다. 분모가 0이면 비율을 계산하지 않는다. 설명이 차단된 건을 조용히 제외해 품질이 좋아 보이게 하지 않도록 미제공 건수·제공률을 함께 보고한다. 위 지표를 평균 낸 하나의 종합 점수는 만들지 않는다.

### 실행·기록 절차

1. 사례 ID·출처·원문·후보·필수 요소를 확정한다. 기업 데이터 원문을 가져오거나 외부 모델에 전송하는 일은 이 작업에 포함하지 않는다.
2. 실제 실행 시 코드 커밋, 프롬프트 버전, 제공자·모델, 일시, 후보 ID, 평가 경로(API 직접/앱 화면)를 기록한다. 고정 후보 설명 시험과 새 교정 후보 생성 시험을 구분한다.
3. 반환 설명과 표시·차단 여부를 보존한다. 처음 실패한 결과도 남기고 재시도는 별도 실행으로 기록한다. 비밀키·인증 헤더는 저장하지 않는다.
4. 항목별 판정·근거 표현·검토자를 기록한다. 의견이 다르면 불일치 항목과 조정 근거를 남긴다. 혼자 평가했다면 내부 1인 점검으로 표시한다.
5. 실제 결과는 [검증 기록](검증%20기록.md)에 실행 자료와 연결하고, 문제별로 프롬프트·검사·화면 중 개선할 범위를 정한다. 이 문서의 기대 예시를 실제 결과 칸에 복사하지 않는다.

기록 양식: `실행 ID / 사례·후보 ID / 출처 / 원문 / 후보 / 실제 설명 / 표시·차단 / 필수 요소별 판정 / 후보 품질 메모 / 설명 종합 판정 / 근거 / 검토자 / 미확인 사항`.

기존 [수동 평가 스크립트](../scripts/evaluate-explanations.mjs)는 Gemini에서 기존 fixture 3개와 두 프롬프트를 비교하는 도구다. 위 E-01~07 전체를 자동 실행하거나 이 기준으로 채점하는 도구가 아니다. 실제 모델 호출이 발생하므로 이번 문서 검토에서는 실행하지 않았다. CI의 응답 주입 테스트도 이 의미 평가를 대신하지 않는다.

## 6. 남은 검증과 후속 작업

- #5의 산출물은 평가 기준과 사례다. 당시 프롬프트·코드·화면 수정, 새 모델 평가, 실제 사용자 실험은 수행하지 않았다.
- 이후 #20에서 고정 원문·후보의 실제 설명 수집과 AI 보조 예비 평가를 수행했다. [1차 평가](evaluations/교정%20설명%201차%20평가.md)의 실제 출력·실패 결과를 보존하며 사람의 최종 평가와 사용자 효과 검증은 남아 있다.
- #20에서 발견한 문제의 개선은 [#22](https://github.com/dhwjdgh1122/writing-demo/issues/22)·[PR #23](https://github.com/dhwjdgh1122/writing-demo/pull/23)에서 다뤘다. 11/17 기준 설명 품질 문제로 보류 중이며 해당 작업 브랜치의 구현·추가 평가는 main에 반영되지 않았다. 제공자 비교를 재개할 때는 [#9](https://github.com/dhwjdgh1122/writing-demo/issues/9)의 계획과 맞춘다.
- 사람이 설명을 읽고 의미 변화를 이해하는지, 의도에 맞는 선택에 도움이 되는지는 [PRD의 사용자 도움 검증](PRD.md#설명-품질과-사용자-도움)에서 별도로 확인한다. 참여자·비교 순서·목표 수치는 아직 미정이다.
- [AI 사용성 사전 점검](AI%20사용성%20사전%20점검.md)은 기존 E-01·02·03과 #20의 저장 설명을 재사용한다. [첫 기록](검증%20기록.md#ai-precheck-01)의 E-02에서는 AI가 설명 전부터 날짜 차이를 알아냈다. 이 답변을 사람의 선택 도움이나 #22 병합 품질 기준 충족으로 계산하지 않는다.
- 외부 문법·사전 근거 연계, 설명 미리 생성, 주변 문맥 활용은 후속 검토다. 이번 기준 정리만으로 구현하기로 결정한 것은 아니다.
