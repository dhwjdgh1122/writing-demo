# AI 사용성 사전 점검

> 역할: AI 에이전트가 화면을 조작하거나 고정 사례를 검토하는 사전 점검 방법을 안내한다. 2026-11-18 작성. 실제 결과는 [검증 기록 AI-PRECHECK-01](검증%20기록.md#ai-precheck-01), 개선 의견은 [사용자 피드백](사용자%20피드백.md#ai-feedback-01)에서 관리한다. 실제 사용자 평가나 서비스의 자동 실행 기능이 아니다.

**기록 시점 구분:** 아래 첫 점검 계획과 저장 설명은 11/18 기준이다. 이후 교정 이력·후보별 재교정·변경 표현별 설명 탐색이 추가됐으므로 새 점검을 채택할 때는 당시 화면과 [현재 기능명세](FEATURE_SPEC.md)를 구분해 과제를 정한다. 기존 결과를 새 UI의 사용성 검증으로 계산하지 않는다. #22 장시간 품질 개선 목표는 [미달성 종료](검증%20기록.md#explanation-goal-closeout-01)했으며, 이 안내가 추가 실행이나 목표 재개를 승인하는 것은 아니다.

## 목적과 구분

실제 사람에게 사용을 부탁하기 전에 조작이 막히는 지점과 설명의 부족한 정보를 찾는다. AI가 성공했다고 사람이 쉽게 사용한다는 뜻은 아니며, AI의 선택·만족도 표현을 사용자 효과의 근거로 삼지 않는다. 제품의 검증 목표는 [PRD](PRD.md#설명-품질과-사용자-도움), 설명의 필수 내용은 [평가 기준](교정%20설명%20평가%20기준.md)을 따른다.

| 구분 | 제공 자료 | 확인 범위 |
|---|---|---|
| A. 화면 사용 흐름 | 실행된 데모·공개 가능한 원문·과제 | 실제 입력·선택·교정·비교·적용·복사와 막힌 지점 |
| B. 설명 내용 | 고정 원문·후보, 이후 저장된 실제 설명 | 설명 전후 판단 근거, 설명의 누락·모순에 대한 AI 예비 검토 |

화면 캡처만 제공하면 실제 클릭·반응을 확인할 수 없다. B를 채팅으로 진행하면 브라우저 사용성·설명 표시 성공을 확인한 것이 아니다. 두 결과를 합쳐 사용자 효과가 검증됐다고 표현하지 않는다.

## 환경과 실행 범위

1. 개발 대화·정답·사용법을 전달하지 않은 새 세션을 준비한다. 이 문서 전체에는 진행자용 기준이 있으므로 과제 부분만 전달한다.
2. 브라우저 실행·캡처 확인·조작 가능 여부와 데모 접근을 먼저 확인한다. URL만 전달해도 조작 가능한 것은 아니며 다른 실행 환경에서 로컬 주소에 접근하지 못할 수 있다.
3. 개발자가 [README](../README.md)의 방법으로 데모를 준비한다. 실제 API 사용량과 공개 가능한 입력 범위를 확인한다. 서비스 키나 인증 헤더를 에이전트 과제·기록에 넣지 않는다.
4. 에이전트는 소스코드·README·개발 문서·기존 테스트를 읽거나 API를 직접 호출해 과정을 건너뛰지 않는다. 브라우저 조작용 임시 스크립트는 사용할 수 있지만 제품 코드 변경·응답 주입은 하지 않는다.
5. 첫 점검 범위는 A-01 1회와 B-02 1회다. A는 교정 요청 1회·필요한 경우 설명 요청 최대 1회, 오류 시 재요청하지 않는다. B는 저장 자료를 사용하므로 서비스 모델을 추가 호출하지 않는다. 에이전트 자체의 모델 이용은 서비스 호출 횟수와 별개다.
6. A를 먼저 끝내고 B를 진행한다. 같은 세션이면 그 사실을 기록하며 서로 독립된 참여자로 계산하지 않는다. 도구 접근 실패는 서비스 결함과 구분한다.

### 로컬 브라우저 도구를 찾지 못할 때

Node와 저장소에 설치된 Playwright를 사용할 수 있다. 저장소 루트에서 `node -e "console.log(require.resolve('playwright'))"`로 위치를 확인하고, 조작용 스크립트에서 `chromium.launch({ channel: 'msedge' })`로 Edge 실행을 시도할 수 있다. Edge 설치·실행 권한·스크린샷 열람 도구는 별도 확인한다. 전역 명령이 없다는 것만으로 브라우저가 없다고 결론 내리지 않는다. 실행할 수 없으면 오류와 미실행 범위를 남긴다. 이 안내는 클릭 순서나 정답을 제공하는 것이 아니다.

## A. 화면 과제 템플릿

중괄호 항목만 채워 전달한다. 드래그·교정 실행·이유 보기 같은 정답 순서는 알려주지 않는다.

```text
{데모 주소}에 접속하고 브라우저를 조작할 수 있는지 먼저 확인해주세요.
불가능하면 실행하지 못했다고 알려주세요.
소스코드·README·개발 문서·기존 테스트는 읽지 말고 화면만 사용하세요.
API 직접 호출·응답 주입·제품 코드 수정은 하지 마세요.

상황: {상황}
원문: {원문}
원문이 전달하는 내용을 유지하면서 문장을 다듬고 최종 문장을 복사해 답변해주세요.
적절한 후보가 없으면 적용하지 않아도 됩니다.
교정 요청은 1회, 교정 이유 요청은 필요하면 최대 1회입니다.
오류가 나면 재요청하지 말고 기록해주세요.

화면을 확인한 뒤 다음 조작을 결정하세요. 실제 조작·화면 반응·최종 문장·
막힌 지점을 적고 가능하면 캡처를 남겨주세요. 관찰 사실·예상 불편·
도구 제약을 구분하고 하지 않은 행동·감정·대기 시간을 만들지 마세요.
```

설명을 열지 않거나 부적절한 후보를 적용하지 않는 행동을 실패·이탈로 단정하지 않는다. 아래 B의 고정 후보가 실제 서비스에서 나올 것이라고 가정하지 않는다.

## 사례 선택 — 진행자용

기존 #5·#20의 개발자 작성 사례다. 실제 사용자의 문제 빈도를 입증하는 표본이나 기업 데이터가 아니다.

| 사례 | 상황·원문 | B의 고정 후보 | 확인할 정보 |
|---|---|---|---|
| A-01 / B-01 (E-01) | 팀원에게 자료 제출 요청. `금요일까지 자료를 보내 주세여.` | `금요일까지 자료를 보내 주세요.` | 오타 수정과 요청 내용 유지 |
| B-02 (E-02), 첫 설명 점검 | 행사 참가자에게 다음 일정 안내. `목요일에 다시 안내하겠습니다.` | `이후에 다시 안내하겠습니다.` | 특정 요일 소실과 시점의 구체성 감소 |
| B-03 (E-03), 후속 확장 | 팀에 발송 계획 공유. `담당자의 확인을 받은 경우에만 화요일까지 8명에게 자료를 보낼 예정이며, 발송은 확정되지 않았습니다.` | `화요일까지 10명에게 자료를 발송합니다.` | 확인 조건 삭제·8명→10명·미확정→확정적 표현 |

B-03은 복합 사례이므로 어떤 요소 하나가 어려움의 원인이라고 단정하지 않는다. 첫 점검에서 B-01·B-03까지 모두 실행할 필요는 없다.

## B. 설명 전후 자료 제공

먼저 상황·원문·고정 후보만 전달하고 답변을 보존한다.

```text
아래는 준비된 고정 사례이며 이번 서비스 실행에서 생성한 후보가 아닙니다.
상황: {상황}
원문: {원문}
후보: {고정 후보}
원문이 전달하는 내용을 유지하려 합니다. 이 후보를 그대로 사용하겠나요?
사용 / 사용하지 않음 / 판단하기 어려움 중 선택하고 원문·후보의 근거를 적어주세요.
제공되지 않은 맥락이나 의도는 추측하지 마세요. 서비스 요청은 하지 마세요.
```

그다음 [#20 원자료](evaluations/criteria-2026-11-16T11-06-00-424Z.json)의 해당 사례 `response.explanations`를 그대로 제공한다. 실행 ID·후보 ID를 기록하며, [기대 설명 예시](교정%20설명%20평가%20기준.md)를 실제 출력 대신 사용하지 않는다.

```text
다음은 과거 실제 API 평가에서 저장된 설명입니다. 새로 생성한 응답이 아닙니다.
설명: {저장된 실제 설명}
1. 후보를 사용할지 판단이 같나요, 달라졌나요?
2. 새로 얻은 정보가 있나요? 앞선 답변에서 이미 알아낸 내용과 구분해주세요.
3. 판단 근거로 사용한 실제 설명 문구를 적어주세요.
4. 설명에 틀리거나 이해하기 어려운 내용이 있나요? 없으면 없다고 답해주세요.
설명이 도움이 됐다고 가정하거나 사람의 감정·만족도를 대신 판단하지 마세요.
추가 서비스 요청은 하지 마세요.
```

## 기록과 후속 판단

- 날짜·커밋·에이전트 모델·도구·브라우저·데모 모델 설정을 기록한다. 확보하지 못한 값은 미확인으로 남긴다.
- A/B·사례 ID·실시간/저장 응답·원문/후보/설명·실제 요청 횟수·조작·캡처·실패와 중단을 구분한다. 실행 보고만 전달받았다면 직접 재현으로 기록하지 않는다.
- B는 설명 전후 선택·이유·새 정보·근거 문구를 남긴다. 선택 변화만을 성공으로 보지 않고 반복해서 읽은 영향과 이미 알고 있던 내용을 구분한다.
- 실제 결과는 [검증 기록](검증%20기록.md), 예상 불편·개선 제안은 [사용자 피드백](사용자%20피드백.md)에 연결한다. 상세 결과나 상태표를 여러 문서에 복제하지 않는다.
- 기존 #5·#20의 기준·자료와 #22의 실패 근거를 먼저 활용한다. #22의 보류 브랜치 결과를 main 기능으로 표시하거나 이 점검으로 병합 기준을 대체하지 않는다. #8 히스토리의 필요성도 이 점검에서 검증한 것이 아니다. 최신 작업 상태는 [TASKS](TASKS.md)의 Issue·Projects 링크를 따른다.
- 최초 소규모 점검이 끝나면 추가 실행 필요성을 판단한다. 실제 사람의 사용성·설명 효과·전체 품질·만족도·이탈률은 별도 검증 대상이다.
