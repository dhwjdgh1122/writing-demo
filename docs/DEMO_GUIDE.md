### 11/24 최종발표 전 멘토링 반영 방향

사용자가 전달한 5차 멘토링 정리본을 현재 구현·기존 분석 기록과 대조했다. 녹음·녹취 원문을 검증한 기록은 아니다. 아래는 발표를 구성할 지침이며 완성된 자료·대본이나 새 개발 계획을 뜻하지 않는다.

**필요성부터 설명한다.** 기존 서비스 사용 경험에서 후보 판단을 돕는 설명이라는 가설을 세웠고, 이후 기업 자료를 분석해 어떤 변경에서 판단 정보가 필요한지 구체화했다. 처음부터 데이터로 효과를 입증해 기능을 기획한 것처럼 설명하지 않는다. [기업 CSV·로그와 분석 JSON](research/기업%20데이터%20탐색.md)에는 전체 CSV 75,881행과 고유 전체행 25,253개, 원문·선택문 24쌍의 대조가 있다. 이들은 사람·독립 요청 수가 아니다. 24쌍은 대표성 있는 사용자 실험이 아니며, [평가 준비 적합 7개·보류 12개·범위 제외 5개](evaluations/enterprise-case-suitability-2026-11-21.md)의 구분을 함께 제시한다. 예를 들어 P22의 상태 표현이 덜 구체적으로 바뀐 사례를 통해 ‘자연스러운 표현인가’ 외에 ‘전달할 상태가 유지되는가’를 확인할 필요성을 설명할 수 있다. 실제 사용자의 곤란이나 설명 효과가 확인됐다는 주장은 하지 않는다.

**기능·시연·내부 처리를 묶는다.** 화면을 전부 소개한 뒤 기술을 따로 나열하기보다 아래 연결에 맞춰 필요한 장면과 도식을 배치한다. 각 묶음의 분량을 동일하게 맞추거나 발표 시간을 새로 확정하지 않는다.

| 보여줄 장면 | 함께 설명할 설계·기술 |
|---|---|
| 선택한 부분을 바로 교정하고 후보 3개 받기 | 확인창을 없앤 이유, 선택 범위 보관, 선택한 제공자 한 곳에 요청, 교정 전용 지침과 후보 수·응답 형식 검사 |
| 변경 표현을 눌러 해당 이유 읽기 | 전체 설명을 읽고 변경을 찾아야 했던 불편 → 표현별 연결로 개선한 과정. 코드의 문자열 비교, 별도 설명 요청, 변경 ID·인용 검사, 클릭 시 받은 설명 재사용 |
| 후보 적용·다시 교정하기 | 원문 선택 위치만 교체하는 처리, 적용 전 후보 1개 수정과 적용 후 3개 생성의 차이, 열린 비교·설명과 정상 결과 보존 |
| 실패와 남은 한계 확인 | [기술 설명 사례](#technical-story)의 문제 → 시도 → 확인 결과 → 미해결 범위. 자동 동작 검사·실제 모델 응답·사용자 효과를 구분 |

표현별 이유를 하나씩 확인하는 개선은 멘토링에서 긍정적으로 평가됐다는 전달을 받았다. 이를 설계 피드백으로 소개하고, 실제 사용자 판단 개선 수치로 바꾸지 않는다. 마무리는 **관찰한 불편 → 세운 가설 → 구현한 대응 → 확인한 동작과 남은 검증**으로 연결한다. 센틴스파이에 없는 기능에 대한 설명은 [기록한 조사 범위](research/서비스%20분석.md)에 한정하고, 발표자가 실제로 설명할 수 있는 말로 대본을 정리한다.

**성공·실패의 판단 기준과 실측 결과를 구분한다.** 후보 선택 분포와 설명 클릭률은 향후 가설 검증 지표의 예시다. 첫 후보 선택이 줄거나 클릭이 늘었다는 사실만으로 판단이 좋아졌다고 결론 내릴 수 없다. 비교 조건·분모·해석 기준·목표 수치는 미확정이며 [기존 측정 계약](교정%20설명%20평가%20기준.md#kpi-contract)과 실제 판단 정확성·부담을 함께 검토해야 한다. 행동 기록의 기본 비활성화와 사용자 효과 미측정 상태를 그대로 밝힌다. 시연에 사용할 문장은 사전에 확인하되, 해당 사례의 성공을 전체 품질로 일반화하거나 실패 기록을 제외하지 않는다. 기존 #22 기준을 낮추거나 종료한 장시간 품질 작업을 재개한 결정은 아니다.

## 핵심 흐름 확인·화면 설명 — 약 2분

아래 예문은 기업 데이터가 아닌 직접 작성한 문장이다.

```text
안녕하세요.
금요일까지 자료를 보내 주세여.
감사합니다.
```

| 순서 | 조작 | 확인·설명할 내용 |
|---|---|---|
| 1 | 세 줄을 원문 작업 공간에 붙여넣고 가운데 문장만 드래그 | 선택 글자 수와 근처 ‘교정하기’가 표시됨. 선택만으로 요청하지 않으며 앞뒤 문장은 대상에 포함되지 않음 |
| 2 | 근처 ‘교정하기’ 또는 상단 ‘교정 실행’ 클릭 | 확인 팝업 없이 바로 요청. 성공 결과는 후보 3개. ‘주세여’가 고쳐졌는지, 금요일까지라는 기한과 자료 요청이 유지되는지 확인 |
| 3 | 후보의 ‘원문 비교’ 펼치기 | 상단은 완성 문장, 비교 안은 전체 원문과 교정안을 위아래로 표시. 원문의 변경 표현은 취소선, 교정안의 변경 표현은 밑줄로 구분. 띄어쓰기는 주변 표현까지 함께 강조하며 문법·의미의 옳고 그름을 판정하는 표시는 아님 |
| 4 | ‘교정 이유’ 클릭 후 비교의 변경 표현 선택 | 표현별 자료가 있으면 대응하는 원문·교정안이 함께 강조되고 해당 이유를 하나씩 표시. 현재 순서·전체 개수와 이전·다음으로 탐색하며 추가 모델 호출은 없음. 설명이 화면 밖일 때 직접 표현을 선택하면 해당 이유로 이동. 내용이 짧으면 영역도 짧아지는지 확인. 표현별 자료가 없는 응답·과거 이력은 ‘전체 교정 이유’로 표시하며 임의로 나누지 않음 |
| 5 | 비교·설명을 접었다 다시 열기 | 같은 후보에서는 받은 설명과 선택한 변경 표현을 재사용. 이유가 실제 변경과 맞는지 확인하고, 읽지 않고도 적용 가능 |
| 6 | 사용할 후보의 ‘이 문장 적용’ 클릭 → 원문의 변경 위치 확인 → 다른 카드의 ‘이 후보로 바꾸기’ | 가운데 문장만 바뀌고 인사·맺음말은 유지. 적용 직후 바뀐 원문 범위를 보여주고 잠시 녹색으로 선택 강조하며, 긴 범위는 시작부터 보여줌([동작 기준](FEATURE_SPEC.md#applied-source-visibility)). 후보 3개·기존 비교·설명은 남고 적용한 카드 표시만 바뀜. 길이가 달라도 현재 적용 범위를 정확히 교체하며 비교·설명은 후보 생성 당시 원문 기준 |
| 7 | 오른쪽 패널의 ‘교정 이력’ 클릭 → 기록 펼치기 → 뒤로가기 | 당시 선택 원문·후보·받은 설명·적용 기록을 읽기 전용으로 확인. 뒤로가면 현재 후보·비교·설명 상태 유지. 새로고침 후에도 이력은 남지만 작성 중인 글 전체는 복원되지 않음. 조회는 모델을 호출하지 않음 |
| 8 | 적용한 카드의 ‘다시 교정하기’에서 요구 선택 → ‘교정 시작’ | 적용 전과 같은 크기·위치의 버튼에서 현재 문장으로 새 후보 3개를 요청. 대기·실패에는 기존 후보·비교·설명을 유지하고 성공 시 새 원문 기준으로 전환. 비교·이유 열림만 유지하며 열린 이유는 새 설명으로 이어지고 닫힌 이유는 자동 요청하지 않음. 원문 작업 공간은 새 후보를 적용하기 전까지 그대로 |
| 8-1 | 새 묶음의 후보를 적용하기 전에 후보 3에서 같은 재교정 조작 실행 | 이번에는 후보 3만 교체되고 후보 1·2는 유지. 열린 비교와 설명은 새 내용으로 연결되며 요구 선택 영역만 닫고 초기화. [적용 전/후 동작 기준](FEATURE_SPEC.md#rerun-entry-plan) 참고 |

넓은 화면에서 비교·이유를 펼치고 아래쪽 후보까지 내려가며 왼쪽 원문도 함께 확인한다. 너비 1,024px 이상·높이 600px 이상에서는 원문 패널 전체가 화면 위 16px에 유지되고 긴 원문은 입력란 안에서 스크롤한다. 적용한 범위가 이미 보이면 페이지를 이동하지 않고 해당 범위에 포커스·녹색 강조를 표시한다. 좁거나 낮은 화면에서는 패널 전체 고정을 해제하므로 같은 배치를 기대하지 않는다. 촬영 전 사용할 창 크기에서 [원문 패널 유지 기준](FEATURE_SPEC.md#sticky-source-workspace)을 확인하며, 이 화면 개선을 사용자 판단 효과의 검증 결과로 설명하지 않는다.

11/24 사용자 결정으로 최종 프로젝트의 기본 화면에서는 행동 기록 패널과 새 수집을 비활성화한다. 기존 ‘행동 기록 JSON/CSV 내보내기’ 단계는 시연 흐름에서 제외하고 교정·이유·선택 적용과 재교정·교정 이력만 확인한다. 과거 행동 기록의 구현·검증은 보존하며 사용자 효과 측정 완료로 설명하지 않는다. 필요할 때만 켜는 설정은 [기능명세](FEATURE_SPEC.md#activity-recording-default-off)를 따른다.

두 교정 버튼의 확인창은 11/23 사용자 요청에 따라 제거했다([#64](https://github.com/dhwjdgh1122/writing-demo/issues/64)·[직접 실행 검증](검증%20기록.md#direct-correction-entry-01)). 드래그 후 버튼 표시는 유지하며 버튼을 누를 때만 요청한다. [PR #26](https://github.com/dhwjdgh1122/writing-demo/pull/26)의 확인창과 아래 11/7 촬영 자료는 당시 화면의 기록이다.

표현별 이유 연결과 내용에 맞춘 높이는 [PR #69](https://github.com/dhwjdgh1122/writing-demo/pull/69)로 main에 반영했다. [실제 모델 연결·자동 검증·남은 품질 한계](검증%20기록.md#expression-linked-reasons-01)를 구분하며, 변경 표현을 찾아 읽기 쉬워진 것이 설명 내용의 정확성이나 사용자 판단 도움을 입증한 것은 아니다.

적용 후 후보 비교 유지와 현재 카드의 재교정 진입은 [PR #72](https://github.com/dhwjdgh1122/writing-demo/pull/72)로 반영했다. 재교정 뒤 자동 설명이 실패하면 정상 후보·다른 설명은 유지되고 수동 재시도를 제공한다. 실패한 요청을 자동 반복하거나 실사용 API 안정성이 해결됐다고 설명하지 않는다. [읽기 유지 검증](검증%20기록.md#rerun-reading-continuity-01)과 [11/24 재시도 회귀 2개](검증%20기록.md#explanation-retry-regression-20261124)는 주입 응답 검사다. #59의 최초 재시도 불가 현상·원인은 확인하지 못해 Issue는 열어 둔다.

설명할 멘트 예시:

## 기술 설명 흐름 — 약 3분

2026-11-20, main `b9fb2e7`에서 시작한 발표 준비안을 이후 main의 기능 변경에 맞춰 보완했다. 아래 시간은 계획 분량이며 실제 발표 시간이 아니다. 과거 실패 사례의 수치는 당시 실행 결과이고, 최신 표현별 설명 연결의 검증은 위 PR #69 기록과 구분한다. 11/11 제출 PPT와 아래 11/7 촬영 자료는 당시 기록으로 유지한다. 코드별 책임과 상세 흐름은 [구조 설계의 기술 흐름](ARCHITECTURE.md#technical-flow), 화면 표시 기준은 [DESIGN의 변경 표시와 설명](DESIGN.md#4-변경-표시와-설명)을 참고한다.

### 0:00~0:35 — 후보와 설명을 판단할 수 있게 연결하기

> 교정 후보가 나왔다고 내용까지 정확한 것은 아닙니다. 처음에는 선택한 제공자 한 곳에 한 번 요청해 후보 3개를 받습니다. 특정 후보에서 ‘다시 교정하기’를 실행하면 그 후보를 다듬은 1개만 받아 같은 자리에 교체합니다. 적용 후 재교정은 적용한 문장으로 새 후보 3개를 만듭니다. 화면은 선택 원문과 후보의 문자열 차이를 계산해 보여주며 후보 번호는 추천 순위가 아닙니다. ‘교정 이유’는 각 후보를 만든 요청의 원문·요구와 연결해 별도로 생성하고, 바뀌지 않은 후보의 이미 받은 설명은 유지합니다. 서버는 응답 형식과 후보 ID, 인용한 문자열을 검사하고 사용자는 비교와 설명을 참고해 선택합니다. 적용 위치는 모델이 아니라 화면이 기억한 선택 범위로 결정하며 중복 없는 생성·요구 충족을 보장하지는 않습니다.

문자열 비교의 밑줄·취소선은 실제 차이를 바탕으로 변경된 표현을 묶어 보여준다. 띄어쓰기처럼 작은 변화도 주변 표현과 함께 강조하므로 강조된 글자 모두가 바뀌었다는 뜻은 아니며, 의미 변화 판정도 아니다. 현재 표현별 설명은 서버가 같은 원문·후보에서 계산한 변경 묶음 ID에 모델의 설명을 연결하고 ID·인용을 검사한다. 화면은 연결된 이유를 전환하며, 표현 클릭마다 모델을 새로 부르지 않는다. 설명을 열지 않거나 설명이 실패해도 후보 비교·적용은 가능하다. 다음 세 사례는 이 연결에서 발견한 실패와 대응을 보여준다.

### 0:35~1:20 — 사례 1: 여러 문장 중 일부만 돌아온 후보

처음에는 여러 줄을 선택해도 각 후보가 선택문 전체를 담을 것으로 기대했다. 그러나 세 문장 입력에서 첫 문장만 남거나 나머지 문장만 합쳐진 후보가 관찰됐다. 전달 경로를 점검한 뒤 교정 지침에 줄바꿈·빈 줄·문장 순서 보존을 명시했다. 변경 후 해당 사례의 두 후보는 세 문장과 끝 줄바꿈을 유지했다. 이어 기존 사례 3개를 각 3회 요청한 제한 점검에서 **9/9 응답, 후보 13/13의 핵심 정보·줄 구조 보존**을 관찰했다. 이는 기존 실제 모델 실행 기록이며, 모든 입력의 누락을 자동으로 막거나 모든 표현을 교정했다는 뜻은 아니다. [누락 재현과 전달 경로 점검](검증%20기록.md#correction-coverage-01), [지침 전후 비교](검증%20기록.md#linebreak-prompt-01), [제한 반복 결과](검증%20기록.md#correction-stability-01).

### 1:20~2:00 — 사례 2: 설명 한 개의 오류로 정상 설명도 숨겨짐

후보의 `보내주세요`를 설명이 `보내 주세요`로 인용한 사례에서, 형식이 맞아도 설명 내용은 후보와 어긋날 수 있음을 확인했다. 공백까지 문자열을 대조하는 검사를 추가했지만, 당시에는 한 후보의 오류로 설명 묶음 전체가 차단됐다. 현재는 후보 ID의 대응을 먼저 확인한 뒤 개별 형식·인용 오류만 분리한다. 정상 설명은 보여주고 **‘실패한 설명 다시 시도’는 실패한 후보만 요청**하며, 재요청 중에도 정상 설명과 후보 적용을 유지한다. 기존 주입 응답 검사로 이 동작을 확인했고 해당 개선의 실제 모델 추가 호출은 **0회**였다. 인용 검사를 통과해도 설명의 의미가 정확하다는 보장은 없다. [공백 인용 사례](검증%20기록.md#space-01--오타-문장의-두-후보와-공백-인용-오류), [전체 차단이 관찰된 설명 평가](검증%20기록.md#explanation-eval-01), [후보별 실패 격리와 검증](검증%20기록.md#explanation-isolation-01).

### 2:00~2:35 — 사례 3: 정확한 여러 줄 인용도 거절된 경우

문자열 검사는 잘못된 설명 노출을 줄이려는 장치지만 검사 자체에도 오류가 있었다. 팀원이 전달한 정확한 여러 줄 인용에서 인용 사이의 조사 `가 `를 잘못 검사한 사례다. 닫힌 인용 구간 전체를 읽도록 경계를 수정한 뒤, 저장한 재현 데이터와 테스트 응답으로 해당 사례의 통과를 확인했다. 공백·줄바꿈 일치 기준은 유지하므로 `있었\n는데`를 `있었는데`로 인용한 차이는 계속 실패한다. 이 역시 실제 모델을 다시 호출한 결과가 아니며, 생략 인용 허용 정책이나 의미 정확성을 해결한 것은 아니다. [팀원 사례·재현 데이터·검증 범위](검증%20기록.md#explanation-isolation-01).

### 2:35~3:00 — 현재 반영 범위와 남은 질문

현재 main에는 위 보존 지침과 후보별 실패 처리·재시도·여러 줄 인용 경계 수정, PR #69의 표현별 설명 연결이 반영돼 있다. **과거 실험의 변경 근거 `references` 응답 형식·설명 프롬프트, 원문 비교 바로가기·숫자 표기 비교는 미병합 PR #34에 보존돼 있다.** main의 실제 diff ID 기반 `changes` 연결과 같은 구현으로 소개하지 않는다. #22의 조건 오해, 필수 정보·선택 기준 누락, 남은 단어 오용과 반복 평가 미실행 범위·실제 사용자 효과 검증은 미완료다. 동작 개선과 설명 품질 개선의 완료를 구분한다. [반영·제외 범위와 후속 과제](검증%20기록.md#explanation-isolation-01), [보존 PR #34](https://github.com/dhwjdgh1122/writing-demo/pull/34), [Issue #22](https://github.com/dhwjdgh1122/writing-demo/issues/22).

위 기술 설명은 기존 발표 준비 기록을 이어 보완한 내용이다. **11/22의 미병합 품질 개선·진단 기록은 [보존 PR #55](https://github.com/dhwjdgh1122/writing-demo/pull/55)**에 있으며 PR #23·#34는 이전 실험을 보존한다. 공백 변경 사실 안내와 명제 생성 진단은 main 기능으로 시연하지 않는다. 의미 중복·인용 재작성의 후속 설계·제한 진단까지 진행했으나 품질 기준을 충족하지 못했고, 사용자 결정으로 [기존 장시간 목표를 종료](검증%20기록.md#explanation-goal-closeout-01)했다. #22의 미해결 문제와 실제 사용자 효과 미검증을 설명하되 다음 실험이 확정된 것으로 발표하지 않는다. main·작업 브랜치·CI의 확인 시점별 차이는 [정합성 점검과 후속 반영](검증%20기록.md#project-integration-20261122)을 참고한다.

## 오류·경계 확인

- **후보 수 불일치·출력 중단:** 일반 생성/적용 후 재교정은 3개, 카드 재교정은 1개가 아니거나 출력이 잘리면 실패 안내를 확인한다. 자동 재시도·후보 채우기·복제 없이 원문과 선택 및 재교정 전 유효 결과를 유지해야 한다. 기존에 저장한 후보 1~3개의 이력은 그대로 조회할 수 있다.
- **후보별 설명 실패:** 정상 설명과 후보 비교·적용은 유지한다. ‘실패한 설명 다시 시도’는 실패한 후보의 설명만 요청한다. 전부 실패해도 후보는 적용할 수 있다. 인용 검사로 정상적인 설명이 거절될 수도 있으므로 실패를 숨기지 않고 기록한다.
- **설명 요청 전체 실패:** 통신·전체 응답 형식·후보 ID 대응 오류 등은 요청 실패로 안내하며 ‘설명 다시 시도’를 제공한다. 이미 받은 정상 설명이 있다면 유지한다. 자동 재시도하거나 교정 후보를 새로 생성하지 않는다.
- **선택 변경:** 결과가 나온 뒤 다른 문장을 선택하면 이전 후보와 설명이 닫혀야 한다.
- **원문 편집:** 요청 중 또는 결과가 나온 뒤 원문을 수정하면 이전 응답을 적용하면 안 된다.
- **길이·빈 선택:** 공백만 선택하거나 1,000자를 넘게 선택하면 실행이 막혀야 한다.
- **연결 실패:** 원문을 보존하고 오류를 안내해야 한다. 실패한 요청을 성공 화면으로 대체하지 않는다.

선택·적용·오래된 응답 처리·설명 실패 분기는 자동 테스트로도 확인했다. 실제 모델의 시간 초과나 설명 오류는 매번 같은 방식으로 재현된다고 보장하지 않는다.
