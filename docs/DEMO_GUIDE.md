# 시연 안내 — 교정·설명·선택 적용

> 목적: 팀원이 같은 순서로 핵심 흐름을 확인하고 시연 자료를 준비하도록 돕고, 실제 중간발표 방식을 기록한다. 실제 모델의 결과는 실행마다 달라질 수 있다. 아래 화면은 기록 당시의 실제 결과이며 재실행 시 동일한 결과를 보장하지 않는다.

## 발표 방식

**2026-11-11 실제 발표:** 심사위원에게 제출·공유된 PPT를 발표자가 화면 공유하며 중간발표를 진행했다. 웹 데모는 캡처한 실행 화면을 PPT에 삽입해 설명했으며, 발표 당일 실시간 시연이나 영상 촬영은 진행하지 않았다. 이 내용은 11/12 오정호의 전달을 기준으로 기록했다.

아래 예문·실행 절차·11/7 촬영 자료는 이후 팀원 점검과 시연 자료 준비에도 사용한다. 11/7 저장 자료 전체가 실제 제출 PPT에 사용됐다고 단정하지 않으며, 실제 캡처와 해당 실행의 결과를 연결해 설명한다.

### 실제 제출본과 발표 대본

- [중간평가 발표자료 — 4팀](demo/2026-11-11/북엔드_중간평가_발표자료_4팀.pptx): 11/12 오정호가 실제 발표에 사용했다고 확인한 파일이다. 전달된 원본 파일명은 `북엔드_중간평가_발표자료_4팀 (1).pptx`이며, 저장소 사본은 파일명만 정리했다. PPT 내용과 발표자 메모는 수정하지 않았다.
- 총 15장으로 본 발표 1~10장, 별도 이미지 슬라이드 11장, 참고자료 12~15장이다. 본 발표 슬라이드별 대본은 **PowerPoint의 메모(발표자 노트)**에서 확인한다. 참고자료 메모에는 본 발표에서 설명하지 않는다는 안내가 있다.
- 본 발표 흐름: 서비스 소개·기업 방향 → 기존 사용 관찰·판단 문제 → 선택형 설명 가설 → 웹 데모 구현 → 검증 방향 → 다음 단계. 메모의 0:00~10:00 표기는 계획한 분량이며 실제 발표 시간을 계측한 기록이 아니다.
- 제출본의 검증 계획은 설명 유무에 따른 의미 변화 인지, 설명 정확성, 판단 시간·부담을 비교하는 **방향 초안**이다. 참여자 수·구체적 평가 방식·목표 수치는 미확정이며, 발표 대본을 새 요구사항이나 사용자 효과 검증 결과로 간주하지 않는다.

## 실행 준비

[README](../README.md#실제-ai-연결)에 따라 저장소 루트에서 설치·실행하고 선택한 제공자의 API를 설정한다. Gemini 무료 등급 또는 엘리스 Serverless의 키·모델 접근과 사용 한도를 확인한다. 제공자·키·모델을 변경한 뒤에는 서버를 재시작한다. 키 없는 환경에서는 입력·선택과 미설정 안내까지만 확인할 수 있다.

화면을 새로 준비하거나 직접 검증할 때 서버를 실행하고 브라우저의 화면 배율과 네트워크를 확인한다. 페이지 새로고침 시 입력은 사라진다. 발표자료에는 아래 저장 화면의 촬영 시점과 실제 결과를 표시한다. 발표 전에는 PPT/PDF의 글자·이미지가 잘 보이는지와 설명 순서를 확인한다.

## 핵심 흐름 확인·화면 설명 — 약 2분

아래 예문은 기업 데이터가 아닌 직접 작성한 문장이다.

```text
안녕하세요.
금요일까지 자료를 보내 주세여.
감사합니다.
```

| 순서 | 조작 | 확인·설명할 내용 |
|---|---|---|
| 1 | 세 줄을 원문 작업 공간에 붙여넣고 가운데 문장만 드래그 | 선택만으로 팝업이 뜨지 않음. 근처 ‘교정하기’ 또는 상단 ‘교정 실행’에서 읽기 전용 원문을 확인하며 앞뒤 문장은 대상에 포함되지 않음 |
| 2 | 확인창에서 ‘교정 시작’ 클릭 | 후보 수는 1~3개. ‘주세여’가 고쳐졌는지, 금요일까지라는 기한과 자료 요청이 유지되는지 확인 |
| 3 | 후보의 ‘원문 비교’ 펼치기 | 밑줄·취소선은 실제 문자열 차이. 교체도 삭제와 추가로 표현되므로 ‘삭제된 내용 있음’이 의미 누락을 뜻하는 것은 아님 |
| 4 | ‘교정 이유 보기’ 클릭 | 해당 원문과 후보의 실제 변경을 설명하는지 확인. 설명을 읽지 않고도 적용 가능 |
| 5 | 설명을 접었다 다시 열기 | 같은 결과에서는 받은 설명을 재사용 |
| 6 | 사용할 후보의 ‘이 문장 적용’ 클릭 | 가운데 문장만 바뀌고 인사·맺음말은 유지. 이전 후보와 설명은 닫힘 |
| 7 | 작업 공간 아래 ‘교정 이력’ 펼치기 | 당시 선택 원문·후보·받은 설명·적용 기록을 읽기 전용으로 확인. 새로고침 후에도 이력은 남지만 작성 중인 글 전체는 복원되지 않음. 조회는 모델을 호출하지 않음 |
| 8 | 현재 결과 또는 적용 직후 ‘다시 다듬기’의 요구를 선택하고 실행 | 적용 전/후의 기준 원문이 다름을 확인. 요구를 새 생성에 전달하며 결과를 비교한 뒤 적용. 요구 미선택도 가능하며 요구 충족은 직접 확인 |
| 9 | ‘행동 기록’에서 JSON/CSV 내보내기 | 기본은 참여자 코드·요구·동작·오류만 포함. 문장 포함은 별도 선택이며 적용률을 만족·설명 효과로 설명하지 않음 |

위 확인창 흐름은 11/18 #4의 개선 내용이다. 변경 이력과 병합 근거는 [PR #26](https://github.com/dhwjdgh1122/writing-demo/pull/26)에서 확인한다. 긴 선택 원문은 확인창 본문에서 스크롤하며, 취소하면 선택과 화면 위치를 유지한다. 아래 11/7 촬영 자료는 당시 화면으로 보존한다.

설명할 멘트 예시:

> 교정 결과와 바뀐 부분을 먼저 보여줍니다. 이유가 궁금할 때 설명을 열어 후보를 판단하는 데 참고할 수 있습니다. 설명도 AI 생성 결과이므로 실제 차이와 맞는지 확인해야 합니다. 선택한 후보는 원문의 해당 위치에만 적용됩니다.

## 기술 설명 흐름 — 약 3분

2026-11-20, main `b9fb2e7`의 구현과 기존 기록을 연결한 발표 준비안이다. 아래 시간은 계획 분량이며 실제 발표 시간이나 새 모델 평가 결과가 아니다. 문서 작성 과정에서 새 모델 호출·로컬 제품 테스트는 실행하지 않았으며, 이번 PR의 자동 검사 결과는 PR에서 별도 확인한다. 11/11 제출 PPT와 아래 11/7 촬영 자료는 당시 기록으로 유지한다. 코드별 책임과 상세 흐름은 [구조 설계의 기술 흐름](ARCHITECTURE.md#technical-flow), 화면 표시 기준은 [DESIGN의 변경 표시와 설명](DESIGN.md#4-변경-표시와-설명)을 참고한다.

### 0:00~0:35 — 후보와 설명을 판단할 수 있게 연결하기

> 교정 후보가 나왔다고 내용까지 정확한 것은 아닙니다. 일반 교정은 선택한 문장으로 후보 1~3개를 받고, 화면은 원문과 후보의 문자열 차이를 계산해 보여줍니다. ‘교정 이유’를 열 때는 같은 원문과 현재 후보로 설명을 따로 요청합니다. 요구를 선택한 재교정은 이전 선택 원문·후보도 함께 전달합니다. 서버는 응답 형식과 후보 ID, 인용한 문자열을 검사하고, 사용자는 비교와 설명을 참고해 후보를 선택합니다. 적용 위치는 모델이 아니라 화면이 기억한 선택 범위로 결정합니다.

문자열 비교의 밑줄·취소선은 실제 글자 차이이며, 의미 변화 판정은 아니다. 설명을 열지 않거나 설명이 실패해도 후보 비교·적용은 가능하다. 다음 세 사례는 이 연결에서 발견한 실패와 대응을 보여준다.

### 0:35~1:20 — 사례 1: 여러 문장 중 일부만 돌아온 후보

처음에는 여러 줄을 선택해도 각 후보가 선택문 전체를 담을 것으로 기대했다. 그러나 세 문장 입력에서 첫 문장만 남거나 나머지 문장만 합쳐진 후보가 관찰됐다. 전달 경로를 점검한 뒤 교정 지침에 줄바꿈·빈 줄·문장 순서 보존을 명시했다. 변경 후 해당 사례의 두 후보는 세 문장과 끝 줄바꿈을 유지했다. 이어 기존 사례 3개를 각 3회 요청한 제한 점검에서 **9/9 응답, 후보 13/13의 핵심 정보·줄 구조 보존**을 관찰했다. 이는 기존 실제 모델 실행 기록이며, 모든 입력의 누락을 자동으로 막거나 모든 표현을 교정했다는 뜻은 아니다. [누락 재현과 전달 경로 점검](검증%20기록.md#correction-coverage-01), [지침 전후 비교](검증%20기록.md#linebreak-prompt-01), [제한 반복 결과](검증%20기록.md#correction-stability-01).

### 1:20~2:00 — 사례 2: 설명 한 개의 오류로 정상 설명도 숨겨짐

후보의 `보내주세요`를 설명이 `보내 주세요`로 인용한 사례에서, 형식이 맞아도 설명 내용은 후보와 어긋날 수 있음을 확인했다. 공백까지 문자열을 대조하는 검사를 추가했지만, 당시에는 한 후보의 오류로 설명 묶음 전체가 차단됐다. 현재는 후보 ID의 대응을 먼저 확인한 뒤 개별 형식·인용 오류만 분리한다. 정상 설명은 보여주고 **‘실패한 설명 다시 시도’는 실패한 후보만 요청**하며, 재요청 중에도 정상 설명과 후보 적용을 유지한다. 기존 주입 응답 검사로 이 동작을 확인했고 해당 개선의 실제 모델 추가 호출은 **0회**였다. 인용 검사를 통과해도 설명의 의미가 정확하다는 보장은 없다. [공백 인용 사례](검증%20기록.md#space-01--오타-문장의-두-후보와-공백-인용-오류), [전체 차단이 관찰된 설명 평가](검증%20기록.md#explanation-eval-01), [후보별 실패 격리와 검증](검증%20기록.md#explanation-isolation-01).

### 2:00~2:35 — 사례 3: 정확한 여러 줄 인용도 거절된 경우

문자열 검사는 잘못된 설명 노출을 줄이려는 장치지만 검사 자체에도 오류가 있었다. 팀원이 전달한 정확한 여러 줄 인용에서 인용 사이의 조사 `가 `를 잘못 검사한 사례다. 닫힌 인용 구간 전체를 읽도록 경계를 수정한 뒤, 저장한 재현 데이터와 테스트 응답으로 해당 사례의 통과를 확인했다. 공백·줄바꿈 일치 기준은 유지하므로 `있었\n는데`를 `있었는데`로 인용한 차이는 계속 실패한다. 이 역시 실제 모델을 다시 호출한 결과가 아니며, 생략 인용 허용 정책이나 의미 정확성을 해결한 것은 아니다. [팀원 사례·재현 데이터·검증 범위](검증%20기록.md#explanation-isolation-01).

### 2:35~3:00 — 현재 반영 범위와 남은 질문

현재 main에는 위 보존 지침과 후보별 실패 처리·재시도·여러 줄 인용 경계 수정이 반영돼 있다. **변경 근거 `references`와 설명문을 분리하는 새 모델 응답 형식·연결된 설명 프롬프트, 원문 비교 바로가기·숫자 표기 비교는 Draft PR #34에 남아 있으며 main 기능으로 소개하지 않는다.** #22의 조건 오해, 필수 정보·선택 기준 누락, 남은 단어 오용과 반복 평가 미실행 범위·실제 사용자 효과 검증은 미완료다. 동작 개선과 설명 품질 개선의 완료를 구분한다. [반영·제외 범위와 후속 과제](검증%20기록.md#explanation-isolation-01), [Draft PR #34](https://github.com/dhwjdgh1122/writing-demo/pull/34), [Issue #22](https://github.com/dhwjdgh1122/writing-demo/issues/22).

## 오류·경계 확인

- **후보별 설명 실패:** 정상 설명과 후보 비교·적용은 유지한다. ‘실패한 설명 다시 시도’는 실패한 후보의 설명만 요청한다. 전부 실패해도 후보는 적용할 수 있다. 인용 검사로 정상적인 설명이 거절될 수도 있으므로 실패를 숨기지 않고 기록한다.
- **설명 요청 전체 실패:** 통신·전체 응답 형식·후보 ID 대응 오류 등은 요청 실패로 안내하며 ‘설명 다시 시도’를 제공한다. 이미 받은 정상 설명이 있다면 유지한다. 자동 재시도하거나 교정 후보를 새로 생성하지 않는다.
- **선택 변경:** 결과가 나온 뒤 다른 문장을 선택하면 이전 후보와 설명이 닫혀야 한다.
- **원문 편집:** 요청 중 또는 결과가 나온 뒤 원문을 수정하면 이전 응답을 적용하면 안 된다.
- **길이·빈 선택:** 공백만 선택하거나 1,000자를 넘게 선택하면 실행이 막혀야 한다.
- **연결 실패:** 원문을 보존하고 오류를 안내해야 한다. 실패한 요청을 성공 화면으로 대체하지 않는다.

선택·적용·오래된 응답 처리·설명 실패 분기는 자동 테스트로도 확인했다. 실제 모델의 시간 초과나 설명 오류는 매번 같은 방식으로 재현된다고 보장하지 않는다.
