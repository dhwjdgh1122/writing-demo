# 시연 안내 — 교정·설명·선택 적용

> 목적: 팀원이 같은 순서로 핵심 흐름을 확인하고 시연 자료를 준비하도록 돕고, 실제 중간발표 방식을 기록한다. 실제 모델의 결과는 실행마다 달라질 수 있다. 아래 화면은 기록 당시의 실제 결과이며 재실행 시 동일한 결과를 보장하지 않는다.

## 발표 방식

**2026-11-11 실제 발표:** 심사위원에게 제출·공유된 PPT를 발표자가 화면 공유하며 중간발표를 진행했다. 웹 데모는 캡처한 실행 화면을 PPT에 삽입해 설명했으며, 발표 당일 실시간 시연이나 영상 촬영은 진행하지 않았다. 이 내용은 11/12 오정호의 전달을 기준으로 기록했다.

아래 예문·실행 절차·11/7 촬영 자료는 이후 팀원 점검과 시연 자료 준비에도 사용한다. 11/7 저장 자료 전체가 실제 제출 PPT에 사용됐다고 단정하지 않으며, 실제 캡처와 해당 실행의 결과를 연결해 설명한다.

### 실제 제출본과 발표 대본

- [중간평가 발표자료 — 4팀](demo/2026-11-11/북엔드_중간평가_발표자료_4팀.pptx): 11/12 오정호가 실제 발표에 사용했다고 확인한 파일이다. 전달된 원본 파일명은 `북엔드_중간평가_발표자료_4팀 (1).pptx`이며, 저장소 사본은 파일명만 정리했다. PPT 내용과 발표자 메모는 수정하지 않았다.
- 총 15장으로 본 발표 1~10장, 별도 이미지 슬라이드 11장, 참고자료 12~15장이다. 본 발표 슬라이드별 대본은 **PowerPoint의 메모(발표자 노트)**에서 확인한다. 참고자료 메모에는 본 발표에서 설명하지 않는다는 안내가 있다.
- 본 발표 흐름: 서비스 소개·기업 방향 → 기존 사용 관찰·판단 문제 → 선택형 설명 가설 → 웹 데모 구현 → 검증 방향 → 다음 단계. 메모의 0:00~10:00 표기는 계획한 분량이며 실제 발표 시간을 계측한 기록이 아니다.
- 제출본의 검증 계획은 설명 유무에 따른 의미 변화 인지, 설명 정확성, 판단 시간·부담을 비교하는 **방향 초안**이다. 참여자 수·구체적 평가 방식·목표 수치는 미확정이며, 발표 대본을 새 요구사항이나 사용자 효과 검증 결과로 간주하지 않는다.

## 실행 준비

[README](../README.md#실제-ai-연결)에 따라 저장소 루트에서 설치·실행하고 선택한 제공자의 API를 설정한다. Gemini 무료 등급 또는 엘리스 Serverless의 키·모델 접근과 사용 한도를 확인한다. 제공자·키·모델을 변경한 뒤에는 서버를 재시작한다. 키 없는 환경에서는 입력·선택과 미설정 안내까지만 확인할 수 있다.

화면을 새로 준비하거나 직접 검증할 때 서버를 실행하고 브라우저의 화면 배율과 네트워크를 확인한다. 페이지 새로고침 시 입력은 사라진다. 발표자료에는 아래 저장 화면의 촬영 시점과 실제 결과를 표시한다. 발표 전에는 PPT/PDF의 글자·이미지가 잘 보이는지와 설명 순서를 확인한다.

## 핵심 흐름 확인·화면 설명 — 약 2분

아래 예문은 기업 데이터가 아닌 직접 작성한 문장이다.

```text
안녕하세요.
금요일까지 자료를 보내 주세여.
감사합니다.
```

| 순서 | 조작 | 확인·설명할 내용 |
|---|---|---|
| 1 | 세 줄을 원문 작업 공간에 붙여넣고 가운데 문장만 드래그 | 선택한 문장만 오른쪽에 표시되고 앞뒤 문장은 교정 대상에 포함되지 않음 |
| 2 | ‘교정 실행’ 클릭 | 후보 수는 1~3개. ‘주세여’가 고쳐졌는지, 금요일까지라는 기한과 자료 요청이 유지되는지 확인 |
| 3 | 후보의 ‘원문 비교’ 펼치기 | 밑줄·취소선은 실제 문자열 차이. 교체도 삭제와 추가로 표현되므로 ‘삭제된 내용 있음’이 의미 누락을 뜻하는 것은 아님 |
| 4 | ‘교정 이유 보기’ 클릭 | 해당 원문과 후보의 실제 변경을 설명하는지 확인. 설명을 읽지 않고도 적용 가능 |
| 5 | 설명을 접었다 다시 열기 | 같은 결과에서는 받은 설명을 재사용 |
| 6 | 사용할 후보의 ‘이 문장 적용’ 클릭 | 가운데 문장만 바뀌고 인사·맺음말은 유지. 이전 후보와 설명은 닫힘 |

설명할 멘트 예시:

> 교정 결과와 바뀐 부분을 먼저 보여줍니다. 이유가 궁금할 때 설명을 열어 후보를 판단하는 데 참고할 수 있습니다. 설명도 AI 생성 결과이므로 실제 차이와 맞는지 확인해야 합니다. 선택한 후보는 원문의 해당 위치에만 적용됩니다.

## 추가 확인용 예문

아래는 앞으로 확인할 사례이며, 이번에 실제 AI로 전부 실행한 결과가 아니다. 후보 개수나 특정 문구를 정답으로 고정하지 않고 실제 출력과 기준을 비교한다.

| 목적 | 원문 | 확인 기준 |
|---|---|---|
| 오타·금액 관련 단어·숫자 | 참가자 8명중 2명은 등록비를 아직 결재하지 않앗습니다. | 8명·2명 유지, 오타·띄어쓰기 수정, 등록비를 내는 문맥의 ‘결제’ 검토. 남은 오류를 설명이 정확하게 구분하는지 |
| 조건·기한·미확정 표현 | 담당자가 승인한 경우에만 화요일까지 자료를 보낼 예정입니다. 발송은 아직 확정되지 않았슴니다. | 승인 조건·화요일 기한·미확정 상태 유지. 오타 외의 의미 변화가 생기면 설명이 짚는지 |
| 원문과 같은 결과 | 금요일까지 자료를 보내 주세요. | 변경이 없을 수 있음. 동일 후보라면 변경 없음 안내와 적용 비활성화, 없는 변경을 설명하지 않음 |
| 반복 문장의 위치 | 첫째. 자료를 보내 주세여. 둘째. 자료를 보내 주세여. 끝. | 두 번째 요청 문장만 선택·적용했을 때 첫 번째 문장이 유지되는지 |

## 오류·경계 확인

- **설명 실패:** 후보는 유지되고 적용할 수 있어야 한다. ‘설명 다시 시도’는 설명만 요청한다. 인용 검사로 정상적인 설명이 거절될 수도 있으므로 실패를 숨기지 않고 기록한다.
- **선택 변경:** 결과가 나온 뒤 다른 문장을 선택하면 이전 후보와 설명이 닫혀야 한다.
- **원문 편집:** 요청 중 또는 결과가 나온 뒤 원문을 수정하면 이전 응답을 적용하면 안 된다.
- **길이·빈 선택:** 공백만 선택하거나 1,000자를 넘게 선택하면 실행이 막혀야 한다.
- **연결 실패:** 원문을 보존하고 오류를 안내해야 한다. 실패한 요청을 성공 화면으로 대체하지 않는다.

선택·적용·오래된 응답 처리·설명 실패 분기는 자동 테스트로도 확인했다. 실제 모델의 시간 초과나 설명 오류는 매번 같은 방식으로 재현된다고 보장하지 않는다.

## 팀원이 남길 결과

환경(OS·Node 버전), 입력 원문, 선택 범위, 실제 후보·설명, 조작 순서, 기대와 다른 점을 함께 기록한다. API 키는 포함하지 않는다. 결과는 [검증 기록](검증%20기록.md)에 남기고, 담당과 후속 작업은 [TASKS](TASKS.md)의 관리 안내를 따른다. 보드 운영 전에는 TASKS에, 운영 후에는 해당 Issue와 Projects에 연결한다. 전달받은 결과와 직접 재현한 결과는 구분한다.
