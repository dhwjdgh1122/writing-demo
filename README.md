# 문장 교정·설명 웹 데모

> 선택한 문장의 교정 후보와 변경 부분을 보여주고, 필요한 경우 설명을 열어 비교·선택하도록 돕는 독립 웹 데모입니다. 팀원은 이 문서에서 프로젝트의 전체 흐름을 파악하고, 필요한 문서와 작업으로 이동할 수 있습니다.

센틴스파이 데스크톱 앱의 화면·사용 흐름을 참고해 구현했습니다. 입력·선택·교정·적용은 웹페이지 안에서 동작합니다. 설치형 데스크톱 앱이나 센틴스파이의 실제 교정 API에 연결된 서비스는 아닙니다.

기본 교정·후보 비교·적용과 버튼형 설명 기능을 구현했습니다. 개인 환경에서 실제 Gemini 호출을 확인했지만, 교정·설명 품질 전반과 사용자 효과를 검증한 것은 아닙니다. 작업 관리 안내와 보드 준비 중의 상태는 [TASKS](docs/TASKS.md), 실제 확인 근거는 [검증 기록](docs/검증%20기록.md)을 참고합니다.

## 팀원이 먼저 확인할 내용

사용자가 후보의 표현 차이·의미 변화를 이해하고 의도에 맞는 문장을 선택하도록 돕는 것이 목표입니다. 설명은 필요할 때만 열며, 그 효과가 입증된 단계는 아닙니다.

오정호가 논의한 방향을 실제 화면으로 확인하고 구현 가능성·어려운 부분을 파악하기 위해 먼저 웹 시제품을 만들었습니다. 이를 바탕으로 팀이 개선 범위와 작업을 함께 정합니다.

| 확인할 내용 | 읽을 문서 |
|---|---|
| 무엇을 왜 만드는지·현재 범위 | [PRD](docs/PRD.md) · [프로젝트 선정 근거](docs/research/프로젝트%20선정%20근거.md) |
| 화면에서 어떻게 사용하는지 | 아래 [핵심 흐름](#핵심-흐름-확인) · [시연 안내](docs/DEMO_GUIDE.md) |
| 무엇이 확인됐고 어떤 문제가 남았는지 | [검증 기록](docs/검증%20기록.md) · [사용자 피드백](docs/사용자%20피드백.md) |
| 지금 함께 할 일·일정 | [TASKS](docs/TASKS.md) |
| 수정하고 함께 합치는 방법 | [CONTRIBUTING](CONTRIBUTING.md) |

프로젝트의 최신 정보는 이 저장소에서 관리합니다. 팀원은 별도 전달본이나 상위 개인 자료를 받을 필요 없이 관련 문서를 직접 확인합니다. 중요 변경은 관련 문서·Issue·PR 링크로 공유하고, 수정 사실만으로 팀원 열람이나 합의를 완료로 간주하지 않습니다.

## 처음 실행하기

확인 환경은 **Windows, Node.js 20.12.2, npm 10.5.0**입니다. Node.js와 npm이 설치되어 있어야 합니다. 다른 운영체제의 설치·실행은 별도로 확인해야 합니다.

1. 내려받은 저장소에서 `package.json`이 있는 폴더를 편집기로 열고 터미널을 엽니다. 상위 개인 자료 폴더는 필요하지 않습니다.
2. PowerShell에서 아래 명령을 순서대로 실행합니다.

```powershell
node --version
npm.cmd --version
npm.cmd ci
npm.cmd run dev
```

3. 터미널에 표시된 **http://127.0.0.1:5173**을 브라우저에서 엽니다. 화면과 API 서버가 함께 실행됩니다.
4. 종료하려면 실행 중인 터미널에서 `Ctrl+C`를 누릅니다. 설치가 끝난 다음부터는 `npm.cmd run dev`만 실행하면 됩니다.

`npm.cmd ci`는 잠금 파일에 맞춰 의존성을 설치합니다. macOS·Linux 터미널에서는 `npm.cmd` 대신 `npm`을 사용합니다. 아래 경로와 명령은 모두 저장소 루트 기준입니다.

### API 키 없이 먼저 확인하기

`.env`가 없어도 서버와 화면을 실행할 수 있습니다. 원문 입력·드래그·키보드 선택과 선택 문장 표시를 확인하세요. ‘교정 실행’을 누르면 AI 연결 설정이 필요하다는 안내가 나오며 원문은 유지됩니다. 이 상태에서는 교정 후보와 설명이 생성되지 않습니다.

다른 위치를 선택하거나 원문을 수정하면 이전 결과와 진행 중 요청은 무효화됩니다. 페이지를 새로고침하면 입력과 결과가 사라지므로 필요한 내용은 별도로 보관하세요.

## 실제 AI 연결

서버의 `LLM_PROVIDER`로 제공자를 선택합니다. 웹 화면에 사용자용 모델 선택 메뉴를 추가한 것은 아닙니다. Gemini 연결은 유지하며 엘리스 Serverless의 GPT-4o mini 연결을 선택적으로 시험할 수 있습니다. 두 제공자를 동시에 호출하거나 실패 시 자동 전환하지 않습니다.

### 기존 Gemini 연결

1. [Google AI Studio](https://aistudio.google.com/apikey)에서 테스트용 프로젝트와 API 키를 준비합니다. **프로젝트가 Free Tier인지 확인하고 결제 계정을 연결하거나 유료 등급으로 전환하지 마세요.** 이미 결제가 연결된 프로젝트의 키를 사용하지 않습니다. 무료 구간을 사용할 수 없다면 설정 단계에서 멈추고 팀에 알려주세요.
2. 이 폴더의 `.env.example`을 `.env`라는 이름으로 복사합니다. 기존 `.env`가 있으면 덮어쓰지 말고 직접 편집하세요.
3. `.env`의 `GEMINI_API_KEY=` 뒤에 발급받은 키를 **로컬에서만** 입력하세요. 키를 채팅·공유 문서·화면 코드에 넣지 마세요. `LLM_PROVIDER=gemini`는 유지합니다.
4. `GEMINI_MODEL`의 초기 예시는 `gemini-3.5-flash-lite`입니다. 개인 무료 등급 프로젝트에서 호출을 확인했으며, **본인 프로젝트의 실제 사용 가능 모델·한도도 확인해야 합니다.** 모델명은 이 설정에서 바꿀 수 있습니다. 지원되지 않으면 다른 모델로 자동 전환하지 않습니다.
5. 실행 중인 서버를 `Ctrl+C`로 종료하고 `npm.cmd run dev`로 다시 시작합니다. 환경변수는 시작 시 읽으므로 키·모델 변경 후 재시작해야 합니다. 시스템 환경변수가 이미 있으면 `.env`보다 우선합니다.
6. 직접 작성한 예문으로 실행합니다. 예: `금요일까지 자료를 보내 주세여.` 후보가 나오면 변경 표시와 선택 범위 적용을 확인하세요. 날짜·숫자·조건이 유지되는지도 살펴보세요.

서버는 시작·페이지 열기·텍스트 선택만으로 모델을 호출하지 않습니다. ‘교정 실행’ 한 번에 요청 한 번, ‘교정 이유’ 최초 열기에 설명 요청 한 번이며 자동 재시도·다른 모델 대체·유료 전환 기능은 없습니다. 응답 한 번에 후보 1~3개를 요청하며 출력 상한은 Gemini 8,192토큰, 엘리스 GPT-4o mini 2,000토큰입니다. 엘리스의 비스트리밍 요청 제한에 맞춘 값이며, 긴 입력·복수 후보 출력이 잘리면 불완전한 결과를 적용하지 않고 오류로 처리합니다. 서버는 45초 후 요청을 중단하지만 공급자 측 사용량까지 취소되는 것은 보장하지 않습니다.

짧은 교정의 지연을 줄이기 위해 Gemini 3 계열에는 `thinkingLevel: LOW`를 지정합니다. 이전 계열에는 이 필드를 보내지 않습니다. 이 설정이 일시적인 공급자 장애나 대기를 해결한다고 보장할 수는 없으며, 실제 교정 품질도 별도로 확인해야 합니다.

**무료 여부는 Google 프로젝트의 요금제가 결정합니다. 이 코드나 API 키 문자열만으로 무료 등급을 판별·강제할 수는 없습니다.** 사용량 제한(429)이 오면 원문을 유지하고 안내합니다. Google AI Studio에서 한도를 확인하고 기다렸다가 수동으로 재시도하세요. 무료 구간의 입력·응답은 제품 개선에 사용될 수 있으므로 처음에는 직접 만든 예문으로 시험하세요. [공식 결제 안내](https://ai.google.dev/gemini-api/docs/billing), [요금·데이터 이용 안내](https://ai.google.dev/gemini-api/docs/pricing).

### 엘리스 GPT-4o mini 연결 시험

1. 엘리스 AI Cloud에서 Serverless 키를 발급하고 선택한 모델의 API URL을 확인합니다. API 키는 Google 키와 다릅니다. 교육 지원 크레딧·한도·이용 기간은 별도로 확인하며, 키 발급만으로 무료 사용이 보장되지는 않습니다.
2. 기존 `.env`의 Gemini 값은 보존하고 아래 항목을 추가합니다. `ELICE_API_KEY`에는 본인의 키를 로컬에서만 입력합니다. 예시의 모델명·URL은 본인 계정의 모델 페이지와 일치하는지 확인하세요.

```dotenv
ELICE_API_KEY=
ELICE_MODEL=gpt-4o-mini
ELICE_BASE_URL=https://mlapi.run/40cc17ae-a89b-4f12-a7d6-13293180fc87
```

`ELICE_BASE_URL`은 모델 URL 또는 그 뒤에 `/v1`을 붙인 주소입니다. `/chat/completions`는 코드에서 붙이므로 설정에 넣지 않습니다. 현재 어댑터는 HTTPS의 `mlapi.run` 모델 UUID 주소만 허용합니다.

3. 기존 서버를 Gemini로 유지한 채 연결만 점검하려면 저장소 루트에서 다음 명령을 실행합니다.

```powershell
node --import tsx scripts/check-elice.mjs
```

이 명령은 **실제 엘리스 API에 교정 1회·설명 1회, 최대 2회 생성 요청**을 보내므로 사용량이 발생할 수 있습니다. 직접 작성한 고정 예문을 사용하며 앱의 HTTP 응답 검증·설명 인용 검사까지 거칩니다. 실패하면 다음 단계로 진행하지 않고 중단하며 자동 재시도하지 않습니다. `.env`의 `LLM_PROVIDER`와 실행 중인 서버 설정은 바꾸지 않습니다. 실제 확인 결과는 [ELICE-01 연결 시험 기록](docs/검증%20기록.md#elice-01)을 따릅니다.

4. 웹 데모에서도 엘리스를 사용하려면 `.env`의 기존 `LLM_PROVIDER` 한 줄을 `LLM_PROVIDER=elice`로 바꾸고 서버를 재시작합니다. Gemini로 돌아갈 때는 `LLM_PROVIDER=gemini`로 바꾸고 재시작합니다. 기존 키·연결 코드를 삭제하거나 주석 처리할 필요가 없습니다.

모델 응답의 JSON 형식·후보 수·길이·설명 ID를 검사하지만 의미 보존이나 설명 정확성을 보장하지는 않습니다. 기존 설명 평가 도구 `scripts/evaluate-explanations.mjs`는 Gemini 전용이며, 이번 연결 시험 명령과 구분합니다. [엘리스 키 관리 안내](https://help.elice.io/help/docs/elicecloud/ml-api/api-key)

`/api/health`의 `modelConfigured: true`와 화면의 ‘AI 설정 확인됨’은 설정이 있다는 의미이며 실제 인증·무료 등급·교정 성공을 확인한 표시는 아닙니다.

### 오류가 나올 때

| 안내 | 확인할 것 |
|---|---|
| AI 연결 설정 필요 | `.env`의 제공자·키·모델명과 서버 재시작 여부 |
| API 키·모델명·접근 권한 확인 | 선택한 제공자의 키·모델·URL·요청 옵션·접근 권한 확인; 결제 활성화로 해결하지 않음 |
| 사용량 또는 요청 횟수 제한 | 선택한 제공자의 한도·잔여 크레딧을 확인한 뒤 수동 재시도 |
| 결과를 제공하지 않음 | 입력 문장 확인; 임의 후보로 대체하지 않음 |
| 완전한 결과를 받지 못함·시간 초과 | 잠시 후 재시도; 원문은 유지됨 |
| 원문·교정안과 맞지 않는 인용 | 설명의 인용 검사에서 불일치 발견. 후보 적용은 가능하며 ‘설명 다시 시도’로 설명만 다시 요청 |
| AI 서비스가 일시적으로 요청을 처리하지 못함 | 공급자 측 오류 응답. 잠시 기다린 뒤 수동 재시도; 키 재발급·결제 전환으로 해결된다고 가정하지 않음 |

## 핵심 흐름 확인

원문 선택 → 교정 실행 → 후보 비교 → 필요할 때 교정 이유 보기 → 이 문장 적용 순서로 확인합니다. 후보는 응답에 따라 1~3개이며, 같은 문장도 실행마다 결과가 달라질 수 있습니다.

- 설명은 처음 열 때 요청하고, 같은 결과에서 닫았다 다시 열면 받은 설명을 재사용합니다.
- 설명이 실패해도 후보 적용은 가능합니다. ‘설명 다시 시도’는 설명만 새로 요청합니다.
- 후보 적용은 선택한 위치만 바꿉니다. 적용 후에는 이전 후보와 설명을 닫습니다.
- 같은 선택에서 ‘교정 실행’을 다시 누를 수 있습니다. 별도 재실행 버튼이나 중복 없는 후보 생성은 구현하지 않았습니다.

발표용 예문·확인 기준·화면 자료는 [시연 안내](docs/DEMO_GUIDE.md)에 정리했습니다.

## 검증과 빌드

```powershell
npm.cmd run check
npm.cmd test
npm.cmd run test:browser
npm.cmd run build
npm.cmd start
```

| 명령 | 확인하는 것 |
|---|---|
| `check` | TypeScript 검사 |
| `test` | 선택·적용·문자열 차이·API·Gemini·엘리스 연결 모듈. 모델 응답은 테스트용으로 주입 |
| `test:browser` | Microsoft Edge에서 화면과 조작 검증. Edge가 설치되어 있어야 하며, 테스트 서버의 5174번 포트는 비어 있어야 함 |
| `build` | 타입 검사 후 화면·서버를 `dist/`로 빌드 |
| `start` | 빌드된 앱을 기본 5173번 포트에서 실행. 먼저 `build`를 실행하고 같은 포트의 개발 서버를 종료 |

자동 테스트는 외부 AI를 호출하지 않습니다. 브라우저 테스트는 키를 비운 별도 서버를 사용합니다. 개발 서버와 동시에 실행하면 Vite 자동 새로고침 포트가 겹칠 수 있으므로, 재현 가능한 검증을 위해 개발 서버를 종료한 뒤 실행하는 것을 권장합니다.

고정 사례의 실제 설명 품질을 비교하려면 `node --import tsx scripts/evaluate-explanations.mjs`를 사용합니다. **`LLM_PROVIDER=gemini` 설정에서 Gemini API를 최대 6회 호출하는 수동 평가 도구**입니다. 엘리스 설정에서는 호출 전에 중단하며, 제공자를 자동 전환하지 않습니다. 자동 테스트와 구분하세요. 결과는 `docs/evaluations/`에 저장되며 상세 해석은 검증 기록에 남깁니다.

## 현재 한계

- 설명에 실제 후보와 다른 표현을 인용하거나 의미 변화를 잘못 설명하는 사례가 있습니다.
- 인용 검사는 일부 오류를 걸러내지만, 원문에 없는 문법 용어까지 거절할 수 있습니다. 한 후보의 오류로 설명 전체가 숨겨질 수 있으며 재시도 성공을 보장하지 않습니다.
- 앱의 저장·로그인·히스토리, 카테고리·프리셋 설정, 외부 앱 문장 가져오기·적용, OS 전역 단축키는 구현하지 않았습니다.
- 실제 한국어 IME 조작, 팀원별 환경, 설명의 전반적 품질과 사용자 효과는 추가 확인 대상입니다.
- 테스트 통과는 정해진 사례의 동작 확인이며 모든 문장의 교정 정확성을 뜻하지 않습니다.

## 폴더 구조

아래는 현재 구현 기준의 구조이며 확정된 최종 구조가 아닙니다. 팀 협업 중 폴더·파일·코드·문서·설정·테스트·개발 도구와 작업 방식은 필요에 따라 조정할 수 있습니다. 변경 시 실행 방법, 관련 링크와 설계 문서도 함께 갱신합니다.

```text
writing-demo/
├── README.md
├── AGENTS.md
├── CONTRIBUTING.md      # 브랜치·PR·검증·업로드 기준
├── package.json / package-lock.json
├── client/src/          # 원문 입력·선택·교정 패널·후보 비교
├── server/             # API·로컬 실행·Gemini·엘리스 연결
├── shared/             # 요청·응답 스키마와 제한값
├── scripts/            # 빌드·설명 평가 도구
├── tests/              # 상태·API·브라우저 검증
```

`node_modules/`, `dist/`, `test-results/`는 설치·빌드·검증 시 생성되며 `.gitignore`에서 제외합니다. 비밀키 파일도 제외합니다.

## 협업 시작점

팀원은 작업 브랜치에서 수정한 뒤 PR을 올리고, 오정호의 검토·승인 후 오정호가 `main`에 병합합니다. 오정호 본인의 변경은 필요한 검증 후 별도 사전 승인 없이 직접 반영할 수 있습니다. 세부 절차와 GitHub 강제 설정의 구분은 [협업 안내](CONTRIBUTING.md#브랜치와-pr)를 따릅니다.

[PRD](docs/PRD.md)로 목적과 범위를 확인하고, [CONTRIBUTING](CONTRIBUTING.md)에 따라 작업합니다. 팀원들의 초대 수락과 README 기반 실행은 전달받았으며, 환경별 상세 확인과 사용 피드백은 계속 기록합니다. 실행 확인을 교정·설명 품질 전체의 검증 완료로 보지는 않습니다.

공동 작업 보드는 GitHub Projects로 준비할 예정입니다. 운영 전에는 [TASKS](docs/TASKS.md)에 작업 후보·담당·상태를 유지하고, 운영 후에는 Issues에서 작업 내용·완료 기준·논의를, Projects에서 상태·담당·우선순위를 관리합니다. 보드가 준비되면 TASKS에 실제 링크와 사용 안내를 남깁니다.
